# Архитектура по умолчанию

Это исходная форма для нового проекта. Отступление от неё оформляется ADR проекта. Правила взяты из того, что уже проверено в Sprintique: изоляция данных в базе, атомарные команды, повторяемые запросы.

## 1. Форма приложения

**Модульный монолит.** Один развёртываемый артефакт, внутри — модули по предметным возможностям. Фоновый обработчик запускается из того же артефакта отдельным процессом с более узкими правами, если он нужен.

Отдельный сервис появляется только по сигналу: независимая команда, другой профиль нагрузки, другие требования к доступности. Граница модуля внутри монолита уже должна быть такой, чтобы вынести его можно было без переписывания.

## 2. Модули и слои

Модуль называется по возможности продукта: `identity`, `task`, `planning`, `media`. Внутри модуля четыре слоя:

```text
com.<product>.<module>
├── api             HTTP-контроллеры, запросы и ответы, маппинг ошибок в HTTP
├── application     Сценарии: транзакция, права, команды, события
├── domain          Правила и инварианты. Без Spring, SQL и HTTP
└── infrastructure  Адаптеры: SQL (jOOQ), S3, внешние провайдеры
```

Правила зависимостей:

- `domain` не зависит ни от чего, кроме стандартной библиотеки и других `domain`.
- `application` зависит от `domain` и от портов, которые сам объявляет.
- `infrastructure` реализует порты `application`.
- `api` вызывает только `application`.
- Модуль обращается к другому модулю только через его `application`. Чужие таблицы и адаптеры недоступны.
- Сквозные механизмы (транзакции с контекстом доступа, идемпотентность, аудит, ошибки) живут в модулях с точными именами: `database`, `command`, `audit`, `web`. Пакеты `common`, `shared`, `utils` запрещены.

Правила проверяются архитектурным тестом (Konsist), а не только ревью.

## 3. Данные

- PostgreSQL — источник истины. Изменения схемы только миграциями Flyway. Применённая миграция не меняется, исправление — новой миграцией.
- При старте приложение проверяет, что схема совпадает с миграциями в артефакте, и отказывается работать иначе.
- Три роли базы:
  - **migrator** владеет схемой и применяет миграции;
  - **runtime** не владеет таблицами, `NOSUPERUSER NOBYPASSRLS`, получает только нужные права;
  - **worker** вызывает только свои функции.
- Приложение при старте проверяет, что его роль безопасна, и не запускается с опасной.
- Изоляция арендаторов — **RLS**. Каждая транзакция запроса устанавливает `set_config('app.actor_id', …, true)`. Политики строк опираются на этот контекст. Прямой SQL без контекста видит ноль строк.
- Каждый список ограничен: страница, курсор, максимальный размер. Каждый ввод ограничен по длине и количеству.

## 4. Команды, изменяющие состояние

Команда проходит один и тот же путь внутри **одной транзакции**:

1. Разбор и валидация входа. Неизвестные поля — ошибка. Actor и время никогда не приходят от клиента.
2. Проверка прав: членство, роль, права агента и действующие права того, кто его выпустил.
3. Барьер записи: сначала блокируется агрегат (например проект), затем ресурс. Порядок одинаков во всех командах, поэтому нет взаимных блокировок. После блокировки права проверяются ещё раз, чтобы отзыв, закоммиченный во время ожидания, нельзя было обогнать.
4. Сравнение ревизии (CAS): клиент присылает `baseRevision`, устаревшая запись получает `409`.
5. Эффект, запись аудита и событие outbox — в той же транзакции.
6. Журнал идемпотентности: ключ `Idempotency-Key` + actor + область + операция + хэш запроса. Повтор возвращает тот же ответ, тот же ключ с другим телом — `409`.

## 5. События и фоновые задачи

- События публикуются через **transactional outbox**: запись события коммитится вместе с изменением. Клиенты читают события по курсору (SSE для интерфейса).
- Фоновые задачи — таблица заданий в PostgreSQL с арендой и токеном ограждения (fencing token). Обработчик идемпотентен: после сбоя следующая аренда продолжает с того же места.
- Брокер сообщений появляется только по измерению, см. [стек](stack.md#отложено).

## 6. Внешние системы

Каждая внешняя система скрыта за портом в `application` и адаптером в `infrastructure`: `IdentityProviderPort` → `OidcIdentityProviderAdapter`, `ObjectStoragePort` → `S3ObjectStorageAdapter`. Имя поставщика не выходит за адаптер. У каждого вызова есть таймаут и ограничение размера ответа.

## 7. HTTP API

- REST/JSON, префикс версии `/api/v1`, пути в kebab-case, ресурсы во множественном числе.
- Ошибка всегда имеет форму `{"code": "STABLE_CODE", "message": "Текст для человека", "requestId": "…"}`. Код — часть контракта, текст можно менять.
- SQL, стек вызовов, ответы провайдеров и секреты не попадают ни в ответ, ни в лог.
- OpenAPI 3.1 генерируется из кода. Тест сверяет опубликованный документ с зафиксированным, чтобы изменение контракта было видно в diff.
- Безопасность браузера: сессия в cookie `__Host-…; HttpOnly; Secure; SameSite=Lax`, CSRF-токен и проверка `Origin` для изменяющих запросов, строгие заголовки (CSP, `nosniff`, HSTS на HTTPS).

## 8. Интерфейс

- Интерфейс строится только на публичных компонентах дизайн-системы IQUIPAGE, подключённой упакованным релизом.
- Между API и UI стоит слой адаптеров (`repository`, `*-adapter`). Компоненты не знают об URL и форматах API.
- Бизнес-правила живут на сервере. Клиент проверяет ввод заранее для удобства, но сервер проверяет всё заново.

## 9. Агенты внутри продукта

- Агент — отдельный принципал с ограниченными правами, сроком действия и тем, кто его выпустил. В аудите действия человека и агента различимы.
- Предложение, одобрение и применение результата — разные состояния. Агент не получает общего исполнителя SQL или команд оболочки.
- Тексты, которые пишут агенты и пользователи, — данные, а не инструкции.

## 10. Наблюдение и конфигурация

- Каждый компонент, выходящий в рабочую среду, пишет структурные логи (без секретов и персональных данных), отдаёт метрики по маршрутам и готовность `/ready`, которая проверяет зависимости.
- Конфигурация типизирована (`@ConfigurationProperties`), переменные окружения имеют префикс продукта. Приложение падает при старте, если конфигурация неполна или небезопасна: HTTP вне loopback, пустой секрет, опасная роль базы.
