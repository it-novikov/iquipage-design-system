# Мост

Мост позволяет нескольким агентам и людям работать над одной задачей по очереди, не пересказывая друг другу историю. Вся работа живёт в **карточке задачи**:

- цель и рамки;
- критерии приёмки задачи;
- план: у каждого шага «что», «как», «зачем», критерии и итог;
- решения и вопросы;
- раздел «Передача» с текущим состоянием.

Новый агент читает сжатую сводку карточки — до 7000 символов — вместо истории чата, которая занимает сотни тысяч токенов, и продолжает с того же места.

## Зачем

| Проблема | Как её решает мост |
|---|---|
| Кончился лимит подписки или API вернул ошибку посреди работы | Передача фиксируется автоматически: хуком Claude Code или эстафетой. Эстафета сразу запускает следующего агента цепочки |
| Новый агент тратит много токенов на изучение контекста | `bridge brief` отдаёт только нужное: цель, рамки, приёмку, передачу, активный шаг и два следующих, свежие решения |
| После сжатия контекста агент теряет детали | Хук `SessionStart` после сжатия подкладывает сводку карточки |
| Непонятно, что сделано и чем это доказано | У шагов и задачи есть критерии приёмки, у готового шага — итог с доказательством; `bridge check` это проверяет |
| Два агента правят одно и то же, в том числе из разных worktree | Аренда в общем каталоге git: пока она жива, второй агент задачу не возьмёт и не изменит |
| Человеку трудно следить за агентами | Карточка — обычный Markdown, читается на GitHub, правится руками |
| Непонятно, стал ли процесс быстрее | `bridge stats`: время цикла по уровням риска, раунды ревью, P0/P1, передачи по причинам |

## Главная идея: всегда готово к передаче

Агент, у которого кончился лимит, уже не может написать хорошую сводку. Поэтому мост не полагается на прощальное резюме. Агент ведёт карточку **по ходу работы**: после каждого законченного куска записывает короткую контрольную точку. При обрыве мост дописывает только то, что собирается без модели: ветку, коммит, изменённые файлы, причину и время. Качество передачи зависит от дисциплины контрольных точек, а не от удачи в момент сбоя.

## Понятия

- **Карточка** `.bridge/tasks/<id>/task.md` — единственный источник правды о задаче. Формат — в [FORMAT.md](FORMAT.md).
- **Критерии приёмки задачи** (`A1`, `A2`, …) — проверяемый результат. Каждый критерий покрыт хотя бы одним шагом (`Покрывает: A1`).
- **Шаг** — единица плана: что, как, зачем, критерии шага, итог.
- **Передача** — раздел карточки:
  - состояние;
  - текущий шаг;
  - следующее действие;
  - незакоммиченное со слов агента и механический снимок рабочей копии;
  - ловушки;
  - как проверить;
  - причина последней передачи.
- **Аренда** — кто держит задачу, в какой сессии и до какого времени. Хранится вне рабочего каталога, в `$(git rev-parse --git-common-dir)/bridge/leases/`, поэтому общая для всех worktree и не шумит в diff. Контрольная точка продлевает аренду, передача освобождает. Изменяющие команды отказывают (код 3), если задачу держит другой.
- **Журнал** — история событий по строке на событие. В контекст агента попадают только последние записи.
- **Эстафета** — `bridge run`: запускает агентов по цепочке и передаёт задачу по триггерам.
- **Триггер** — событие, после которого работа переходит к другому агенту: лимит, ошибка авторизации, падение, таймаут, переполнение контекста.

## Кто действует

Каждая команда пишет от имени действующего лица. Порядок:

1. `--agent`.
2. Переменная `BRIDGE_AGENT`. Её задают эстафета и хук Claude Code при старте сессии.
3. Иначе `human:<пользователь>`: агент не подписывается чужим именем незаметно.

Хук `SessionStart` дополнительно записывает `BRIDGE_SESSION` — идентификатор сессии Claude Code. Аренда, взятая в этой сессии, принадлежит только ей: другая вкладка Claude Code с тем же именем агента её не отпустит.

## Быстрый старт

```bash
alias bridge="$PWD/engineering/bridge/bin/bridge"   # из корня репозитория

bridge init                                          # один раз на репозиторий
bridge new kotlin-backend --title "Перенос бэкенда на Kotlin" --risk high --owner it-novikov
# заполните «Цель» и «Рамки» в .bridge/tasks/<id>/task.md
bridge accept "API-тесты проходят против нового бэкенда"
bridge add-step --title "Каркас Gradle" --what "…" --how "…" --why "…" --accept "./gradlew check зелёный" --covers A1
bridge check
```

Работа агента по [протоколу](PROTOCOL.md):

```bash
export BRIDGE_AGENT=codex                            # в Claude Code это делает хук
bridge brief
bridge claim
bridge checkpoint --state "…" --now "S1 — …" --next "…" --trap "…"
bridge step S1 done --check all --result "коммит abc1234; 12 тестов"
bridge accept --done A1
bridge handoff --reason planned
```

Передать задачу любому агенту, в том числе в веб-интерфейсе:

```bash
bridge prompt --agent codex > /tmp/prompt.md          # протокол + сводка, вставить агенту
```

Полный список команд — `bridge help`.

## Триггеры и передача между агентами

### Эстафета

```bash
bridge run                        # цепочка из .bridge/config.json
bridge run --chain codex,claude   # своя цепочка
bridge run --after claude-code    # продолжить после агента, который упёрся в лимит
bridge run --wait                 # если все агенты упёрлись в лимит, дождаться восстановления
bridge run --dry-run              # показать, кто и какой командой будет запущен
```

Что происходит:

1. Берётся первый доступный агент цепочки. Если у активного шага указано `Модель: fast`, берётся первый доступный агент с `"model": "fast"`. Агент получает промпт: протокол и сводку.
2. После завершения процесса мост смотрит код выхода и **последние строки** вывода: 30 строк stderr и 10 строк stdout.
3. Решение принимается по таблице ниже.

| Исход | Признак | Действие |
|---|---|---|
| Задача ушла из работы | статус `review`, `done`, `blocked`, `cancelled` | Эстафета завершена |
| Сессия закончилась нормально | код 0, задача в работе | Новая сессия того же агента с новой сводкой. Две сессии без продвижения ставят задачу в `blocked`: нужен человек |
| Лимит | код ≠ 0 и сигнал `limit` | Передача. Агент недоступен до времени восстановления из сообщения, а если его нет — час. Дальше следующий агент |
| Ошибка авторизации | сигнал `auth` | Передача, следующий агент |
| Перегрузка сервиса | сигнал `overloaded` | Повтор того же агента с паузой (30 с, 2 мин), затем следующий |
| Переполнение контекста | сигнал `context` | Новая сессия того же агента: карточка несёт контекст |
| Падение или таймаут | иное | Передача с причиной `error` или `timeout`, следующий агент |
| Все недоступны | — | Запись в журнал, код выхода 75 и время, когда повторить |

Продвижением считается изменение самой работы или карточки: коммиты, diff, контрольные точки, шаги. Взятие и освобождение аренды продвижением не считается, поэтому агент, который только открывает и закрывает сессии, не крутится до предела раундов.

Сигналы — регулярные выражения в `.bridge/config.json` для каждого агента, по формулировкам провайдера. Они проверяются только при ненулевом коде выхода и только в последних строках вывода. Поэтому агент, который пишет код ограничения запросов или гоняет тесты с `401`, не считается упёршимся в лимит.

**Права агента в эстафете.** Агент работает без человека и не может подтвердить разрешение. Всё, что ему нужно, перечисляется в команде агента. Для Claude Code это `--allowedTools`: CLI моста, git и команды проверок проекта. Шаблон разрешает только мост и git. Команды сборки и тестов добавьте под свой проект — в этом репозитории разрешены проверки Sprintique и дизайн-системы (`npm test`, `npm run …`, `./gradlew …`, `node scripts/…`). `bridge run --dry-run` показывает итоговую команду.

**Аренда в эстафете** принадлежит эстафете, а не сессии, из которой её запустили. Когда следующий шаг уходит другому агенту цепочки, эстафета сама переносит аренду. Хуки внутри эстафеты ничего не экспортируют и не освобождают.

### Хуки Claude Code

В интерактивной работе с Claude Code триггер приходит без эстафеты. Хуки описаны в `.claude/settings.json` репозитория.

| Событие | Что делает мост |
|---|---|
| `SessionStart` | Записывает `BRIDGE_SESSION` и `BRIDGE_AGENT` для команд сессии. При запуске выдаёт одну строку: открытые задачи и вопросы, которые больше суток ждут владельца |
| `SessionStart` после сжатия (`compact`) или `/clear` | Подкладывает в контекст сводку задачи этой сессии. После `/clear` новая сессия принимает аренду предыдущей |
| `SessionStart` при возобновлении | Одна строка: история сессии и так в контексте |
| `StopFailure` с `rate_limit`, `billing_error`, `account_on_hold` | Передача с причиной `limit`: аренда освобождена, в карточке причина и снимок рабочей копии |
| `StopFailure` с ошибками авторизации | Передача с причиной `auth` |
| `StopFailure` с иными ошибками | Запись в журнал, задача остаётся за агентом |
| `PreCompact` | Запись в журнал |
| `SessionEnd` | Аренда этой сессии освобождается; при `/clear` сохраняется для следующей сессии |

Хуки действуют только на аренду своей сессии. Ошибка хука не ломает сессию.

После передачи по лимиту задача свободна, но следующий агент сам не стартует: человек запускает `bridge run --after claude-code`. Если в `.bridge/config.json` включено `"relay": {"fromHooks": true}`, хук сам запускает эту эстафету в фоне и пишет её лог в `.bridge/runs/<id>/`. По умолчанию это выключено: фоновый запуск агентов — решение владельца.

Внутри эстафеты хуки не освобождают аренду и не передают задачу: это делает эстафета, которая видит исход целиком.

### Codex, Gemini и другие

У них нет хука на ошибку API, поэтому их запускают через эстафету, которая видит код выхода. В интерактивном режиме агент ведёт карточку по протоколу. Если сессия оборвалась, человек выполняет `bridge handoff --reason limit --agent codex` (от имени держателя) или ждёт истечения аренды, а следующий агент стартует с `bridge prompt`.

## Ревью

```bash
bridge review --reviewer codex                  # раунд 1: пакет ревьюера и файл reviews/R1.md
bridge review --reviewer gemini                 # второй ревьюер того же раунда: свой файл R2.md
bridge review --reviewer claude --since R1      # раунд 2: замечания R1 и только изменения после него
```

Пакет ревью — критерии задачи, список изменённых файлов и место для замечаний. История автора в него не входит. Повторное ревью (`--since`) проверяет исправления полностью, остальное выборочно. `bridge status done` отказывает, пока в отчётах есть открытые P0/P1.

## Экономия токенов

- Сводка ограничена бюджетом — 7000 символов по умолчанию. Для русского текста это порядка 3–4 тысяч токенов. Если сводка не помещается, первыми сворачиваются будущие шаги, затем готовые, затем старые решения.
- Готовые шаги показываются одной строкой с итогом. Полностью показаны только активный шаг и два следующих.
- Протокол в промпте — 20 строк. Подробности — в этом документе, агент читает их по надобности.
- Журнал в сводку не попадает, кроме последних записей. Подробности — по ссылкам в «Контексте».
- Ревьюер получает пакет, а не историю автора. Повторное ревью смотрит только исправления.
- Механические шаги можно отдать более дешёвой модели: `Модель: fast` у шага и агент с `"model": "fast"` в цепочке.

## Люди и карточки

Карточку можно править руками в любом редакторе. Потом выполните `bridge check`. Он найдёт:

- нарушенный формат;
- незаполненные поля;
- шаг, отмеченный готовым без доказательства;
- критерии, не покрытые шагами;
- уровень риска ниже того, что требуют изменённые файлы (`riskFloor` в конфигурации);
- строки, похожие на секреты.

Одна повреждённая карточка не мешает командам и хукам работать с остальными. Эту же проверку стоит запускать в CI и pre-commit.

## Проверка самого моста

```bash
cd engineering/bridge && npm test
```

Тесты используют поддельных агентов и настоящие git-репозитории. Они проверяют:

- лимит и передачу;
- застой, в том числе агента, который только дёргает хуки;
- выбор дешёвой модели;
- исчерпание цепочки;
- аренду в worktree;
- хуки чужой сессии;
- ревью в параллель и повторное ревью.

Настоящие модели в тестах не вызываются.
