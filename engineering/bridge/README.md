# Мост

Мост позволяет нескольким агентам и людям работать над одной задачей по очереди, не пересказывая друг другу историю. Вся работа живёт в **карточке задачи**: цель, рамки, план с критериями приёмки, решения, вопросы и раздел «Передача» с текущим состоянием. Новый агент читает сжатую сводку карточки (1–2 тысячи токенов) вместо истории чата (сотни тысяч) и продолжает с того же места.

## Зачем

| Проблема | Как её решает мост |
|---|---|
| Кончился лимит подписки или API вернул ошибку посреди работы | Хук или эстафета фиксирует передачу автоматически, следующий агент в цепочке продолжает |
| Новый агент тратит много токенов на изучение контекста | `bridge brief` отдаёт только нужное: цель, рамки, передачу, активный шаг, два следующих, свежие решения |
| После сжатия контекста агент теряет детали | Хук `SessionStart` после сжатия подкладывает сводку карточки |
| Непонятно, что сделано и чем это доказано | У каждого шага есть критерии приёмки и «Итог» с доказательством, `bridge check` это проверяет |
| Два агента правят одно и то же | Аренда (`holder` + `lease`): пока она жива, второй агент задачу не берёт |
| Человеку трудно следить за агентами | Карточка — обычный Markdown, читается на GitHub, правится руками |

## Главная идея: всегда готово к передаче

Агент, у которого кончился лимит, уже не может написать хорошую сводку. Поэтому мост не полагается на прощальное резюме. Агент ведёт карточку **по ходу работы**: после каждого законченного куска — короткая контрольная точка. При обрыве мост дописывает только то, что можно собрать без модели: ветку, коммит, незакоммиченные файлы, причину и время. Качество передачи определяется дисциплиной контрольных точек, а не удачей в момент сбоя.

## Понятия

- **Карточка** `.bridge/tasks/<id>/task.md` — единственный источник правды о задаче. Формат — в [FORMAT.md](FORMAT.md).
- **Передача** — раздел карточки: состояние, текущий шаг, следующее действие, незакоммиченное, ловушки, проверка, причина последней передачи.
- **Шаг** — единица плана: что, как, зачем, критерии приёмки, итог.
- **Аренда** — кто держит задачу и до какого времени. Контрольная точка продлевает её, передача освобождает.
- **Журнал** — история событий, по строке на событие. В контекст агента попадают только последние записи.
- **Эстафета** — `bridge run`: запускает агентов по цепочке и передаёт задачу по триггерам.
- **Триггер** — событие, после которого работа переходит к другому агенту: лимит, ошибка авторизации, падение, таймаут, переполнение контекста.

## Быстрый старт

```bash
alias bridge="$PWD/engineering/bridge/bin/bridge"   # из корня репозитория

bridge init                                          # один раз на репозиторий
bridge new kotlin-backend --title "Перенос бэкенда на Kotlin" --risk high --owner it-novikov
# заполните «Цель» и «Рамки» в .bridge/tasks/<id>/task.md
bridge add-step --title "Каркас Gradle" --what "…" --how "…" --why "…" --accept "./gradlew check зелёный"
bridge check
```

Работа агента (он делает это сам по [протоколу](PROTOCOL.md)):

```bash
bridge brief                                         # что делать
bridge claim --agent claude
bridge checkpoint --state "…" --now "S1 — …" --next "…" --trap "…"
bridge step S1 done --check all --result "коммит abc1234; 12 тестов"
bridge handoff --reason planned
```

Передать задачу вручную любому агенту, в том числе в веб-интерфейсе:

```bash
bridge prompt --agent codex > /tmp/prompt.md          # протокол + сводка, вставить агенту
```

Полный список команд — `bridge help`.

## Триггеры и передача между агентами

### Эстафета

```bash
bridge run                        # цепочка из .bridge/config.json
bridge run --chain codex,claude   # своя цепочка
bridge run --wait                 # если все агенты упёрлись в лимит, дождаться восстановления
```

Что происходит:

1. Берётся первый доступный агент цепочки, он получает промпт: протокол + сводка.
2. После завершения процесса мост смотрит код выхода и хвост вывода.
3. Решение:

| Исход | Признак | Действие |
|---|---|---|
| Задача ушла из `active` | статус `review`, `done`, `blocked` | Эстафета завершена |
| Сессия закончилась нормально | код 0, задача активна | Новая сессия того же агента с новой сводкой; две сессии без продвижения — остановка |
| Лимит | код ≠ 0 и сигнал `limit` | Передача, агент недоступен до времени восстановления из сообщения (или час), дальше следующий |
| Ошибка авторизации | сигнал `auth` | Передача, следующий агент |
| Перегрузка сервиса | сигнал `overloaded` | Повтор того же агента с паузой (30 с, 2 мин), затем следующий |
| Переполнение контекста | сигнал `context` | Новая сессия того же агента: карточка несёт контекст |
| Падение или таймаут | иное | Передача с причиной `error`/`timeout`, следующий агент |
| Все недоступны | — | Запись в журнал, код выхода 75 и время, когда повторить |

Сигналы — регулярные выражения в `.bridge/config.json` для каждого агента. Сигналы проверяются только при ненулевом коде выхода, чтобы агент, который пишет код ограничения запросов, не считался упёршимся в лимит.

### Хуки Claude Code

В интерактивной работе с Claude Code триггер приходит без эстафеты. Хуки в `.claude/settings.json` репозитория:

| Событие | Что делает мост |
|---|---|
| `StopFailure` с `rate_limit`, `billing_error`, `account_on_hold` | Передача с причиной `limit`: аренда освобождена, в карточке причина и незакоммиченные файлы |
| `StopFailure` с ошибками авторизации | Передача с причиной `auth` |
| `StopFailure` с `overloaded`, `server_error` | Запись в журнал, задача остаётся за агентом |
| `PreCompact` | Запись в журнал |
| `SessionStart` после сжатия или при возобновлении | В контекст подкладывается сводка карточки |
| `SessionStart` при запуске | Одна строка: какие задачи открыты |
| `SessionEnd` | Аренда освобождается |

Хуки действуют только на задачу, которую держит этот агент (`BRIDGE_AGENT`, по умолчанию `claude-code`). Посторонняя сессия Claude Code в том же репозитории чужую задачу не тронет. Ошибка хука никогда не ломает сессию.

### Codex, Gemini и другие

У них нет хука на ошибку API, поэтому их запускают через эстафету, которая видит код выхода. В интерактивном режиме агент ведёт карточку по протоколу. Если сессия оборвалась, человек выполняет `bridge handoff --reason limit --agent codex`, и следующий агент стартует с `bridge prompt`.

## Экономия токенов

- Сводка ограничена бюджетом (по умолчанию 7000 символов ≈ 1,5–2 тысячи токенов). Если не помещается, сначала сворачиваются будущие шаги, потом готовые, потом старые решения.
- Готовые шаги — по одной строке с итогом. Полностью показаны только активный шаг и два следующих.
- Журнал в сводку не попадает, кроме последних записей. Подробности — по ссылкам в «Контексте», их читают по мере надобности.
- Ревьюер получает не историю автора, а пакет: критерии, список изменённых файлов, место для замечаний (`bridge review`).
- Механические шаги можно отдавать более дешёвой модели: у шага есть поле «Модель» (`strong`/`fast`).

## Люди и карточки

Карточку можно править руками в любом редакторе. После правки выполните `bridge check`: он найдёт нарушенный формат, незаполненные поля, отмеченный «готовым» шаг без доказательства и похожие на секреты строки. Эту же команду стоит запускать в CI и в pre-commit.

## Проверка самого моста

```bash
cd engineering/bridge && npm test
```

Тесты используют поддельных агентов: один упирается в лимит, второй завершает задачу. Так проверяется вся эстафета без обращения к настоящим моделям.
