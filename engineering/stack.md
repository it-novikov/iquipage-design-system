# Базовый стек

Статус: **рабочая основа**, пересматривается при новых требованиях. Дата линии: 27.09.2026.

Документ отвечает на вопрос, какими технологиями мы разрабатываем. Он не описывает функции продукта и не выбирает архитектуру конкретного проекта. Технология из таблицы берётся, только когда проекту нужна соответствующая часть.

Статусы:

- **Основной** — используем по умолчанию.
- **Условный** — используем, если эта часть системы действительно нужна.
- **Отложен** — выберем, когда появятся требования.

## Эталонный проект

Перед широкой разработкой на новой линии стека один проект подтверждает её совместимость. Для текущей линии это каркас бэкенда Sprintique. Он должен подтвердить:

- Kotlin, JDK, Spring Boot и Gradle собираются вместе, ktlint и Detekt проходят;
- HTTP API принимает и возвращает JSON по строгим правилам;
- запросы к PostgreSQL через jOOQ выполняются в транзакции с RLS-контекстом;
- Flyway создаёт схему с нуля;
- модульные, интеграционные и архитектурные тесты работают;
- собирается контейнер;
- доступны структурные логи и метрики;
- зависимости закреплены lock-файлами и проверены на известные уязвимости.

Смена мажорной версии Kotlin, Spring Boot или Gradle повторяет эту проверку.

## Отложено

| Область | Когда решать |
|---|---|
| Микросервисы, отдельные сервисы | Когда появятся независимые команды или требования к независимому запуску |
| Очереди и брокеры сообщений | Когда таблица заданий в PostgreSQL перестанет справляться по измерениям |
| Redis и общий кэш | Когда измерения покажут общее состояние между несколькими экземплярами |
| Поиск вне PostgreSQL | Когда появятся данные и критерии качества поиска |
| Долгие процессы (Temporal и аналоги) | Когда появятся процессы с ожиданием, повторами и восстановлением |
| Облако, Kubernetes, IaC | Когда появятся требования к регионам, стоимости и доступности |
| AI-фреймворки внутри продукта | Когда появятся сценарии, модели и требования безопасности |

## Как добавить технологию

1. Опишите требование простыми словами и с числами, если они известны.
2. Проверьте, решает ли его уже выбранный стек.
3. Если нет, сравните два-три варианта по сложности, стоимости и рискам. При сомнении сделайте POC.
4. Оформите ADR: какое требование закрывается, кто владелец, как тестируется и обновляется, сколько стоит, как от неё отказаться.
5. Обновите этот документ после принятия решения, не до.
