# 0004. Problem-first разбор внутри существующего процесса

- **Статус:** proposed
- **Дата:** 2026-10-11
- **Владелец:** владелец репозитория

## Контекст

Четыре IQUIPAGE skills уже разделяют discovery, аудит, внедрение и ревью. Их краткий brief недостаточно явно сохраняет конкурирующие причины, изменяемые продуктовые решения и выбор не строить новую функцию. Исторический DS baseline 0.5.7 можно ошибочно принять за текущую поставку. Новый параллельный процесс увеличил бы объём контекста и риск противоречий.

## Решение

Уточнить существующие skills и шаблоны, сохранив имена и acceptance schema 2.0. В одной task/brief/finding card связывать эпизод и человеческий результат с причиной, необходимыми гарантиями, вариантами, небольшой проверкой и решением. Глубина соответствует неопределённости и риску: ясному багу не нужны интервью и искусственные альтернативы; полный аудит имеет явный inventory всех согласованных семейств.

Не добавлять новые approval/release gates и не менять risk tiers. Существующая авторизация сохраняется. Текущий DS устанавливается по exact package потребителя; historical lock остаётся историческим. Общие сведения переносимы, маршруты и preview-ограничения Sprintique принадлежат продуктовой документации. Canonical skills и клиентские копии синхронизируются явно и детерминированно.

## Альтернативы

| Вариант | Почему не выбран |
|---|---|
| Пятый универсальный skill и отдельные JTBD/CJM/PRD | Повторяет существующую ответственность и увеличивает контекст каждой задачи. |
| Только большой отчёт вне репозитория | Следующий агент не получает короткий актуальный путь и воспроизводимые сценарии. |
| Новый полный mock backend для аудита | У продукта уже есть настоящий temporary preview; UI-fixtures нужны только при конкретном пробеле обратной связи. |
| Переписать historical pin на новую версию | Изменение числа не доказывает совместимость или выполненные проверки. |

## Последствия и пересмотр

Стоимость — одна краткая причинно-решенческая запись для неоднозначной задачи и поддержание route index. Статические проверки подтверждают формат и целостность, а качество работы проверяется независимыми заданиями/ревью; model cases остаются NOT_RUN до реальных запусков. Пересмотреть метод, если он повторно порождает лишние согласования, скрывает непроверенное или не меняет качество принятого решения. При отказе убрать дополнительный reference и поля; приложение, API и schema 2.0 не мигрируются.
