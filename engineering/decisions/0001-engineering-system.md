# 0001. Единая инженерная система и базовый стек

- **Статус:** accepted
- **Дата:** 2026-09-27
- **Владелец:** it-novikov

## Контекст

У нас есть дизайн-система IQUIPAGE для интерфейса, но нет общей основы для остального: каждый проект заново выбирал язык бэкенда, структуру, правила имён, способ тестирования и процесс. Sprintique сделан на Node/Fastify, соседний проект Jarnee — на Kotlin/Spring с детальными правилами имён, качества и поставки. Агенты в каждом проекте получают разные правила и тратят токены на их изучение.

## Решение

1. Завести `engineering/` — инженерную систему, общую для всех проектов: принципы, стек, архитектуру, имена, качество, тестирование, безопасность, процесс, ревью и мост для агентов.
2. Базовый стек backend — линия Jarnee: Kotlin 2.3.21, JDK 25, Spring Boot 4.1, Spring MVC, PostgreSQL, jOOQ, Flyway, Jackson 3, OpenAPI 3.1, Gradle 9.6 Kotlin DSL, JUnit 6, Testcontainers 2, Micrometer/OpenTelemetry. Версии библиотек — из BOM Spring Boot.
3. Frontend — дизайн-система IQUIPAGE на нативных Web Components, Vite, TypeScript strict в контрактах и клиентах.
4. Правила имён Jarnee обобщены на все языки и приняты как [конвенция](../conventions/naming.md).

## Альтернативы

| Вариант | Почему не выбран |
|---|---|
| Kotlin только для новых проектов, Sprintique остаётся на Node до измеримого сигнала | Рассмотрено. Сэкономило бы перенос: ≈3000 строк плотного TypeScript, около 100 маршрутов, 29 файлов тестов, по оценке несколько дней работы агента. Против: продукт ещё не в production, дальше он будет только расти, а владелец явно решил переносить сейчас, пока это дешевле всего. Решение по переносу — отдельный ADR продукта с оценкой и планом |
| Оставить Node/TypeScript во всех проектах | Две линии бэкенда в компании; меньше типобезопасности SQL; правила Jarnee и опыт команды на JVM |
| Правила в каждом проекте отдельно | Расхождение правил, повторная работа, агенты учат одно и то же заново |
| Микросервисная основа | Нет требований к независимому запуску; модульный монолит закрывает текущие задачи |

## Последствия

- Новый проект начинается с копии `engineering/` и не выбирает основы заново.
- Sprintique переносит бэкенд на Kotlin: это отдельная задача высокого риска со своим ADR продукта. Каркас Sprintique служит эталонным проектом линии стека ([стек](../stack.md#эталонный-проект)).
- Старый код остальных проектов переносится только по своему ADR с оценкой, а не как следствие этого решения.
- Две среды инструментов: JVM для бэкенда, Node для фронтенда и CLI моста.
- Версии Kotlin и Detekt связаны: обновляются одним изменением.

## Условия пересмотра

Появление стабильного Detekt 2.x; требования, которые стек не закрывает (см. «Отложено» в [стеке](../stack.md)); измеримые проблемы производительности JVM-приложений.
