# 0002. Мост: карточка задачи в Markdown как формат передачи работы

- **Статус:** accepted
- **Дата:** 2026-09-27
- **Владелец:** it-novikov

## Контекст

Над одной задачей работают разные агенты (Claude Code, Codex и другие) и люди. Сейчас передача работы — это либо чтение всей истории чата (сотни тысяч токенов), либо свободный handoff-документ, качество которого зависит от автора и который не пишется, если агент упал на лимите. Нужен единый формат, который читают и люди, и программы, и способ передавать работу автоматически по триггеру.

## Решение

1. **Карточка задачи** — Markdown-файл с YAML-заголовком и фиксированной грамматикой разделов и полей (`.bridge/tasks/<id>/task.md`). Это единственный источник правды. Формат — [FORMAT.md](../bridge/FORMAT.md), модель данных — [JSON Schema](../bridge/schema/task.v1.schema.json).
2. **Протокол «всегда готово к передаче»**: агент пишет контрольные точки по ходу работы. При обрыве мост дописывает только механически собираемые факты.
3. **CLI без зависимостей** на Node (`engineering/bridge/bin/bridge`): создание, проверка, сводка с бюджетом, аренда, контрольные точки, передача, пакет ревью, эстафета агентов.
4. **Триггеры**: хуки Claude Code (`StopFailure`, `SessionStart`, `PreCompact`, `SessionEnd`) и эстафета `bridge run`, которая классифицирует завершение агента по коду выхода и сигналам в выводе.
5. **Та же модель в продукте**: план работы задачи в Sprintique использует модель `bridge/1`, чтобы карточка переходила между репозиторием и платформой без перевода ([проект](../../products/sprintique/docs/agent-bridge.md)).

## Альтернативы

| Вариант | Почему не выбран |
|---|---|
| Только JSON или YAML | Неудобно читать и править людям, плохо смотрится в PR |
| Свободный Markdown-handoff | Не проверяется машиной, нет гарантии полноты, нельзя собрать сводку по бюджету |
| Трекер задач как источник правды | Агент в репозитории без доступа к сети или токена теряет контекст; вернёмся к этому через синхронизацию с Sprintique |
| Резюме от уходящего агента | Не пишется при сбое лимита; качество непредсказуемо |

## Последствия

- Агент тратит на вход в задачу около 1,5–2 тысяч токенов вместо истории чата.
- Нужна дисциплина контрольных точек. Протокол требует их после каждого законченного куска.
- Карточки лежат в git и видны в PR, поэтому `bridge check` запрещает похожее на секреты.
- Формат версионируется. CLI не меняет карточки незнакомой версии.

## Условия пересмотра

Карточки систематически длиннее 600 строк; агенты игнорируют контрольные точки (видно по журналу); появление стандартного межагентного формата с поддержкой у основных агентов.
