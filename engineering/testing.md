# Тестирование

Тест нужен, чтобы изменение можно было безопасно сделать завтра. Тест, который не упадёт при реальной поломке, хуже отсутствия теста: он создаёт ложную уверенность.

## Что каким тестом проверяем

| Что проверяется | Вид теста | Где выполняется | Скорость |
|---|---|---|---|
| Правила и инварианты предметной области | Модульный | Без Spring, без базы | миллисекунды |
| SQL, транзакции, RLS, блокировки, миграции | Интеграционный | Настоящий PostgreSQL (Testcontainers или изолированный кластер) | секунды |
| HTTP-контракт, права, CSRF, коды ошибок, идемпотентность | API-тест «чёрным ящиком» | Запущенное приложение, запросы по HTTP | секунды |
| Границы модулей и слоёв | Архитектурный | ArchUnit / скрипты проверки границ | секунды |
| Совпадение OpenAPI с кодом | Контрактный | Сравнение с зафиксированным документом | секунды |
| Интерфейс: состояния, адаптеры, жизненный цикл | Модульный для адаптеров, браузерный сценарий для потоков | Node / браузер | секунды–минуты |
| Нагрузка | Нагрузочный | Отдельный прогон | по требованию |

Правила выбора:

- Предметное правило — модульным тестом. Если для проверки правила нужен Spring, правило лежит не в том слое.
- Всё, что зависит от поведения базы (RLS, блокировки, ограничения, `ON CONFLICT`), проверяется только на настоящем PostgreSQL. Моки базы не пишем.
- API-тесты обращаются к приложению по HTTP и не импортируют его код. Такой тест не знает, на каком языке написано приложение, и переживает смену реализации. Сценарии, которым нужно вмешаться внутрь (отказ хранилища, гонка под блокировкой, отзыв прав во время ожидания), — это интеграционные тесты на языке приложения с фейками портов.
- Моки допустимы только на внешних границах: провайдер идентичности, S3, часы. Предпочтительнее фейк-реализация порта, чем мок-фреймворк.

## Обязательные сценарии для каждого изменяющего эндпоинта

- без аутентификации → `401`;
- чужой проект → `404` (не `403`, чтобы не раскрывать существование);
- недостаточно прав → `403`;
- CSRF: нет токена или чужой `Origin` → `403`;
- неизвестное поле, неверная дата, превышение лимита → `400` или `422`;
- устаревшая ревизия → `409`;
- повтор с тем же `Idempotency-Key` → тот же ответ, одна запись аудита и одно событие;
- тот же ключ с другим телом → `409`.

## Данные для тестов

- Тесты создают свою базу, роли и пространство имён хранилища и удаляют только их. Пользовательские базы и хранилища тестам недоступны.
- Фикстуры называются по состоянию: `projectWithActiveRelease`. Никаких `testData`, `foo`, `dummy`.
- Время в тестах управляется через `Clock`, а не `sleep`.

## Исправление ошибки

Сначала тест, который воспроизводит ошибку и падает. Затем исправление. Если такой тест сделать неразумно дорого, это записывается в карточку задачи с причиной.

## Проверки перед коммитом и слиянием

| Когда | Что запускается |
|---|---|
| Перед коммитом (хук) | Формат и статический анализ staged-снимка |
| Перед ревью | Полный набор тестов модуля и API-тесты затронутых маршрутов |
| Release gate | Всё: сборка, качество, модульные, интеграционные, API, контракт, миграция с нуля, отделяемость продукта |

Пропущенный тест — это непройденная проверка, а не зелёная. Если S3 или провайдер недоступны и часть тестов пропущена, отчёт говорит об этом прямо.
