# 0003. Финансы проекта: журнал операций

- **Статус:** proposed
- **Дата:** 2026-09-29
- **Владелец:** it-novikov
- **Основание:** задача владельца 2026-09-29 (журнал операций проекта; счета, переводы, гипотезы, сценарии и курсы — вне рамок), карточка `.bridge/tasks/20260928-project-finance`

## Контекст

В пилоте Sprintique (sprintique.jarnee.com) у проекта был учёт денег: `project_finance_settings` (валюта, по умолчанию RUB) и `project_finance_entries` (доход или расход, сумма в минимальных единицах, дата, категория, описание, контрагент, основание, статус posted/voided с причиной аннулирования, версия, неизменяемые ревизии, итоги по проекту). Там есть реальные данные: 6 операций в 2 проектах, часть аннулирована или исправлена; их загрузит отдельный импортёр. Более поздний прототип добавлял счета, переводы, бюджеты, гипотезы и сценарии, но данных в нём нет.

В vNext финансов не было. Без решения пилотные данные некуда перенести, а у команды нет плана и факта по деньгам проекта рядом с задачами.

## Решение

1. **Журнал операций проекта, без счетов.** Операция — доход или расход; сумма — целое число минимальных единиц (`amount_minor`, 1…10¹⁵−1, поэтому любое значение точно в JavaScript) и ISO-код валюты. Валюта проекта (по умолчанию RUB) — только значение по умолчанию для новых операций; у операции может быть своя. Курсов и пересчёта нет: итоги считаются по каждой валюте отдельно.
2. **Три состояния.** `planned` — ожидается к `due_date`; `posted` — случилось `posted_date` (проведение запланированной операции ставит фактическую дату и сумму, плановая дата сохраняется); `voided` — аннулирована с причиной, окончательно. Переходы: planned → posted, planned → voided, posted → voided. Возврата в план нет, удаления нет: ошибка исправляется правкой или аннулированием. `entry_date` = фактическая дата, иначе плановая — по ней сортируется журнал и строятся разрезы по месяцам.
3. **История — в базе, триггером.** Каждое сохранённое состояние операции (INSERT или UPDATE `app.finance_entry`) пишет строку `app.finance_entry_version` с полным снимком, видом изменения (`created`, `updated`, `posted`, `voided`), автором (`updated_by`) и временем (`updated_at`). Второй триггер держит правила для любого пишущего, включая импорт на роли владельца: операция создаётся ревизией 1 в состоянии planned или posted, каждое изменение добавляет ровно одну ревизию, аннулирование меняет только состояние и причину, аннулированная операция не меняется, идентичность и создание неизменны. У runtime-роли нет UPDATE и DELETE на версиях и DELETE на операциях.
4. **Итоги считаются при чтении.** Сводка — агрегат SQL по журналу: проведённые доходы и расходы, баланс, запланированные доходы и расходы, прогноз (баланс + план), число операций по состояниям; разрезы по месяцам и категориям. Аннулированные операции в итоги не входят. Суммы в ответе — десятичная строка минимальных единиц: сумма многих операций может выйти за 2⁵³. Хранимых итогов нет, расходиться с журналом нечему.
5. **Права.** Читают финансы люди — участники проекта в любой роли (reader, editor, admin). Меняют — только администраторы проекта. Агентам финансы недоступны: возможностей `finance:read` и `finance:write` нет среди выдаваемых агенту, события `finance-*` агентам не отдаются. Администратор пространства без участия в проекте финансов не видит. Правило проверяется в сценарии (`ProjectAccess`, возможности `FINANCE_READ`/`FINANCE_WRITE`) и в базе: RLS через `auth.can_read_finance` и `auth.can_manage_finance`.

   *Уточнено 2026-09-30 ([доступ и приглашения](../access/access-and-invitations.md)):* роль заменена правами `finance.read` и `finance.write`. `finance.read` есть в пресетах Администратор, Редактор и Наблюдатель, нет у Гостя; `finance.write` — у Администратора, остальным добавляется лично. RLS: `auth.can_read_finance(p)` = `auth.can(p, 'finance.read')`, `auth.can_manage_finance(p)` = `auth.can(p, 'finance.write')`. Проектным агентам финансы по-прежнему недоступны; сервисным аккаунтам (часть II, PR #27) — только явной выдачей при том же праве у владельца.
6. **Команды по образцу продукта.** Запись — `PUT …/finance-entries/{id}` c `baseRevision` (0 — создание), смена состояния — `PATCH …/finance-entries/{id}/state` (проведение или аннулирование), валюта — `PUT …/finance-settings`. Все с `Idempotency-Key` в журнале повторов (квитанция хранит только id и ревизию операции), аудитом и outbox в транзакции изменения, под блокировкой проекта (`projectWriteFence`). Список — keyset-курсор по `entry_date DESC, id DESC`, привязанный к фильтру.
7. **Новые таблицы — в единственном числе** (`finance_entry`, `finance_entry_version`) по [правилам имён](../../../../engineering/conventions/naming.md#12-sql-и-миграции); документ настроек — `finance_settings`, как `task_settings`. Ограничения названы `pk_/fk_/ck_/ix_`.

## Альтернативы

| Вариант | Почему не выбран |
|---|---|
| Счета, переводы, бюджеты, сценарии из прототипа | Вне рамок задачи; реальных данных нет. Схема их не исключает: счёт станет новой таблицей и необязательной ссылкой из операции. |
| Версии пишет приложение (как `map_versions`) | Импорт по SQL и любой будущий писатель могли бы обойти историю. Триггер делает её полной при любом способе записи. |
| Хранить итоги проекта (как в пилоте) | Требует пересчёта при каждой правке и может разойтись с журналом; объём журнала мал (лимит 100 000 операций на проект). |
| Суммы как `numeric` с дробной частью | Минимальные единицы точны, не зависят от округления и совпадают с пилотом. |
| Изменение для редакторов проекта | Финансы чувствительны; в модели ролей есть администраторы проекта, они и ведут журнал. |
| Удаление ошибочных операций | Бухгалтерский журнал не теряет записи; аннулирование с причиной сохраняет след. |

## Последствия

- Импорт пилота идёт напрямую в таблицы (см. [docs/finance.md](../finance.md#импорт-пилотных-данных)): триггер сам создаёт версии при повторе ревизий через INSERT и UPDATE.
- Сводка — один проход по журналу проекта; при лимите 100 000 операций и индексе `(project_id, entry_date DESC, id DESC)` это миллисекунды. Разрезы ограничены последними 240 месяцами и 200 категориями в каждой валюте (`truncated`).
- Проверка: `tests/finance.test.ts` (FN01–FN09: CAS, повторы, переходы, права, RLS, события, сводка, конкурентность, OpenAPI), `FinanceLedgerIntegrationTest` (триггеры для роли владельца, RLS по ролям, откат), `FinanceRulesTest`.
- Откат: `server/src/main/resources/db/rollback/V20260929000025__add_project_finance.sql` удаляет таблицы, функции, события и квитанции финансов и строку журнала Flyway; интеграционный тест выполняет его в транзакции. Данные финансов при этом теряются — сначала резервная копия.

## Условия пересмотра

- Нужны счета, переводы или остатки на дату — добавить таблицу счетов и ссылку из операции.
- Нужны сводки в одной валюте — понадобятся курсы и их источник.
- Проект подходит к 100 000 операций или сводка дольше 200 мс — архивирование периодов или хранимые итоги по месяцам.
