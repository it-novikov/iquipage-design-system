# 0001. Перенос бэкенда Sprintique на Kotlin и Spring Boot

- **Статус:** accepted
- **Дата:** 2026-09-27
- **Владелец:** it-novikov
- **Основание:** [ADR 0001 инженерной системы](../../../../engineering/decisions/0001-engineering-system.md), карточка `.bridge/tasks/20260927-kotlin-backend`

## Контекст

Бэкенд написан на Node 24, Fastify, `pg` и zod: около 100 маршрутов, 20 миграций, RLS, три роли базы, журнал идемпотентности, CAS, аудит с outbox, OIDC, S3 и воркер заданий. Инженерная система закрепляет для бэкенда Kotlin/Spring. Продукт не выложен в production: миграции применялись только к локальным и тестовым базам.

## Решение

### Подход: перенос с проверкой паритета

1. Kotlin-приложение живёт в `server/` рядом с текущим бэкендом, пока не пройдёт паритет.
2. **Мерило паритета — все сценарии текущих тестов.** Инвентаризация и новое место каждого сценария — в [test-parity.md](../test-parity.md). Тесты по HTTP идут против запущенного Kotlin-сервера через фикстуру, которая не импортирует код бэкенда. Сценарии, которым нужно вмешаться внутрь процесса (отказ хранилища, гонка под блокировкой, отзыв прав во время ожидания, очередь заданий, прямые вызовы домена), переносятся в интеграционные и модульные тесты Kotlin с фейками портов. Ни один сценарий не удаляется молча.
3. После паритета скрипты, стенд и контейнер переключаются на Kotlin, `backend/` удаляется. Контракты `contracts/` остаются: их использует интерфейс.

### Внешние имена

Поведение HTTP API сохраняется один в один, и это важнее конвенции имён ([naming.md §21](../../../../engineering/conventions/naming.md#21-применение)). Не меняются:

- коды ошибок (`CONFLICT`, `VALIDATION` и другие);
- пути (в том числе `/api/v1/logout`, `/api/v1/invitations/accept`);
- заголовки и поля JSON;
- имена схем OpenAPI (`PutMap`, `StartAgentRun`, `EventHeadResponse` — задаются через `@Schema(name = …)`);
- имена таблиц и формат событий.

Конвенция действует внутри Kotlin-кода.

Меняются только имена, которые не входят в API и не имеют пользователей в production:

- переменные окружения — приводятся к префиксу `SPRINTIQUE_`;
- имена файлов миграций — переводятся в формат Flyway.

Оба изменения затрагивают только скрипты этого репозитория, и эти скрипты обновляются вместе с переключением.

### Структура

```text
server/src/main/kotlin/com/sprintique/
├── Application.kt                 Запуск: api (по умолчанию), worker, migrate
├── configuration/                 Типизированные свойства, проверки при старте
├── database/                      Пул, транзакции с RLS-контекстом, проверка ролей и схемы, разбор URL
├── command/                       Журнал идемпотентности, аудит и outbox
├── web/                           Ошибки, заголовки, лимиты, наблюдение, статика
├── identity/                      Учётные данные, CSRF, сессии, OIDC, dev-login, агенты
├── workspace/                     Пространства, проекты, профили, участники, приглашения, аватары
├── task/  catalog/  discussion/   Задачи, каталоги, связи, настройки; обсуждения
├── planning/                      Домен планирования, превью, коммиты, одобрения, представления
├── map/  media/  event/  agent/   Карты; файлы и изображения; события и SSE; запуски агентов
├── operation/  search/            Задания и их повтор; поиск
└── worker/                        Процесс очистки файлов
```

Внутри модуля — `api`, `application`, `domain`, `infrastructure` по [архитектуре](../../../../engineering/architecture.md). Граница проверяется архитектурным тестом.

### Данные

- **Схема не меняется.** Миграции 001–020 переводятся в Flyway без изменения SQL: `V20260927000001__create_foundation.sql` … `V20260927000020__create_person_avatars.sql`. Переименование допустимо, потому что production-базы нет. Это последний раз, когда миграции переименовываются.
- Права ролей, которые раньше выдавал `migrate.ts`, выдаёт `afterMigrate.sql` с плейсхолдерами `${runtime_role}` и `${worker_role}`. Так права восстанавливаются после каждой миграции, как и раньше.
- Миграции запускает отдельная команда `migrate` с учётными данными мигратора. API и воркер Flyway не запускают. При старте они проверяют, что история Flyway совпадает с миграциями в артефакте.
- **jOOQ.** Классы генерируются из настоящей схемы (изолированный кластер + Flyway) в `src/generated/jooq` и лежат в репозитории, так что сборка не требует базы. Тест сверяет сгенерированный код со схемой. Простые запросы пишутся на DSL. Сложные, выверенные запросы (страницы обсуждений, события, поиск, планирование) переносятся как SQL-шаблоны jOOQ с параметрами без изменения смысла и покрываются интеграционными тестами.
- **Транзакции явные.** `Database.transaction { }` и `Database.authenticated(credential) { }` поверх `DataSource`: `SET LOCAL statement_timeout = '10s'`, контекст `app.actor_id` и `app.project_limit` через `set_config(..., true)`. `@Transactional` не используется: границы транзакции видны в коде, как и раньше.
- **Откат.** Production-базы нет. Стенды и тесты создают базу с нуля, стенд пересевается при каждом запуске. Поэтому откат на TypeScript-бэкенд — это checkout прежнего коммита и новая база; перенос истории миграций не нужен. База, мигрированная Flyway, для TypeScript-бэкенда несовместима (его проверка ищет `public.schema_migrations`), и это ожидаемо. После первой production-выкладки откат делается только новой миграцией.
- **Адрес базы** — URL в формате libpq (`postgresql://user@host/db?host=/socket/dir`). Модуль `database` переводит его в свойства JDBC. Тестовый кластер слушает только Unix-сокет, поэтому драйвер получает сокет через junixsocket, а TCP-порт не открывается.

### Переменные окружения

По [конвенции](../../../../engineering/conventions/naming.md#13-конфигурация) все переменные получают префикс `SPRINTIQUE_`.

| Было | Стало |
|---|---|
| `DATABASE_URL`, `WORKER_DATABASE_URL`, `MIGRATION_DATABASE_URL` | `SPRINTIQUE_DATABASE_URL`, `SPRINTIQUE_WORKER_DATABASE_URL`, `SPRINTIQUE_MIGRATION_DATABASE_URL` |
| `DATABASE_RUNTIME_ROLE`, `DATABASE_WORKER_ROLE` | `SPRINTIQUE_DATABASE_RUNTIME_ROLE`, `SPRINTIQUE_DATABASE_WORKER_ROLE` |
| `PUBLIC_ORIGIN`, `HOST`, `PORT`, `TRUST_PROXY` | `SPRINTIQUE_PUBLIC_ORIGIN`, `SPRINTIQUE_HOST`, `SPRINTIQUE_PORT`, `SPRINTIQUE_TRUST_PROXY` |
| `OIDC_ISSUER`, `OIDC_CLIENT_ID`, `OIDC_CLIENT_SECRET` | `SPRINTIQUE_OIDC_ISSUER`, `SPRINTIQUE_OIDC_CLIENT_ID`, `SPRINTIQUE_OIDC_CLIENT_SECRET` |
| `S3_*` | `SPRINTIQUE_STORAGE_ENDPOINT`, `…_REGION`, `…_BUCKET`, `…_ACCESS_KEY_ID`, `…_SECRET_ACCESS_KEY` |
| `METRICS_TOKEN` | `SPRINTIQUE_METRICS_TOKEN` |
| `createApp({devLogin:true})` | `SPRINTIQUE_DEV_LOGIN=true` (отказ при `production` и не-loopback) |

### Безопасность и HTTP

- Spring Security без сессий сервлета и без его CSRF-хранилища. Собственный фильтр разбирает cookie `__Host-sprintique` или `Bearer spr_…`, а CSRF проверяется по токену учётных данных и `Origin`, как сейчас.
- OIDC code+PKCE — Nimbus OAuth 2.0 SDK за `IdentityProviderPort`. Состояние входа хранится в `auth.login_states`, как сейчас. Встроенный oauth2-client Spring не подходит: он хранит состояние в HTTP-сессии.
- Ошибки — `{code, message, requestId}` с теми же кодами и статусами. Тела запросов разбираются строго: неизвестное поле, неверный тип или пустое обязательное поле дают `400 VALIDATION`. Ограничения полей повторяют zod-контракты и видны в OpenAPI.
- Заголовки, лимиты запросов и загрузок, ограничение числа одновременных запросов, CSP для статики, `Cache-Control` — те же значения.
- OpenAPI 3.1 — springdoc, путь `/openapi.json` сохраняется, Swagger UI — `/api/docs`. Тест сверяет документ с зафиксированным.
- **Два описания контракта.** Zod-контракты остаются источником правды для интерфейса, Kotlin-классы запросов — для сервера. Контрактный тест сравнивает схемы запросов из `/openapi.json` с `z.toJSONSchema` тех же контрактов: обязательные поля, перечисления, длины, шаблоны, границы чисел. Расхождение — ошибка теста. `/api/v1/contracts` отдаёт JSON Schema запросов из OpenAPI сервера.
- **Dev-login вне production-артефакта.** Контроллер входа admin/admin и тестовые маршруты стенда (`/__preview/:role`) лежат в отдельном наборе исходников Gradle `local`. Их содержит только `sprintique-server-local.jar`, которым пользуются тесты и стенд. Production-артефакт `sprintique-server.jar` этих классов не содержит, и тест проверяет это по списку файлов jar. Сам контроллер тоже отказывается запускаться при `SPRINTIQUE_ENVIRONMENT=production` и на не-loopback адресе.
- **Поток событий (SSE).** До 100 одновременных потоков на процесс, как сейчас. Используется `SseEmitter` на виртуальных потоках JDK 25. Каждый тик берёт соединение из пула, читает outbox и возвращает соединение, между тиками соединение не удерживается.

### Файлы и изображения

- S3 — AWS SDK for Java 2, те же ключи объектов и ограничения размера.
- Изображения: ImageIO + TwelveMonkeys (JPEG с CMYK и EXIF) + webp-imageio (libwebp в комплекте, чтение и запись WebP). Перед декодированием читается размер без декодирования, ограничение пикселей и времени, не более двух одновременных декодирований, результат перекодируется в WebP без метаданных.
- Поведение sharp, которое повторяется:
  - поворот по EXIF (TwelveMonkeys читает ориентацию, поворот применяется до масштабирования);
  - отказ на повреждённых данных (`failOn: warning` — любое предупреждение reader'а считается ошибкой);
  - отказ на анимации (больше одного кадра);
  - ограничение пикселей до декодирования;
  - таймаут 10 секунд: декодирование в отдельном потоке, по истечении `ImageReader.abort()` и `422 IMAGE_DECODE`;
  - не больше двух одновременных декодирований (`429 IMAGE_BUSY`).
- Отличие от sharp: кадрирование аватара по центру вместо выбора «интересной» области (`attention`). Это видимое, но не контрактное отличие, и оно записано в заметки к выпуску.
- Декодирование — только чистый Java-reader TwelveMonkeys, выбранный явно. Нативная libwebp (`com.github.usefulness:webp-imageio` 0.11) только кодирует уже проверенные пиксели.

### Процессы и упаковка

Один артефакт, три команды: `api`, `worker`, `migrate`. Образ собирает Jib с базой Temurin 25 JRE, пользователь 1000, только чтение корня. `Dockerfile` удаляется после переключения.

## Альтернативы

| Вариант | Почему не выбран |
|---|---|
| Переписать с нуля с новой схемой | Потеря проверенной схемы, прав и RLS; нет мерила паритета |
| Весь SQL на DSL jOOQ | Высокий риск изменить смысл выверенных запросов; SQL-шаблоны + интеграционные тесты дают ту же уверенность дешевле |
| Spring Data JDBC / JPA | Противоречит стеку; JPA плохо сочетается с RLS-контекстом и явным SQL |
| libvips через FFM | Нужна системная библиотека в образе и на машинах разработчиков |
| Открыть TCP у тестового кластера | Ослабляет изоляцию тестовой базы (trust-аутентификация) |

## Последствия

- Интерфейс и данные не меняются. Меняются переменные окружения и команды запуска: README и operations.md обновляются вместе с переключением.
- Тесты продукта работают против запущенного сервера. Каждый файл тестов стартует JVM, поэтому прогон дольше.
- Сборка требует JDK 25.
- **Отступление от стека: интеграционные тесты без Testcontainers.** Базу даёт изолированный кластер `scripts/test.mjs`: только Unix-сокет, отдельные роли, guard от осиротевших кластеров. Его же используют API-тесты. Правило продукта «Docker только через явный контекст, VM по умолчанию не трогать» так соблюдается без исключений, а автоопределение Docker у Testcontainers невозможно. Генерация jOOQ тоже идёт через этот кластер (`scripts/test.mjs --jooq`).

## Условия пересмотра

Паритетный набор выявляет контрактное отличие, которое нельзя устранить без изменения API. Тогда нужен отдельный ADR и версия API.
