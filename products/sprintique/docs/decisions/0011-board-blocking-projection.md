# 0011: Блокировка карточки из полного снимка проекта

Статус: proposed. Scope разрешён постановкой SPR-24 и поручением владельца выполнить оставшиеся задачи релиза 1.0.

Карточки доски читаются постранично и фильтруются по релизу. Расчёт зависимостей по показанным карточкам пропустил бы блокирующую задачу из другого релиза или страницы.

PlanningQueries обогащает текущие read rows полями `effectiveBlocked`, `blockingTaskCount`, `blockers` (не более трёх id/displayId/title). Расчёт использует полный авторизованный PlanningState до фильтрации и paging. Направление `depends`: from ждёт to. Учитываются только действующие зависимости на задачи с result=open и status!=ready_for_release; у готовой/принятой задачи сигнал отсутствует. Related links не блокируют. Унаследованный releaseId уже предоставляет существующий planning resolver.

Чтение остаётся под project lock и TASKS_READ/RLS. Свойства не добавляются в сохранённые previews или историю: прошлые снимки не приобретают изменяемое состояние. Нет миграции и нового права; старый совместимый runtime остаётся пригодным для отката. UI не выводит предположение «свободна», если новое поле отсутствует. События task/task-link/planning заставляют перечитать актуальную проекцию.

Приёмка: реальный HTTP с блокером вне показанной страницы, количеством больше трёх, завершением, архивированием связи, направлением и tenant isolation; далее браузерное обновление сигнала.
