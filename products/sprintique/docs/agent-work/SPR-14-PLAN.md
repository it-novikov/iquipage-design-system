# SPR-14: работа людей и агентов в задаче

Revision 1, 2026-10-11. **Согласовано владельцем 2026-10-11, реализация начата.**

Основание: SPR-14 и связанная SPR-4 прочитаны из текущего Sprintique. Исследование: архитектура, продукт/надёжность, UI/UX (GPT 6 Astra). База репозитория и production — `931e09d`. DS — `0.6.0-vnext.38`, SHA256 `391f4fc499985a3ae3052ba8811fcd595fbeeee6d266244ac5244893c31b46c9`.

## Проблема и результат

Человек должен понимать, кто работает над задачей, что уже сделано, что требует ответа и как продолжить после сбоя. Агенту нужен сохраняемый план с критериями и передачей, а не восстановление всей истории сообщений. SPR-14 требует также реестр агентов, управление доступом и навыками, MCP и скиллы. SPR-4 связывает вопросы и подтверждённые решения с общей работой.

Предлагается единое рабочее место в задаче: поручение, вопросы, план, доказательства и журнал. Два режима исполнения остаются различимыми: во внешнем клиенте через MCP и внутри Sprintique через API модели. Сервисный аккаунт определяет личность и права; подключение определяет провайдера; профиль — поведение; запуск — конкретную работу. Навык не выдаёт разрешения.

## UI/UX — GPT 6 Astra

В задаче отдельная вкладка работы агента. На основной вкладке остаются только значимые сейчас быстрые действия и переход к работе. Агентская вкладка имеет ясную иерархию: текущий шаг, требующий ответа вопрос или результат для проверки; подробный план, условия, журнал и прежние запуски раскрываются по необходимости. Цель, состояние и контрольная точка не повторяют друг друга. Журнал показывает действия и результаты связным текстом, без скрытых рассуждений и секретов. Новые события не перетаскивают прокрутку и фокус.

«Поручить агенту» для API и «Передать поручение» внешнему клиенту имеют разные подтверждения: передача не означает начало выполнения. Перед запуском видны область данных, действия и лимит. Остановка показывает запрос до подтверждённого завершения и сохраняет уже выполненные эффекты.

Общая страница «Агенты»: поиск, фильтры проекта/режима/состояния; имя, роль, текущая задача и подтверждённая активность. Профиль: обзор, активность, доступ, навыки, подключения. Существующие настройки сохраняют маршруты. Недоступный агент показывает причину и допустимый следующий шаг. Роль назначения не смешивается с пресетом прав.

SPR-4: расширить существующий тред вопросом с контекстом, вариантами и последствиями, рекомендацией, своим ответом и подтверждённым решением. Не делать второй чат. «Вопрос решён», «план одобрен» и «изменения применены» — отдельные события. Референс: https://design.jarnee.ru/planning.html; массовое принятие рекомендаций не использовать для рискованных одобрений.

Использовать поставленные layouts, dialog, remote-combobox, markdown, обсуждения, аватары и feedback. Дополнить публичные контракты, если пилот подтвердит необходимость:

- DS-GAP-SPR14-01: controlled карточка решения с вариантами, readonly/pending/conflict/stale, сохранением и подтверждением.
- DS-GAP-SPR14-02: журнал активности со стабильными ID, деталями, пагинацией, новыми событиями и кратким live-announcement.

Пилот в двух темах и узкой панели → публичные типы/документация → версия → build/test/pack → точный архив продукта и lockfile. Комбобокс со свободной моделью сначала проверить на уже существующем `creatable`, не объявлять новый gap по старому комментарию.

## Архитектура, данные и ограничения

Добавить модуль `work`: план 1:1 к задаче со своей ревизией; шаги/критерии/доказательства; checkpoint; общая сессия участия с mode и ссылкой на существующий run; отдельное обращение человека с thread/message; аренда изменения плана с fencing token; версии навыков с digest. Это предлагаемая модель, окончательный контракт — в ADR до миграций.

Все REST/MCP/API-исполнители используют одни application commands. Сервер определяет actor/initiator и время. CAS, idempotency, RLS, audit/outbox остаются обязательными; эффект и событие атомарны. Чтение — `tasks.read`; предлагаемое `work.write` включается в существующий каталог после согласования. Управление рамками, риском, доступом и одобрение остаются человеку. Одобрение связано с ревизией/digest и не переживает изменение результата.

Аренда защищает общий план, а не запрещает параллельный анализ/обсуждение. Поздний старый держатель отклоняется. Timeout фиксируется ровно один раз командой API runtime или узкой SECURITY DEFINER queue-функцией, без мутации на GET. Нынешняя worker-role имеет cleanup-доступ и не получает доступ к tasks; расширение роли требует отдельного ADR. Эффективные права: аккаунт ∩ текущие права владельца ∩ права поручившего человека ∩ scope/проект запуска. Они проверяются на каждой команде; передача и навыки их не расширяют. Для внешнего процесса отзыв доступа запрещает запись в Sprintique, но не обещает остановить локальный процесс.

Повторное обращение во время активного API run нужно сохранять отдельно: нынешнее присоединение к run не гарантирует обработки второго message/thread. Тексты передачи имеют автора и трактуются как данные. Не добавлять произвольные shell/SQL инструменты или исполнение загруженного кода скиллов.

## Приёмка и выпуск

1. Два держателя аренды; повтор ключа с тем же/другим payload; crash после effect commit до ответа; устаревшие revision/fence.
2. Два обращения в разных тредах при активном run; сохранение исходного адресата и threadId; чтение входящих не равно обработке.
3. Отзыв прав во время tool call, отмена во время provider HTTP, собственное одобрение агента, malicious handoff, изменение digest после approval.
4. Reload/потеря связи/лимит/удалённое подключение/нет прав; сохранение черновика, истории и частичных результатов; отсутствие секретов в journal/export/errors.
5. Реальные Codex и Claude Code MCP OAuth, 401/403/expiry; внешняя передача не имитирует запуск; учёт API-расхода только по данным провайдера.
6. Две темы, телефон, длинные строки, клавиатура, reduced motion, отсутствие потери фокуса; браузерная приёмка финального DS-архива и продукта.
7. Полный `verify-vnext` с изолированными PostgreSQL/S3 и detached product; зелёный remote CI. Фактические результаты фиксируются отдельно в записи выпуска.

Миграции аддитивные, флаги для поэтапного включения. До выкладки backup и restore drill. Старый образ на расширенном строгом Flyway ledger не считать работоспособным откатом: нужен совместимый rollback image либо проверенное восстановление. После выкладки проверить реальный SHA/image, `/ready`, worker, ключевой сценарий; критерии прекращения и окно наблюдения фиксировать в release-карточке.

## Внешние источники и границы обещаний

Эксперт проверил первичные документы: [Codex authentication](https://learn.chatgpt.com/docs/auth), [Codex MCP](https://learn.chatgpt.com/docs/extend/mcp?surface=cli), [Claude Code MCP](https://code.claude.com/docs/en/mcp), [MCP authorization](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization).

Подписочный клиент подключается к Sprintique по MCP. API-ключ — отдельный серверный способ использования модели, не расход включённых кредитов подписки. Не передавать токены провайдера как credentials Sprintique. Реальная совместимость конкретных версий клиентов проверяется в P08; исследование не является production-приёмкой.

## Решение владельца

11 октября владелец отклонил первую композицию агентского раздела как перегруженную текстом. Требуется полностью пересобрать UI задачи с отдельной агентской вкладкой; основной экран содержит только важные быстрые действия. Это обязательная корректировка P06, её реализует GPT 6 Astra. Предварительная браузерная проверка старой композиции не считается приёмкой новой.

Владелец утвердил revision 1 и полный scope P01–P12 сообщением «В остальном ок, давай пробовать», с обязательными уточнениями: в агентском разделе только короткий человекочитаемый связный текст, без буллет-разбиения, шаблонных отчётов и признаков нейрослопа. UI без информационного шума; быстрый доступ содержит только действия, реально значимые для работы. UI реализует GPT 6 Astra. Разрешение push/deploy уже дано. Новое расширение согласованных рамок требует решения владельца. Реализация идёт по утверждённому плану. Codex подключён штатным OAuth; чтение SPR-14 и создание подзадач SPR-25–SPR-36 проверены через MCP от собственного сервисного аккаунта. Записи от имени человека не выполняются. Результаты окончательной приёмки и выкладки фиксируются в RELEASE.md.
