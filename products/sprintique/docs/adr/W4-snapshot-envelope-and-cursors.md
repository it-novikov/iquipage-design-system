# W4. Конверт одного снимка, курсоры, счётчики и лимиты

- **Статус:** accepted
- **Дата:** 2026-09-29
- **Основание:** delivery-plan §2.G, §4, §7, §12

## Решение

1. **`GET /api/v1/workbench?projects=…&limit=…`** — один SQL-запрос, значит один снимок: авторизованные проекты (членство актора, до 1000) → кандидаты причин (`UNION ALL`) → дедупликация по `(project_id, task_id)` с приоритетом `action > joined > active > waiting > updates` (решение владельца 2026-09-30, design-v2 §7) → секции и группы → счётчики и первые страницы (`row_number()` по секции). Дедупликация до пагинации: задача не бывает в двух секциях, счётчик равен числу строк списка.
   - Группы «Текущей работы» не пересекаются по определению: `joined` («Участвую») — открытая задача, в которой человек участвует, не исполняет и не поручал; `active` («В работе») — назначена ему в активной стадии, даже если он в ней участвует (автор); `waiting` («Жду») — участвует и последним назначил другому (W5).
   - Новость по задаче, у которой есть место в «Нужно действие» или «Текущей работе», остаётся в её строке (`updates.count`, `updates.latest` — «было → стало»). «Изменилось» — задачи с новостями без такого места: завершённые задачи, в которых человек участвует, своя задача в бэклоге, задача только со своим запросом.
   - Строка несёт `group: joined|active|waiting`, `personal {participating, rank, checkBackAt, …ревизии}`, `waiting {expectedAssignee, ownerNow, checkBackAt, done, expectedAssigneeLeft, assignedAt}`, `updates.latest {kind, detail{from,to}, actor, actorName, at, sequence}` и `statusEnteredAt`.
2. **Порядок** — канонический, на сервере, ключ `sort_key` (текст, сравнение `COLLATE "C"`):
   - action: `neededBy` (раньше — выше, просроченные первыми), возраст запроса, id;
   - joined: личный `rank`, id; active: стадия, приоритет, срок (без срока — в конце), id;
   - waiting: `checkBackAt` (без даты — в конце), последнее событие (новее — выше), id;
   - updates: последнее событие (новее — выше), id.
3. **Счётчики:** точные для action, групп текущей работы, отложенных и бэклога; updates — до 100, UI показывает «99+». Отложенные — задачи, у которых все открытые запросы к человеку отложены: задача с бодрствующим запросом стоит только в «Нужно действие».
4. **Страницы:** `GET /api/v1/workbench/list?section=…&cursor=…`. Курсор непрозрачный: `base64url(payload).base64url(HMAC-SHA256)`, payload — версия, актор, эпоха авторизации (хэш членств и ролей актора), секция, хэш фильтра, срок (15 минут), ключ позиции. Ключ HMAC — `SPRINTIQUE_WORKBENCH_CURSOR_SECRET` (32+ символов) или случайный на процесс (перезапуск делает курсоры устаревшими; несколько экземпляров API требуют общий секрет). Чужой актор, другой фильтр, подделка — `400 CURSOR_INVALID` одним текстом; истёк — `400 CURSOR_EXPIRED`; изменилось членство — `409 CURSOR_STALE`. Страница — keyset `sort_key > курсор`, без дублей и пропусков при неизменных данных.
5. **Приватность:** чужой проект не влияет на счётчики, текст ошибок и курсоры: фильтр `projects` пересекается с членством актора до всех вычислений, неизвестный id просто не даёт строк. Ответы `Cache-Control: no-store`. Имя пространства в строке — только при совпадении имён проектов в выдаче.
6. **Лимиты:** `limit` 1–50 (по умолчанию 10); проектов 1000 (сверх — `scope.truncated`); участий 2000 на человека, открытых запросов 500 на получателя по всем проектам (при записи, под блокировкой адресата, `422 …_LIMIT`); не более 100 непросмотренных событий на задачу; `statement_timeout` 5 с на запрос выдачи.
7. **Свежесть:** `snapshotToken` — хэш состава и порядка первых страниц и счётчиков. Клиент опрашивает конверт и при смене токена показывает «Появились изменения», не переставляя строки.
8. **Только человек:** агентский токен получает `403 HUMAN_REQUIRED`: у агента нет кросс-проектного права чтения.

## Последствия

- Запрос выдачи ограничен числом отношений одного человека, а не числом задач в системе; тест ёмкости проверяет план без N+1.
- Раздельные эндпоинты секций не нужны: невозможный экран (задача в двух секциях, счётчик ≠ строкам) исключён.
