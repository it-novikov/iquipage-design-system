# SPR-17 · Новая композиция документации

Revision 2, 11 октября 2026. Статус: предложение для независимого ревью. Реализация прежнего интерфейса остановлена по обратной связи владельца; его функциональные проверки не являются приёмкой дизайна. Новый runtime и DS пока не меняются. Root координирует команду и решение после ревью. Исследование R1: [WIKI-REDESIGN-RESEARCH.md](WIKI-REDESIGN-RESEARCH.md).

## Бриф

Документация нужна человеку, который пришёл разобраться в работе проекта, найти принятое решение или уточнить инструкцию. Текущий экран предъявляет каталог, административные кнопки и форму раньше самого документа. При правке документ теряет визуальную идентичность; история заменяет его длинным списком. Пользователь прямо отверг эту композицию. Это основание для пересборки, а не для дальнейшего изменения отдельных отступов.

Предлагается рабочее пространство документа: постоянная спокойная навигация, контекст страницы и широкая, но ограниченная по длине строки область текста. Чтение — основной режим. Поиск, правка, история и архив получают собственные понятные состояния с сохранением места и названия страницы. Пустой корень заменяется полезным обзором реального содержания. Человек с правом чтения видит тот же документ без обещаний недоступных действий. Сохранение всегда явное, без имитации совместного редактора и автоматической записи.

Сохраняются согласованные API, права TASKS_READ/WRITE, сервисные аккаунты, Markdown, поиск, древовидная структура, история, архив и связи с задачами. Не добавляются отдельные коллекции/права, AI-помощник, публикация, файлы, совместная правка, избранное или автосохранение. Типизированные ссылки из задачи подключаются после merge материалов в рамках этого же SPR-17; доступные обратные ссылки документа входят в этот дизайн.

## Источники и ограничения исследования

Это экспертный walkthrough текущего продукта и официальных публичных страниц, не интервью и не подтверждённая аналитикой частота сценариев. Текущий runtime проверялся в Chromium на synthetic4318: чтение, явное сохранение, конфликт двух вкладок, дерево, перенос, архив, история55 и поиск53. Скриншоты прежнего варианта остаются baseline, не целевым дизайном.

[Outline navigation](https://docs.getoutline.com/s/guide/doc/navigation-Nxnr2lWbck) показывает постоянную боковую навигацию и поиск с клавиатуры. При визуальном просмотре публичного документа его название и текст занимают главную область; навигационные строки компактны. Берём разделение навигации и чтения. Не переносим коллекционные права, звёзды и command menu целиком: их нет в принятом контракте.

[GitBook quickstart](https://gitbook.com/docs/getting-started/quickstart) описывает визуальную правку и добавление страниц из оглавления. [Обновление TOC](https://gitbook.com/docs/changelog/april-2025/30-april-auto-updating-api-reference-docs-design-improvements-editor-updates-and-more) связывает изменения с различением навигации и контента; официальный [mobile update](https://gitbook.com/docs/changelog) описывает боковую панель для оглавления. Берём спокойное дерево, breadcrumb и мобильное раскрытие. Не переносим ветки публикации, маркетинговую шапку, AI и библиотеку файлов.

[Notion sidebar](https://www.notion.com/help/navigate-with-the-sidebar) описывает вложенность страниц, раскрытие и поиск. Публичная help-страница визуально сохраняет название и путь документа, использует вторичное оглавление. Берём неизменную идентичность страницы и поиск по человеческой задаче. Не обещаем block editor, drag-and-drop, безграничную глубину или private draft — сервер имеет явные пределы.

Выводы выше — наши проектные решения по источникам, а не доказательство превосходства одного продукта. Подробные сценарии и дополнительные первичные источники Outline/Notion/Confluence собраны R1.

## Целевая композиция

Один существующий общий header проекта сохраняет workspace/project/profile и маршруты. Ни второй платформенной шапки, ни большого повторного H1 «Документация» над каждой страницей. Название раздела находится в боковой навигации; H1 принадлежит открытому документу. В корне H1 — «Документация проекта».

На desktop навигационная полоса приблизительно248px содержит название раздела, доступное создание страницы, поиск, дерево и нижний вход в архив. Геометрия берётся из документированного DS pattern после ревью, а не из private override. Дерево — плоская нейтральная поверхность, без округлой карточки вокруг всей иерархии, без папок на каждом родителе и счётчиков детей. Метка страницы открывает её; отдельный disclosure раскрывает детей. Выбранная страница заметна одним спокойным акцентом. Длинный каталог прокручивается в своей области. Для длинных названий — перенос максимум в две строки и доступное полное имя; при глубокой вложенности предельный отступ сохраняет полезную ширину.

Над документом остаётся одна компактная строка: breadcrumb слева, «Изменить» и меню страницы справа. В документе — название, вторичная строка автора/времени с входом в историю, затем текст. Текстовая мера около68–76ch; при1280×720 заголовок и начало первого смыслового блока видны без прокрутки. Ведущая кнопка не обязана быть самой контрастной вещью в режиме чтения; акцент сохранения появляется во время правки. Никаких карточек для каждого абзаца.

Корень показывает верхние страницы как простые строки и до5 недавно изменённых документов, вычисленных по updatedAt. Это не «вы недавно читали», не популярность и не придуманные описания. Подписи дочерних страниц можно собрать из реального каталога. Для пустого проекта — короткое предложение создать первую страницу; у reader — «В проекте пока нет страниц» без недоступной кнопки.

Поиск открывает отдельную основную область с одним полем, запросом и результатами. Поиск по названию/тексту остаётся серверным, по50 с курсором. Нет обещания поиска подстроки и морфологии. Путь берётся из каталога. Excerpt приводится к тексту без raw Markdown/HTML; выделение совпадения экранируется. Пустой запрос предлагает дерево/обзор, а не бессмысленный запрос ко всем страницам. При закрытии поиска восстанавливаются открытый документ, expandedIds и прокрутка дерева.

Правка сохраняет место названия и содержания. Публичный Markdown editor показывает реальные поддержанные инструменты; «Предпросмотр» не покидает draft. Статусы «Есть изменения», «Сохраняем…», «Сохранено» соответствуют реальному состоянию, а последний — только подтверждённой записи. Новая страница имеет явное название и тело, без готового текста, который человек вынужден стирать. Создание вложенной доступно из меню родителя; создание из раздела — в корень.

История — временный режим документа. Рекомендуемый вариант заменяет левую навигацию списком версий и «К страницам», сохраняя текст в основной области. Это предпочтительнее трёх постоянных колонок. Выбранная версия отмечена датой и автором; текущая названа текущей. Восстановление старой версии доступно после её просмотра и создаёт новую. Режим истории не показывает «Изменить» старую версию. Breadcrumb продолжает обозначать текущий документ; дата версии добавляет контекст, не заменяет идентичность.

На390px сохраняются общий мобильный header, строка документа с кнопкой «Страницы» и краткие действия. Навигация открывается отдельной панелью с фокусом и явным закрытием; открытие документа закрывает её и фокусирует H1. Текст имеет20px внешние поля. История сначала показывает компактный список, затем версию; нет горизонтального скролла всего приложения и трёх узких колонок. Сравнение конфликта переключает «Мой текст»/«Сохранённый текст» с сохранением собственного ввода; действие замены следует после явного ознакомления.

## Состояния и сохранность

Loading повторяет будущий документ/дерево и заканчивается при success/error/abort. Переходы между страницами не стирают сохранённую страницу до подтверждения запроса; skeleton принадлежит только меняющейся области. Ошибка чтения имеет локальный retry. Архив, отсутствие прав и404 различаются по реальному ответу, не по предположению.

Любой переход из dirty editor — страница, поиск, история, проект, section, browser back — предлагает сохранить, остаться или уйти без сохранения. После «Остаться» возвращаются фокус/caret, текст и route. Закрытие вкладки использует beforeunload. Серверные события не перерисовывают textarea и не обрывают IME.

409 сохраняет собственный текст, показывает актуальное title/body и отдельно обозначает архивное состояние. Человек может вернуться к правке, явно принять актуальную версию с подтверждением потери draft либо проверить её и сохранить свой текст. Новая ревизия только после явного решения; повторный конфликт снова требует проверки.403 оставляет текст доступным для копирования. Весь UI не обещает локальное постоянное хранение после закрытия вкладки.

Архивирование родителя с активными детьми блокируется с объяснением. Перенос исключает себя и потомков, соблюдает глубину12. Восстановление из архива требует выбора действующего родителя, если прежний архивирован. Version restore меняет title/body, сохраняет parentId. История и архив не содержат необратимого удаления.

## Прототип и сравнение вариантов

`output/design-review/index.html`, `concept.css`, `concept.js` — отдельный кликабельный концепт, публичные DS tokens/CSS/fonts. Предлагаемая tree/document geometry помечена как исследование, не существующий контракт DS. Внизу есть только review-переключатель состояний; его не будет в продукте. Данные синтетические, действия не вызывают API, связи/сохранение/восстановление демонстрируют переход, а не реальную запись. Точный общий platform header будет переиспользован из продукта; его прототип — схематичный контекст.

Альтернатива A — каталог-карточки как главный экран с отдельным документом. Упрощает пустой вход, но требует возвращаться в каталог при каждом переходе и ухудшает связанную работу с несколькими страницами. Альтернатива B (выбрана) — постоянная тихая навигация и документ; полезный overview только в корне. Для истории сравниваем временную замену дерева на версии и третий sidebar: выбираем замену, чтобы не сжимать документ на1280px. Мобильный overlay сохраняет контекст, но требует проверки focus trap/Escape/возврата — это обязательная цена выбора, не готовый факт.

## План реализации после ревью

1. Root + два независимых профиля проверяют сценарии, desktop/mobile концепт и DS gaps. Все P1/P2 замечания по плану отражаются revision2; без этого runtime не начинается.
2. Согласовать только необходимые public DS расширения. Проверить типы, семантику, keyboard, обе темы, font/CSS/core bytes в officialLinuxNode24.20. Выпустить следующую свободную exact версию.
3. Пересобрать wiki workspace/navigation/overview/read/search на существующих repository methods. Удалить rejected composition, сохранить contracts/rights/routes, abort и stale-read guards.
4. Встроить editor/CAS/history/archive/move/backlinks, собственный draft отделить от read state. Доделать task links после merge078 в этом же SPR-17: выбрать внутреннюю страницу в материалах задачи, открыть её, удалить/восстановить привязку и проверить обратную ссылку. Новое согласование уже разрешённого scope не требуется.
5. Meaningful UI tests состояния и lifecycle, build/boundaries; затем actual synthetic browser с сохранением→reload, чужой revision, permission denial, archive/restore, paginated search/history, keyboard/mobile/themes. Screenshot не заменяет scenario.
6. Freeze, два независимых review/root gate. Финальная отчётность отделяет дизайн-прототип, synthetic runtime и production. Root единолично ведёт merge/delivery.

## Уточнения root review к revision1

Task→wiki links остаются обязательной частью SPR-17 после интеграции078. Оглавление длинного документа получает минимальный public DS API и проверку, а не бессрочную отсрочку. Прототип правки теперь использует настоящий exact46 iq-markdown-editor (не имитацию), чтобы gap определялся фактической геометрией. Общая шапка продукта сохраняется; prototype header лишь контекст. Breadcrumb на desktop показывает родителей без повторения текущего H1, на mobile — ближайшего родителя с доступным раскрытием полного пути; длинный путь не вытесняет действия. Дерево1000 записей должно быть проверено на реальном catalog с глубоким и широким распределением: initial render, раскрытие, keyboard, выбор, refresh без потери фокуса. Числовой performance target до измерения не объявляется достигнутым.

## Исправления после технического и визуального ревью — revision2

P1 concurrent move закрыт в спецификации: conflict comparison показывает актуальное место; content draft rebase сохраняет latest parentId и archived. Обязательный regression: peer переносит страницу → save409 → owntext reviewed → save сохраняет новое место; второй409 сбрасывает review. Архивирование peer требует отдельного явно названного восстановления, а не implicit unarchive.

P2 geometry истории закрыт в концепте: версии заменяют дерево, body/rightedge не обрезаются при1280. На мобильном список версий открывается отдельной панелью, выбранная версия сохраняет основную область.

DS-GAP-WIKI-03 теперь определён фактическим exact46 editor: убрать из document variant визуальный двойной label, серую header/footer карточку и счётчик, сохранив доступные инструменты/preview. Очевидная подсказка «Название и текст сохранятся вместе» убрана из концепта. Текущий прототип намеренно показывает реальный компонент46: его шум — evidence для gap, а не утверждённый финальный вид. Минимальный новый вид нужно повторно проверить после publicDS реализации, без изменения private CSS.

Минимальный outline contract для ревью: viewer.headings — readonly Array<{id:string,level:number,text:string}> с уникальными стабильными в пределах value идентификаторами; viewer.focusHeading(id,{scroll:true}) возвращает boolean, переводит фокус без изменения location.hash; событие iq-outline-change сообщает новое оглавление после value. Навигация внутри документа не пишет #heading поверх #wiki/page/id. Дубли заголовков получают deterministic suffix; запрещены raw HTML/unsafe anchor injection. На мобильном оглавление — раскрываемый список в document context, desktop при достаточной ширине — тот же список без третьей постоянной колонки. Контракт окончательно утверждается DS review до кода.

В review toolbar прототипа «Редактор46» показывает настоящий publiccomponent; «Новая правка» — отдельный предлагаемый визуальный эскиз document variant без рамки/footer. Эскиз не выдаётся за готовый компонент: форматирующие элементы иллюстрируют расположение, не реализуют editing API. Окончательная toolbar сохраняет полный набор публично поддержанных команд, mobilewrap/overflow и доступные имена. Уменьшение шума не означает удаления функций.

## Минимальные публичные контракты для implementation review

WIKI-01: `iq-tree appearance="plain" density="compact" hide-counts` — additive presentation attributes, defaults сохраняют46. Events/items/value/expandedIds остаются прежними. `plain` снимает только внешнюю карточку/декоративные folder icons; disclosure остаётся отдельной доступной кнопкой, выбранность — `aria-selected`. Compact desktop36px row minimum, touch44px; отступ ограничен после глубины6, но aria-level и понятный parentpath показывают действительную глубину до12. Ellipsis не является единственным способом получить полное название. Exact names фиксируются declarations/docs и проверяются before consumer adoption.

WIKI-02: публичный CSS composition pattern `.iq-document-layout`, `.iq-document-rail`, `.iq-document-bar`, `.iq-document-content`, `.iq-document-title` на обычных semantic elements. Это геометрия/типографика, без repository/draft state. Рабочие слоты platform header не изменяются. Мобильная навигация использует существующий публичный dialog/drawer с focus trap/return; product не пишет собственную замену focus manager. Длинная редактируемая строка заголовка получает документированный autosize field pattern, не one-line input, теряющий текст. Pattern должен применять к title native textbox accessible name и не заменять значение при resize.

WIKI-03: `iq-markdown-editor variant="document"`, defaults прежние. Убирает только декоративный visible label/info footer/counter и лишнюю внешнюю карточку. Не скрывает caller footerActions, toolbarActions, hints/error/help, submit controls. Accessible name доходит до textarea и preview. Полный набор команд, disabled/readOnly, previewMode и focusEditor остаются. Переключение variant/resize не сбрасывает value, selection, undo или IME. Реальный46 показан в прототипе, proposed chrome — отдельный эскиз; после нового DS обязательна повторная визуальная сверка.

WIKI-04: logical heading IDs стабильны для одного value, DOM IDs имеют namespace отдельного viewer, чтобы current/history/conflict не дублировали DOMid. `focusHeading` ищет только внутри своего viewer; invalid id даёт false без scroll/focus. `headings` содержит levels1–6 и plain text, формируется тем же parse, без второй несовместимой обработки Markdown. `iq-outline-change` не переводит фокус сам. Проверить дубли заголовков,100000 знаков, updatevalue/late fetch и сохранение routehash.

Эти условия подтверждены R2 как обязательная граница до реализации. Review дизайна не является подтверждением, что код этих API уже существует.

## Закрываемые состояния R1

Прототип дополнен: новая пустая страница; reader без write actions; длинное название/пример12уровней; одинаковые названия с разным path в search; несохранённый preview; архивный detail с явным состоянием и подтверждением восстановления; conflict с тем же H1 и мобильными вкладками; history current label и отдельное закрытие панели версий без выхода из истории. Данные демонстрационные, перечисленные переходы не имитируют серверный результат. Независимое фактическое closure фиксирует R1, не автор прототипа.

## Обязательная поверхность task → wiki в этом выпуске

В task drawer существующая секция материалов «Документация» сохраняет компактную композицию SPR-16. Прикреплённая внутренняя страница показывает название и path/«Страница проекта», открывается одним действием. «Прикрепить страницу» открывает один диалог с поиском доступных активных страниц текущего проекта; совпадающие названия различаются путём. Уже прикреплённая запись отмечена и не создаётся второй раз. Выбор создаёт typed task→wiki link; внешние HTTP(S) материалы не меняют модель. Убрать связь можно отдельно от страницы, с обратимым «Вернуть»; CAS/ошибка оставляет список и выбор, не удаляет документ. Reader видит доступные ссылки и открывает их, без attach/remove/restore. Существующие accepted-result ограничения задачи сохраняются. Прототип «Из задачи» показывает выбор,2связанные строки, открытие и отдельное снятие связи; это не дополнительная функция сверх утверждённого SPR-17.

Прототип revision2 также показывает оглавление с переходом к3реальным заголовкам без смены hash; восстановление при архивном родителе с явным выбором нового места; conflict после чужого переноса с новым path; отдельный архивный конфликт с явно названным восстановлением. Reader-сценарий сохраняет роль при открытии истории/архива, поэтому write controls не возвращаются при навигации. Историческая панель имеет собственное закрытие без ухода с выбранной версии. Проверка этих состояний R1 ещё не заменяет будущие API/browser regressions.
