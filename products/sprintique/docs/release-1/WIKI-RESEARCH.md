# SPR-17: wiki проекта и материалы задачи

2026-10-11, `fix/release-1-feedback`. Исследование и предлагаемый план, не подтверждение реализации или согласования каждой детали. Прочитаны AGENTS, инженерные правила и `engineering:architecture`; runtime не изменялся. Постановки SPR-17 и SPR-16 взяты из фактического `/tmp/sprintique-rework-details.json`.

## Результат для человека

В проекте появляется «Документация»: дерево страниц, поиск и понятная кнопка создания. Страница — гайд, требования, решение или инструкция с названием, Markdown-текстом, автором изменения и историей. Человек открывает материал из задачи и возвращается обратно; одна страница может объяснять несколько задач. В SPR-16 «Дизайн» и «Документация» содержат несколько именованных материалов, а пустые разделы занимают одну короткую строку с действием «Добавить», раскрываются по запросу. Заполненные показывают количество и небольшой список с раскрытием остальных.

Основной выпуск: страницы, вложенность, редактирование с сохранением, история и восстановление, поиск, архив и восстановление из архива, связи страниц с задачами, внешние ссылки на документацию и дизайн. Совместное редактирование в реальном времени, публичные страницы и отдельные ACL каждой страницы усложняют модель и не следуют из постановок; их отсутствие нужно сообщить прямо. При сохранении документ видят имеющие доступ к проекту. Несохранённый черновик редактора не следует называть приватной опубликованной страницей.

## Что подтверждено

- В продукте уже есть модульный Kotlin/PostgreSQL backend, project authorization/RLS, revision CAS, ledger повторов, audit/outbox. Паттерны: `server/src/main/kotlin/com/sprintique/command/CommandLedger.kt`, `identity/application/ProjectAccess.kt`, `map/application/Maps.kt` (версии и CAS).
- Задача хранит Markdown-описание до 10000 символов; стабильный task ID отделён от читаемого номера. Контракт: `contracts/index.ts`. `TaskLinks.kt` описывает связи **задача→задача**, поэтому wiki-ссылки не должны маскироваться под `depends` или `related`.
- DS Markdown не исполняет HTML, не загружает изображения/плагины; web links проверяют протокол и запрещают credentials. Есть публичные редактор и viewer: `libraries/iquipage/src/modules/markdown.js`, `ui/src/board/description-view.js`. Проверять пригодность поддерживаемого подмножества для длинных инструкций отдельно от наличия редактора.
- Search сейчас ищет задачи, карты и проекты с project access, ограниченным ответом и курсором: `search/application/Search.kt`. Страницы wiki в этих выборках пока отсутствуют.
- Приватное media storage существует, но `Assets.linkTaskAssets` проверяет targetType/targetId и свежую загрузку того же actor. Файл задачи нельзя прикрепить к странице простым копированием ID: `media/application/Assets.kt`, `ObjectStoragePort.kt`, `contracts/media.ts`. Старое README содержит исторические версии/границы; текущие контракты и код надёжнее этого текста.

Пути Kotlin после первого полного пути выше относятся к `server/src/main/kotlin/com/sprintique/`.

## Что берём из Confluence

Для инструкций и требований Atlassian предлагает страницы с сохранением изменений и историей; восстановление не удаляет более поздние версии. Это поддерживает выбор версий вместо бесследной замены текста. [Страницы и история](https://support.atlassian.com/confluence-cloud/docs/create-edit-and-publish-a-page/).

Архив убирает материал из дерева и быстрого поиска, сохраняя возможность возврата; скрытие в дереве не означает запрет доступа. В Sprintique архив также должен оставлять рабочую ссылку из старой задачи и явно показывать состояние. [Архив](https://support.atlassian.com/confluence-cloud/docs/archive-pages/), [возврат](https://support.atlassian.com/confluence-cloud/docs/restore-archived-pages-to-the-page-tree/), [перемещение и скрытие](https://support.atlassian.com/confluence-cloud/docs/move-copy-and-hide-pages/).

Confluence различает общие права и ограничения документа, а Jira/Confluence показывают связанные задачи и страницы в обе стороны. Для первого выпуска Sprintique предлагается общий проектный доступ и явная обратная связь, без копирования всей системы ограничений Confluence. [Доступ](https://support.atlassian.com/confluence-cloud/docs/add-or-remove-page-restrictions/), [связь с задачами](https://support.atlassian.com/confluence-cloud/docs/use-jira-and-confluence-together/). Поиск и загрузка файлов — отдельные возможности, а не свойства Markdown. [Поиск](https://support.atlassian.com/confluence-cloud/docs/search-for-pages-and-posts/), [файлы](https://support.atlassian.com/confluence-cloud/docs/manage-uploaded-files/).

## Минимальные данные и команды

| Сущность | Поля и смысл |
|---|---|
| wiki_page | projectId, стабильный id, parentId, title, Markdown, revision, archivedAt, createdBy/updatedBy и время. Уникальность title не обязательна: адрес использует id. |
| wiki_page_version | projectId/pageId/revision, неизменяемый полный снимок текста и метаданных, author/initiator, время и краткая причина. Восстановление создаёт новую текущую версию. |
| task_resource | projectId/taskId/id, category=design/documentation, label, target=external URL или wikiPageId, revision, порядок, archivedAt. Ровно один тип цели; wiki FK внутри проекта. |

Рекомендуемые typed API: list/read/create/update pages; versions/read-version/restore-version; archive/restore; task resources list/upsert/archive. PUT/PATCH всегда baseRevision + Idempotency-Key; GET не меняет данные. Backlinks вычисляются по активным task_resource, без дополнительной несогласованной копии. Ссылка ведёт на текущую страницу; неизменяемый вариант при необходимости — явный version URL, а не скрытое прикрепление старого текста.

Одновременные изменения дают 409 с сохранённым черновиком; человек перечитывает чужой вариант перед повтором. Restore тоже CAS текущей страницы, чтобы не затереть новое изменение. Потеря ответа + чужая следующая правка + retry возвращает исходный appliedRevision, **не** текущий revision, иначе клиент ошибочно примет чужую правку за основание своего текста. Версия, current page, audit, outbox и receipt фиксируются атомарно. Простой project lock перед page/resource lock согласует parent changes, archive и version restore; запрет циклов и cross-project parents обязателен.

## Права, безопасность и пределы

Предлагаемое допущение первого выпуска: wiki разделяет существующие TASKS_READ/TASKS_WRITE проекта; изменение привязок задачи требует TASKS_WRITE. Это включает существующих редакторов/сервисных аккаунтов с таким правом и должно быть явно принято в продуктовой политике. Сервисный actor действует в пределах текущих прав владельца/инициатора; авторство не заменяется именем человека. История, поиск, экспорт, backlinks и archived URL проверяют то же право чтения. Отсутствующая/чужая страница даёт нейтральный 404 без названия и выдержки.

Если нужен отдельный доступ к базе знаний, добавить wiki.read/wiki.write **до реализации**, согласовав defaults и DTO/catalog/схемы. Это увеличивает каталог прав, требует проверки изменённых пресетов и совместимого rollback; нельзя автоматом дать новое право пользовательскому ограниченному пресету только по его системному key. Страничные исключения и публичные URL не включены в это предложение.

Внешние материалы — только нормализованные HTTP(S) URL без credentials/control chars, нейтральные подписи, `noopener noreferrer`. Сервер не скачивает страницу ради preview; нет SSRF, iframe чужого сайта или выполнения HTML. Wiki-текст для агента остаётся недоверенными данными. MCP расширять только именованными ограниченными tools после явного включения возможности; OAuth audience не переносить в REST.

Предлагаемые технические лимиты, не измеренные потребности: title 200, Markdown 100000 символов, 1000 страниц проекта, глубина 12, 50 материалов задачи, list/search 50 за страницу, query 200. Контроль входов до expensive parse/записи; одинаковые ограничения в DTO, TS и БД. История постраничная, без молчаливого удаления версий. Рост истории остаётся риском хранения — retention нельзя придумывать без решения владельца.

Первые файлы можно оставить в существующих вложениях задач и связывать с wiki текстом/ссылкой. Если в выпуск входят собственные вложения страниц, это отдельная обязательная часть media: targetType=wiki, read/write authorization, quota, signature check, safe download, orphan cleanup. Версии должны удерживать свои asset references; удалённое из текущей страницы изображение нельзя собрать GC, пока на него ссылается доступная историческая версия. Публичный Markdown renderer не обещает встроенные картинки: нужна отдельная безопасная поддержка asset reference в DS.

## План реализации и приёмка

1. Зафиксировать ADR: права, видимость сохранённой страницы, состояние архива, parent/archive policy, media scope и лимиты; согласовать продуктовую навигацию «Документация проекта ↔ материалы задачи». Не называть предположения уже утверждёнными.
2. Новая additive миграция, FORCE RLS/не-owner runtime, immutable versions; typed contracts и приложение команд с CAS/ledger/audit/outbox. Реальные тесты cross-project, revoked owner/initiator, parallel update, lost response retry и restore.
3. API и UI: дерево/страница/редактор/история/архив. Поиск title+body в PostgreSQL с индексом, только авторизованные активные страницы; отдельный явный режим архива. Проверить кириллицу, пустую выдачу и курсор другого запроса. Сначала project search, затем global union при сохранении проверки прав и типа результата.
4. SPR-16: несколько дизайнов/документов, поиск wiki страницы и внешняя ссылка, удаление связи не удаляет страницу; архивный материал узнаваем. Проверить пустой/заполненный/ошибочный/read-only состояния, возврат из wiki, keyboard и мобильный экран. Изменённые публичные DS компоненты выпускать exact versioned tarball.
5. Gate: fresh+existing DB migration, immutable history, ограничения дерева, XSS/protocol payloads, API rights, standalone extraction, реальные браузерные сценарии и backup restore. Подтверждение реализации — результаты этих проверок, не сам план.

Новая миграция делает старый strict Flyway image несовместимым даже при скрытом разделе. Feature-off — функциональное выключение на новом image, не полный откат БД. До выпуска нужен отдельный старый runtime с точным новым migration ledger/правами либо восстановление БД из проверенной резервной копии; latter теряет новые записи после backup. Не делать destructive down с потерей wiki/history/resources. Предпочтение project-wiki внутри существующего монолита даёт общие права и навигацию; внешний Confluence добавляет отдельные аккаунты/доступ/интеграцию, а хранение документов в описании каждой задачи дублирует знания и не решает проектный поиск/историю.
