# Сценарии опыта: цели, входы, fixtures

Основа и среды — в [README](README.md). Все записи ниже — **планируемые сценарии, NOT_RUN в этом индексе**. Выполнение хранить в отдельной карточке/assessment с build и evidence; не делать весь список PASS после открытия home. Пути начинаются от origin выбранного local preview; `project-id`, `task-id`, `entry-id` брать из его данных, не подставлять production IDs.

## Первый диагностический срез при подтверждении его приоритета

`SQ-PLANNING → SQ-TASK → SQ-BOARD → возврат` — сильный кандидат, если текущий разбор подтверждает соответствующий барьер. Проверить новую работу, active/planned/без релиза, фильтр, раскрытие детей, selection, draft, scroll и focus. Общее Task поведение дополнительно проверить через Workbench; redesign всех источников входа для этого не требуется.

Не фиксировать заранее отдельную Prepare-кнопку, mode/checkbox layout или смену renderer. Сохранить права, целостность, scope и историю; сравнить варианты достижения человеческого результата. Для backlog одного изменения preparation может быть недостаточно из-за admission; для planned доски не обещать «появится только после старта». Фильтр не обходить незаметным сбросом; показать, почему задача скрыта, и дать понятный обратимый путь найти её.

## Пробелы fixtures добавлять по конкретному риску

| Пробел | Минимальное дополнение и граница |
|---|---|
| Source-seed заранее подготовил задачу | Новый local сценарий с UI create и проверкой Board projection через настоящий server; никаких скрытых Prepare «для успешного теста». |
| `map-main` не связан с задачей Sprintique | Только локально подготовить synthetic объект с `externalTaskId` существующей задачи того же проекта. Проверить, что entry «Открыть задачу» доступен, затем Maps → Task → close/return; `type: task` без этой связи недостаточно. Такой fixture пока не реализован, путь NOT_RUN; отсутствие кнопки у локального объекта само по себе не UI-дефект. |
| Раздельные capabilities | Две synthetic роли с нужными сочетаниями; проверить разрешённые действия, причины отказа и потерю доступа. Не подменять grants одним флагом `canEdit`. |
| Unknown outcome / stale / поздний ответ | Управляемый сценарный transport/local test; сохранить original operation identity. Mock показывает UI состояния; exact-key replay/persistence доказывается server тестом. |
| Неясная эстетика/плотность | Детерминированные длинные тексты, несколько дат/owners, empty+filled, narrow и темы; screenshot смотреть, а не только сохранять. |
| Медленный путь | Реальный data profile, конкретный route-ready/Task/return сценарий, согласованная лаборатория и измерение. Не подменять latency числом DOM строк или gzip DS. |

Не строить отдельный универсальный стенд ради полноты каталога. Если live UI доступен и безопасно отвечает на вопрос, использовать его. Если нужен isolated frontend render, первый практичный entry — `ui/planning/src/index.js::mountPlanning` с exact `ContainersView` из `contracts/planning-view.ts`; подключать остальные families по фактической необходимости. Скриптов standalone frontend fixture в текущем package.json нет.
