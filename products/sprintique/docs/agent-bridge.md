# Мост в Sprintique: план работы агента внутри задачи

Статус: **проект решения**, исправлен по ревью R2 инженерной системы. Реализация — после переноса бэкенда на Kotlin (карточка `.bridge/tasks/20260927-sprintique-agent-work`).

## Идея

Задача Sprintique становится местом, где агенты и люди ведут работу по формату [моста](../../../engineering/bridge/README.md). У задачи появляется **план работы**:

- цель и рамки;
- критерии приёмки;
- шаги с критериями;
- раздел «Передача»;
- решения;
- аренда.

Любой участник продолжает с того места, где остановился предыдущий: другой агент после сбоя провайдера, человек или агент из репозитория разработчика.

Что это даёт продукту:

- **Работа агента видна и проверяема.** Человек видит план, текущий шаг, доказательство по каждому готовому шагу и то, что агент узнал по дороге.
- **Агенты взаимозаменяемы.** Сбой провайдера не теряет работу: задачу можно передать следующему агенту цепочки проекта.
- **Один формат с разработкой.** Карточка из репозитория загружается в задачу и выгружается обратно. Поля, которые не переносятся, перечислены ниже явно.

## Соответствие понятий

| Мост | Sprintique | Решение |
|---|---|---|
| Карточка | Задача (`app.tasks`) | План работы — отдельный агрегат 1:1 к задаче со своей ревизией |
| `title` | Название задачи, 1–240 символов | Берётся из задачи. Схема моста тоже ограничена 240 символами |
| `owner` | Исполнитель-человек (принципал) | При выгрузке — имя, при загрузке — участник по имени или пусто с предупреждением |
| `status` карточки | Статус на доске | Разные вещи. У плана свой статус: `draft … done` |
| `risk` | — | Поле плана. `high` требует одобрения завершённых шагов человеком. Понизить уровень может только человек с ролью editor или выше |
| Цель, Рамки, Приёмка | Описание задачи | Отдельные поля плана. Цель по умолчанию предлагается из описания |
| Шаги с критериями | Подзадачи, чек-листы | Шаги плана. Шаг можно превратить в подзадачу |
| Передача | — | Снимок в плане, обновляется контрольными точками |
| Решения | — | Список в плане |
| Вопросы | Обсуждения, вид «вопрос» | Хранятся в плане (id, адресат, ответ). У вопроса может быть связанный тред-вопрос задачи для обсуждения |
| Журнал | Аудит и outbox | События `task.work.*` в общем потоке проекта |
| Аренда | — | `holder_id` (принципал) + `lease_expires_at` в плане |
| Сессия агента | Запуск агента (`app.agent_runs`) | Запуск получает `task_id` |
| Эстафета | — | Новое поле `relayed_from_run_id`. `parent_run_id` сохраняет свой смысл: повтор тем же агентом |
| `branch`, `base`, `links`, `context` | — | Поля плана, хранятся как есть |

**Не переносятся** при выгрузке и загрузке:

- `created` — его задаёт платформа;
- имена людей, которых нет среди участников проекта (при загрузке остаются пустыми, с предупреждением в ответе);
- неизвестные разделы (`extraSections`) — хранятся в плане как текст и выгружаются обратно без изменений.

## Данные

Новые таблицы называются в единственном числе, как требует [конвенция](../../../engineering/conventions/naming.md#12-sql-и-миграции).

```text
app.task_work_plan      project_id, task_id (PK), revision, status, risk, goal, scope_included, scope_excluded,
                        scope_constraints, handoff jsonb, holder_id, lease_expires_at, branch, base, links text[],
                        context text[], extra_sections jsonb, updated_at
app.task_work_criterion project_id, task_id, criterion_no (PK), text, done
app.task_work_step      project_id, task_id, step_no (PK), revision, title, status, what, how, why, result,
                        covers int[], depends_on int[], model, criteria jsonb [{text, done}], subtask_id NULL
app.task_work_decision  project_id, task_id, decision_no (PK), text, decided_by, decided_at
app.task_work_question  project_id, task_id, question_no (PK), text, addressee_id NULL, answer, answered_by,
                        thread_id NULL
```

- RLS как у остальных таблиц проекта: `auth.can_project(project_id)`.
- Каждое изменение — команда с ревизией плана (CAS), идемпотентностью, аудитом и outbox в одной транзакции.
- Лимиты — из [JSON Schema моста](../../../engineering/bridge/schema/task.v1.schema.json).
- Текст плана проверяется на похожее на секреты при записи. Совпадение даёт `422 SECRET_LIKE_CONTENT`.
- У каждого текстового поля плана хранится **автор записи**: принципал и вид — человек или агент.

## Права

| Действие | Человек reader | Человек editor | Человек admin | Агент |
|---|---|---|---|---|
| Читать план и сводку | да | да | да | `tasks:read` |
| Взять и отпустить аренду | — | да | да | `work:write` |
| Контрольная точка, шаги, решения, вопросы | — | держатель аренды | держатель аренды | `work:write` и держатель аренды |
| Ответить на вопрос | — | да | да | — |
| Создать план, загрузить карточку | — | да | да | `work:write`, только в статусе `draft` |
| Изменить `risk`, цель, рамки, приёмку | — | да | да | — (предлагает через вопрос) |
| Одобрить готовый шаг при `risk: high` | — | да, не автор шага | да, не автор шага | — |
| Настроить цепочку агентов проекта | — | — | да | — |

Право `work:read` не вводится: чтение плана — часть `tasks:read`.

## Передача между агентами и безопасность

Сводка плана становится указаниями для следующего агента. Поэтому агент с узкими правами мог бы написать в «Передачу» то, что выполнит агент с широкими правами. Защита:

1. **Автор каждого поля виден.** В сводке текст, записанный агентом, помечен как текст агента и оформлен как данные («агент X записал: …»), а не как указание платформы.
2. **Указания от агента к агенту требуют человека.** Цель, рамки, приёмка и новые шаги, созданные агентом, становятся частью сводки для другого агента только после одобрения человеком. До этого они видны как предложение.
3. **Цепочка не расширяет права.** Задачу можно передать только агенту, у которого права в проекте не шире, чем у инициатора плана, либо с явного одобрения администратора.
4. **Проверка прав остаётся.** Любое действие агента проверяется его разрешениями и правами того, кто его выпустил, независимо от текста плана.

## API

Пути — существительные, как требует конвенция.

| Метод и путь | Назначение | Права |
|---|---|---|
| `GET …/tasks/{id}/work-plan` | План в модели `bridge/1` (JSON) | чтение задачи |
| `GET …/tasks/{id}/work-plan/brief` | Сжатая сводка (Markdown, до 7000 символов) с пометками авторов | чтение задачи |
| `GET …/tasks/{id}/work-plan/card` | Карточка в формате `task.md` | чтение задачи |
| `PUT …/tasks/{id}/work-plan` | Создать план или заменить его, пока он в `draft`. Не меняет статусы шагов, отметки критериев и аренду | editor, агент с `work:write` |
| `PUT …/work-plan/lease` / `DELETE …/work-plan/lease` | Взять или отпустить аренду | см. права |
| `POST …/work-plan/checkpoints` | Обновить «Передачу», продлить аренду | держатель аренды |
| `PATCH …/work-plan/steps/{n}` | Статус шага, отметки, итог | держатель аренды |
| `POST …/work-plan/decisions`, `POST …/work-plan/questions`, `PATCH …/work-plan/questions/{n}` | Решения, вопросы, ответы | см. права |
| `POST …/work-plan/handoffs` | Передача с причиной; для агента завершает текущий запуск | держатель аренды |
| `GET /api/v1/agents/me/work` | Задачи, ожидающие этого агента: передача ему или свободная задача его цепочки | агент |

- Готовый шаг при `risk: high` создаёт одобрение с ключом `step:<task>:<n>:<revision шага>`. После отклонения шаг можно отправить снова с новой ревизией, и уникальный ключ одобрений не мешает.
- Истечение аренды — неявная передача с причиной `timeout`, её фиксирует тот, кто первым прочитает план после срока.

## Эстафета на платформе

1. В настройках проекта («Агенты») администратор задаёт **цепочку агентов**: список выданных агентам разрешений в порядке предпочтения, с классом модели `strong` или `fast`.
2. Запуск агента по задаче: `POST …/agent-runs {taskId, goal}`. Агент получает `agent-context` со сводкой плана.
3. Агенты внешние, и платформа не может их запустить. Агент, упёршийся в лимит, сам `finish` не вызовет. Поэтому передача срабатывает двумя путями:
   - запуск завершён с причиной `limit`, `auth`, `error` или `timeout`;
   - истекла аренда.
4. Следующий агент цепочки узнаёт о задаче двумя способами:
   - опросом `GET /api/v1/agents/me/work` — внешний агент или его обвязка вызывает его по расписанию;
   - событием `task.work.handoff` в SSE проекта.

   Уведомления по почте или webhook не настроены и в этот объём не входят.
5. Агент в репозитории работает с тем же планом через CLI моста (`bridge pull/push`, отдельный шаг).

Платформа не исполняет код агента и не хранит ключи провайдеров моделей. Предложение, одобрение и применение результата остаются разными состояниями.

## Интерфейс

В боковом меню задачи появляется раздел **«План работы»** между описанием и связями:

- сверху — «Передача»: состояние, следующий шаг, кто держит задачу и до какого времени. Ловушки свёрнуты в одну строку. Текст агента помечен;
- шаги — компактный список с прогрессом критериев. Раскрытый шаг показывает что, как, зачем, критерии и итог со ссылками на доказательства;
- критерии приёмки задачи с отметками;
- решения — свёрнутый список с датой;
- предложения агентов, ждущие одобрения, — отдельной группой;
- действия: «Передать агенту…», «Забрать себе», «Выгрузить карточку», «Загрузить карточку».

Интерфейс строится на компонентах IQUIPAGE. Если понадобится новый паттерн, например список шагов с критериями, он оформляется как DS-GAP.

## Этапы

1. **Модель и API** на Kotlin-бэкенде: таблицы, команды, права, JSON и Markdown, тесты по обязательному списку.
2. **Интерфейс** плана в задаче.
3. **Эстафета**: цепочка агентов проекта, `taskId` и `relayed_from_run_id` у запусков, `agents/me/work`, передача по причине завершения и по истечению аренды.
4. **Синхронизация с репозиторием**: `bridge pull/push`.
