# Один процесс, четыре разных ответственности

## 1. Определить проблему
`iquipage-discovery` читает доступный контекст, задаёт короткие серии вопросов и отделяет факты от предположений. Результат — proposed brief и requirements. Владелец утверждает конкретную revision и scope. Скилл сам не может выдать себе approval.

## 2. Спроектировать опыт
`iquipage-experience-audit` нужен при неясном текущем пути, существенной смене UI или жалобах на удобство. Он сохраняет функции, показывает barriers и целевые композиции, проверяет человеческие и агентные сценарии, mapping DS. Не запускается как обязательное повторение уже принятого аудита без причины.

## 3. Пересобрать UI
`iquipage-implement` фиксирует provenance и parity, применяет общий каркас и публичные компоненты, доходит до всех согласованных поверхностей. Все несуществующие capabilities попадают в DS-GAP до кодирования обходов. Первое вертикальное решение проверяется до тиражирования.

## 4. Проверить и исправить
`iquipage-review` проверяет и код, и рендер, и реальную работу. Findings → implementation fixes → recheck на новом build fingerprint. Рецензент не считает свой уверенный текст доказательством. Если доступны субагенты, независимый reviewer полезен; если нет — явно self-review, не выдуманная команда.

## Договор между скиллами
Артефакты хранить в согласованном каталоге работы, например `.iquipage/runs/<run-id>/` (новый путь, не затирать предыдущий run):

```text
context.json                    # проект, DS, инструменты, source/build fingerprints
problem-brief.md                 # proposed/approved, revision, decision reference
requirements-register.md
surface-inventory.csv
capability-map.csv
gap-register/DS-GAP-*.md
adaptations/ADAPT-*.md
experience-report.md
migration-plan.md
assessment.json
findings-report.md
fix-ledger.csv
evidence/                       # raw logs, traces, screenshots, API observations
implementation-handoff.md
```

Перед переходом проверять актуальность: новый DS hash, source commit, revised scope или изменившаяся модель инвалидируют затронутые решения/доказательства. Не перезаписывать старую evidence новым названием версии.

## Гейты
G0 — доступны источники и полномочия.
G1 — однозначная проблема/scope; если меняется решение, есть approval.
G2 — capability map и functional parity; все gaps видимы, альтернативы согласованы.
G3 — одна цельная композиция утверждена, нет vendor bypass.
G4 — реальные операции/состояния по нужным surfaces и ролям.
G5 — visual/code/UX/a11y/human-agent/performance review; required targets проверены.
G6 — исправления подтверждены новой evidence, handoff полон.
Production cutover/deploy — только отдельное разрешение пользователя и техническая готовность проекта.

Нет усреднённого балла, который компенсирует утечку данных или отсутствующий экран. Нельзя считать scope завершённым, если он был незаметно сокращён. Если безопасная часть выполнена, так и написать; blocked часть остаётся в реестре.

## Границы полномочий скиллов
Код исходного продукта может меняться только внутри одобренной задачи. Аудит разрешает сбор отчётов, не самостоятельный redesign. Ни один скилл не получает разрешение отправлять клиентские данные внешнему сервису, выполнять платежи, публиковать, удалять рабочие данные или пушить ветку от самого факта установки.
