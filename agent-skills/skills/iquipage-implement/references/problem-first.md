# От проблемы к проверенному решению

Используй этот разбор, когда причина неудобства или выбор решения ещё не ясны. Веди одну обновляемую карточку: issue, brief или finding с нужными полями. Не создавай отдельные JTBD, CJM и PRD ради названий методов. Уже данная авторизация сохраняется.

## Соразмерная глубина

| Работа | Достаточное содержание |
|---|---|
| Подтверждённый ограниченный дефект | Эпизод/цепочка воспроизведения, человеческий результат, причина, минимальная правка, затронутые гарантии и прямая проверка. Не ждать интервью и не сочинять три альтернативы. |
| Спорное поведение или новая функция | Конкурирующие причины, гарантии отдельно от изменяемых решений, осмысленные варианты, рискованное допущение, проверка и решение. |
| Глубокий аудит продукта | Реестр всех согласованных семейств и значимый walkthrough каждого; явно непросмотренное. Полный реестр не задерживает исправление уже подтверждённого критического пути. |

## 1. Эпизод и человеческий результат

Запиши: «Когда [контекст], [роль] хочет [результат], чтобы [польза]; сейчас мешает [барьер]; последствия/обход [известное], неизвестно [существенное]». Потребность формулируй без кнопки, вкладки, компонента или технологии. Человек может хотеть найти работу команды, а не управлять отдельным внутренним флагом. Достаточным исходом может быть получение информации или обоснованное отсутствие действия; новый CTA не обязателен. Проследи нужное продолжение работы и возврат через реально затронутые разделы/роли: успешный промежуточный клик не закрывает сквозную цель. Для локального copy-дефекта не расширяй путь без причинной связи.

Разделяй свидетельства: рассказ человека; наблюдение его работы; действие исследователя в работающем UI; screenshot; исходники; synthetic fixture. Укажи источник, revision/среду и границу вывода. Код подтверждает правило или достижимый разрыв; он не доказывает эстетический ущерб, частоту и спрос. Walkthrough агента не является наблюдением реального пользователя. Seed, mock callback и наличие компонента в каталоге не доказывают сохранение или успешное выполнение сценария.

Сначала запиши текущее наблюдение, затем сравни его с прежним планом. Если уже знаком с планом, не изображай свежий независимый взгляд. Пустая неделя, нулевая сводка или много свойств сами по себе не дефект: покажи противоречие нужному результату. Если production revision неизвестна, не связывай кадр с локальной строкой как доказанной причиной.

## 2. Причина и изменяемые предпосылки

Проследи действие → intent/state → данные/правило → projection → видимый результат настолько глубоко, насколько это меняет диагноз. Причина может находиться в навигации, содержании, данных, домене, процессе, DS или интеграции. Для спорной причины назови правдоподобное другое объяснение и наблюдение, которое различает их. Не останавливаться на CSS-симптоме; не обследовать весь backend без связи с проблемой.

Отдели необходимые гарантии с источником (сохранность, права, область эффекта, история, возможность выполнить нужную работу) от изменяемых решений (default, отдельный шаг, термин, группировка, renderer). Существование решения в коде не делает его обязательным. Упрощение домена требует разбора затронутых состояний, callers и истории; его нельзя незаметно назвать визуальной правкой.

## 3. Варианты и критерий до прототипа

Оставь нынешнее поведение как baseline для сравнения, не как заведомо приемлемое решение. Рассмотри исправление существующего пути, упрощение/убирание лишнего шага, другой механизм или отсутствие новой функции — только когда они сохраняют нужный результат. Для неоднозначного решения обычно достаточно двух–трёх существенно разных вариантов; обязательной числовой оценки нет.

Сначала исключи варианты, нарушающие гарантии. Остальные сравни по первому понятному действию, доступности ожидаемой информации, рабочей плотности/эстетике, стоимости ошибки и восстановления, отклику, цене принятой агентной правки и сопровождения. Неизвестное оставь неизвестным. Назови допущение, которое может изменить выбор, и признак, при котором предпочтённый вариант будет отвергнут. Референсы передовых продуктов — источник механизмов, не доказательство их пригодности здесь.

## 4. Небольшая проверка и DS

Соотнеси проверку с вопросом: actual render для иерархии/эстетики; интерактивное задание для понятности; реальный API/domain сценарий для прав, сохранности и повторов. Дай цель без подсказки кнопки. Фиксируй первый выбор, помощь, ошибки, объяснение результата и восстановление; эстетическое предпочтение учитывай отдельно. Для сравнения кадров нужны одинаковые данные; для повторных человеческих заданий — эквивалентные наборы, чтобы не измерять запоминание. В baseline записывай известные viewport/theme/input, density и zoom; неизвестное обозначай unknown. Это метаданные сравнения, не обязательная матрица всех сочетаний; CSS zoom и browser zoom различай.

После понимания нужды проверь точный DS package: существующий pattern → поддержанная композиция → исправление документации/контракта → минимальное общее расширение. Не создавать mega-component для прикладного процесса; не урезать нужную работу из-за пробела DS. При общем изменении укажи затронутые текущие consumers, public API и применимые field/form/text/focus/outcome проверки. Типы и поиск строки не заменяют рендер и человеческий путь.

## 5. Решение и остановка

Запиши выбор и основание: исправить сейчас; упростить; не строить новую функцию; провести один конкретный опыт; остановить вариант/изменить постановку. «Не строить» не разрешает оставить подтверждённый критический дефект. Останови дальнейшее исследование, когда остаточная неопределённость не меняет разумный следующий обратимый шаг. Не требовать абсолютной уверенности или выдуманной частоты для исправления доказанного отказа.

Свяжи решение с scope, DS-gap, критерием приёмки и ещё неизвестным. Одиночный диагностический опыт с агентом показывает применение инструкции в этой задаче; фиксируй результат и известные затраты, не объявляй сравнительный выигрыш. Вывод о выигрыше в качестве, стоимости или сопровождении требует сопоставимой исходной задачи/reference, одинаковых условий, затрат до принятого результата с исправлениями и второй малой правки. Не назначай её каждому diagnostic или локальному исправлению; форматный validator не оценивает качество работы агента. Независимое ревью проверяет альтернативную причину и компромиссы. Спор AI-ролей не заменяет проверку с людьми.

## Минимальный контекст следующему агенту

Передай индекс задачи/поверхностей, одну актуальную карточку с evidence, принятое решение и релевантный recipe точного пакета. Дополнительные материалы открывать по причинной необходимости. Не загружать все отчёты и skills заранее. Acceptance schema 2.0 сохраняется: карточка объясняет выбор, plan/check IDs связывают его с проверкой, отдельная новая система статусов не нужна.
