# Концептуальное внедрение IQUIPAGE

## Результат и первый шаг
Пересобери ВЕСЬ согласованный UI: композицию, состояния, поведение и публичные компоненты. Сохрани функции, данные и права. Утверждённую удачную композицию не меняй ради демонстрации объёма работы. «Все возможности библиотеки» — рассмотреть её возможности для каждого сценария, не заставлять пользователя видеть все компоненты.

Сначала прочитай [конституцию](references/constitution.md) и [рабочий контракт](references/execution-contract.md). Найди проект, принятый DS, scope и предыдущий run-state. Выбери точечную работу или полную миграцию. Не проводи discovery заново для ясных согласованных исправлений.

## 1. База и паритет до кода
Прочитай действующие инструкции проекта, команды и авторизацию. Сохрани чужие незакоммиченные изменения. Проверь реальную поставку через `scripts/verify_release.py`; [release map](references/release-map.md) и `assets/ds-release-lock.json` относятся к pinned 05.7, не к любому latest. Не меняй pin для зелёного результата. Для принятой новой DS нужен отдельный provenance review и новый lock.

Инвентаризация охватывает routes, auth, overlays, settings/admin, flags, mobile, empty/error/recovery и роли. Свяжи каждую существующую операцию с поверхностью, предметной сущностью, DS-контрактом и acceptance. Таблица вместо обязательного холста, дедлайн вместо duration, readonly вместо редактирования — потеря функции, пока пользователь явно не согласовал изменение.

## 2. Проектирование и DS mapping
Примени [рубрику концепции](references/design-review.md). Главная работа, следующий шаг, служебные свойства и подтверждённый результат должны различаться. Используй общий shell/grid/density, а не коллекцию независимо оформленных страниц.

Прочитай релевантные семейства [карты поставки](references/release-map.md) и `references/capability-index.json`, затем фактические exports/types/пример принятой DS. Индекс — навигация, не доказательство API. Подбери supplied component, supplied composition или ограниченный adapter.

При большой миграции сначала цельный вертикальный сценарий: shell → список → объект → изменение → API → reload/отказ/отмена, light/dark/узкий экран. Получи решение по НОВОЙ композиции, если оно ещё не дано. Распространяй проверенный паттерн, не слабый первый черновик.

## 3. Недостаток DS — сообщить до обхода
Используй [DS-GAP](references/gap-protocol.md) и `assets/ds-gap.md`. Разделяй: возможность есть; ошибка приложения; ошибка поставленной DS; новая общая возможность; необходимая platform adaptation. Приложи фактический export/тип/fixture и минимальный недостающий контракт. Блокируй затронутую часть, а не весь проект.

Нельзя создавать новый контрол в app/shared и объявлять его DS, патчить внутренний DOM/CSS, импортировать private modules или ставить вторую UI-библиотеку. React event bridge и API adapter допустимы; новый календарь под видом bridge — нет. Native adaptation требует `assets/adaptation-record.md` с реальной платформенной причиной, публичным соответствием, владельцем и проверками.

## 4. Реализация и доказательства
Один неизменённый vendor boundary; JS/CSS одной поставки. Используй поддерживаемые core/advanced/whiteboard entries и согласованный lazy budget. Не включай gallery, demos и example-state в продукт. Через props/events передавай модели; сохраняй прикладные поля и identity.

Проверь controlled state, IME, cleanup, abort, поздние ответы, повторный accept, конфликт revision, смену прав и черновики. Intent не равен записи. Для команд с агентами прочитай [human-agent](references/human-agent.md): мандат, исполнение, принятие и сохранение — разные вещи.

## 5. Review → исправления → повторная проверка
По [методу качества](references/quality-method.md) пройди реальный продукт, не gallery. Если доступен `iquipage-review`, передай scope, план и fingerprints; иначе явно self-review. Отдельный агент не гарантируется названием скилла.

Сначала воспроизвести finding, исправить общий root cause, добавить regression, повторить затронутые состояния на текущем build. Не менять assertions ради PASS. DS-дефект снова проходит GAP. Новый scope не появляется тайком в исправлении.

## Доставка
Для полной миграции: inventory, capability-map, parity, gaps/adaptations, evidence, assessment schema 2.0 и handoff. Для точечной — компактная запись тех же решений без пустой бюрократии. Скрипты scanning/fingerprint помогают собрать данные, не принимают UI. Сохрани `assets/run-state.example.json` для продолжения.

Вердикт относится к согласованному scope, а не всей платформе по умолчанию. Не выдавай новую сборку с прежними доказательствами. Если запрошен архив, создай и проверь его перед ссылкой. Push/deploy — отдельное разрешение; полный проход этого скилла его не даёт.
