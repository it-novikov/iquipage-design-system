# Problem-first discovery

## Начать с известного
Сформулируй проблему, требования и минимально достаточное решение; выдай краткий бриф для явного утверждения. Код пока не писать. [Рабочий контракт](references/execution-contract.md) определяет полномочия и продолжение, [конституция](references/constitution.md) — сохранение языка IQUIPAGE.

Сначала прочитай доступный issue/brief/исследования/согласования. Отдели факт, предположение и неизвестное. **Не спрашивай повторно известное и не начинай с 3–5 вопросов автоматически.** Если для решения уже достаточно данных — сразу дай краткий proposed brief. Если нет — задай 1–3 самых важных вопроса, максимум пять за раунд. DS не обязателен для исследования проблемы; без него совместимость решения остаётся непроверенной.

## 1. Один реальный эпизод
Кто, чего хотел, где и что произошло вместо, как решает сейчас, последствия/частота. Недавний конкретный пример полезнее общей оценки. Причину помечай гипотезой, пока она не подтверждена. Разделяй проблему, симптом и названную первым вариантом функцию.

Формула: «Роль в контексте не достигает результата из-за наблюдаемого барьера; последствия; обход сейчас». Не выдумывай рынок, бюджет, аудиторию, частоту и метрики. В `references/interview-guide.md` — дополнительные вопросы только по необходимости.

## 2. Требования короткими раундами
Покрой релевантное: бизнесовую ценность/ограничения; роли/навыки/устройства; product scope/сущности; функции/альтернативные пути; безопасность/данные/сохранность; нагрузку/latency/доступность; миграцию/паритет. Для команды агентов — мандат, данные, лимиты, принятие, отмена и [контракт действий](references/human-agent.md).

После каждого ответа обнови понимание и только затем выбери следующий вопрос. Числовые targets без согласования — proposed/TBD. Референсы опциональны: уточни, что полезно и что не переносить. Отсутствие референса не блокирует исследование.

У requirements — ID (BIZ/USR/FUN/NFR/AGT/DS), source, priority, owner и проверяемое acceptance. Для маленькой задачи достаточно короткой таблицы, не всех пустых регистров. Если пользователь не знает технический параметр, предложи гипотезу проверки, не заставляй его придумывать число.

## 3. Достаточно ли данных и нужна ли функция
Готовность к предложению: понятны роль, проблема, желаемый результат, важные ограничения и кто принимает решение. Неизвестность, которая меняет scope/права/стоимость, блокирует утверждение, а не заполняется уверенным текстом. Остальные unknowns можно вынести в план проверки.

Сравни улучшение существующего пути, более простое content/process решение и новую функцию, когда эти альтернативы осмысленны. Не создавать три искусственные альтернативы для точечной правки. Возможный результат — не делать новую функцию.

Совместимость сверять по [реальному релизу](references/release-map.md), когда он доступен. Missing API не представлять существующим; по [GAP protocol](references/gap-protocol.md) записать риск/внешнюю зависимость. Не урезать известные функции из-за состава DS.

## 4. Предложение и утверждение
Бриф примерно 250–500 слов: проблема, аудитория, результат, решение, главный сценарий, входит/не входит, сохранение функций, DS fit/gaps, ограничения и риски. Подробности отдельно в `assets/requirements-register.md`; форма — `assets/solution-brief.md`.

Заверши одним вопросом об утверждении конкретной revision/scope. Proposed остаётся proposed до однозначного ответа. Молчание/«интересно»/собственный вывод не approval. Уже данное ясное разрешение не спрашивать снова. Существенное изменение функций/прав/риска требует нового решения, мелкое уточнение принятого — нет.

## Передача
Сохрани brief, requirements, sources/assumptions, decision reference, gaps, acceptance, run-state. Только после approval передай исполнителю. Согласование дизайна не разрешает деплой, изменение vendor, платежи или публичную публикацию. Если реализация не поручена, завершить на брифе; не переходить к коду автоматически.
