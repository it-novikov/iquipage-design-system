# Аудит понятности и целостности продукта

## Вход и граница
Разбери опыт человека и релевантные агентные сценарии, предложи конкретную перестройку. Не меняй приложение без поручения. Сохрани функции и принятый язык IQUIPAGE.

Начни с [конституции](references/constitution.md) и [рабочего контракта](references/execution-contract.md). Прочитай жалобы, текущий UI, маршруты, прежние решения и доступные данные. Укажи доступный уровень: кадр / код / interactive walkthrough / наблюдение участников. Нельзя превратить один screenshot в доказательство неудобства всех сценариев.

## 1. Рабочая задача
Кто, в каком контексте и как часто делает что; где начинает, какой результат нужен, как узнаёт, что он сохранён; что происходит при отказе. Если неизвестность меняет решение, спроси только блокирующее. Если brief уже достаточен, не запускай повторный опрос. Discovery нужен для новой проблемы, не как обязательный церемониал.

## 2. Пройди релевантные пути
Первое полезное действие, повторение частой операции, поиск/продолжение, ошибки/отмена/возврат. Делегирование, проверка и принятие результата — только если продукт их поддерживает или они утверждены. Различай роли, доступ и отсутствие данных. Не путай свободную доску с редактором workflow.

Записывай наблюдения отдельно от предполагаемых причин и эстетических предпочтений. Аналитика или заявка описывает источник, но не доказывает неизвестную частоту. При отсутствии runtime сформулируй ограничения и необходимые поведенческие тесты.

## 3. Три перспективы, не выдуманная команда
UX-исследование: расхождение с ожиданиями; гипотезы; задания для пользователей без подсказок жестов. UI/UX: информационная архитектура, сценарии, ошибки, раскрытие сложности и доступность. Арт-дирекция: [главный объект, иерархия, сетка, ритм и выразительность](references/design-review.md). Перечисление перспектив не означает интервью или работу нанятых специалистов.

Для человеческих и агентных ролей используй [human-agent](references/human-agent.md): стабильные сущности, мандат, явные последствия, проверяемое принятие, отмена, audit trail. Машинная доступность не отменяет читаемые подписи и не даёт агенту дополнительных прав.

## 4. Конкретное целевое решение
Для каждой проблемы: текущее представление → препятствие результату → что объединить/перенести/убрать/переименовать → новый путь → supplied DS pattern → acceptance. «Сделать премиальнее» без конкретной структуры не задание.

Пример: соединить header/summary через public compact work layout, перенести свойства задачи из основного потока в контекст, сопоставить полезную рабочую площадь при 1280×720. Это гипотеза композиции до проверки, не обещание роста конверсии.

Для существенного спорного решения сравни две альтернативы на одинаковых данных; для локального бага достаточно одной исправленной композиции. Проверяй mappings по [release map](references/release-map.md) и реальному API. Missing capability передать по [DS-GAP](references/gap-protocol.md), не как задание «сделать похожий контрол».

## Выход и следующий шаг
Выдай короткое резюме, карту путей, конкретный backlog с ID, evidence/confidence, priority, целевой структурой, DS mapping и проверкой. Используй `assets/experience-report.md`; для исследований — вопросы и критерии, не фиктивные результаты. Предложение сначала утверждается, если меняет продуктовый scope.

Для реализации передай `iquipage-implement`; для дефектов кода — `iquipage-review`. Если их нет, отдавай переносимый handoff, не утверждай запуск. Сохранить run-state и исходные ограничения. Нет итогового «идеально»: оценка касается явно просмотренного scope, а не всех возможных людей и состояний.
