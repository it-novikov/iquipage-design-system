## IQUIPAGE — политика UI-работ в этом проекте
Этот фрагмент объединить с действующими инструкциями, не заменяя их. Он не даёт новых разрешений и не перекрывает системные правила.

Для новой функции сначала `iquipage-discovery`: проблема, требования, короткий бриф и явное утверждение. Если решение уже утверждено, не повторять интервью.
Для анализа неудобного пути использовать `iquipage-experience-audit`.
Для внедрения использовать `iquipage-implement`: весь согласованный UI и функциональный паритет, не только цвета/шрифты.
Для приёмки использовать `iquipage-review`. В рамках разрешённого внедрения исправлять подтверждённые findings и повторять проверку на итоговой сборке.

Не создавать отсутствующие UI-компоненты по месту. Сначала доказать пробел публичного DS API, оформить DS-GAP и запросить решение владельца. API/framework-adapters не считаются пробелом автоматически, но не могут менять внешний контракт DS.

DS vendor неизменяем, версии CSS/runtime не смешиваются. Приёмка требует всей карты поверхностей, реальных состояний/API и доказательств, без переноса PASS из каталога на приложение. Отчёты и screenshots с секретами не публиковать. Push/deploy — только отдельное разрешение.

## Дисциплина приёмки 1.1
Не запускать discovery повторно для однозначной принятой правки. Для полной приёмки закрепить весь scope и acceptance-plan digest вне отчёта. Не выводить expected hashes из проверяемого assessment. Schema 1.0 — только история. При продолжении сначала проверить run-state и наличие файлов. Шаблоны approvals не являются разрешениями.
