- **F1** [P1] `products/sprintique/server/src/main/kotlin/com/sprintique/planning/application/PlanningStates.kt:83` — дата вехи читается как обязательная строка: `it.string("date")`. Но `app.milestones.date` допускает NULL (`date date`), и все три контракта разрешают веху без даты: `MilestoneWriteValue.date: String?`, `MilestoneValueContract.date: String?` в команде `milestone` и интент `milestone` экрана планирования. Кроме того, `schedule` с `entity.kind = "milestone"` и `plannedStart = plannedEnd = null` проходит проверку `start == end` и сохраняет `date = null` (`PlanChange.kt`, `milestones[index] = milestone.copy(date = start)`). Для NULL `Row.string` делает `error("Column date is not text")`. Прежний бэкенд возвращал `null`.
  Сценарий: `PUT /api/v1/projects/{p}/planning/milestones/gate` с `{"baseRevision":0,"value":{"title":"Gate","date":null}}` → 200, строка сохранена. После этого любой вызов `PlanningStates.load` падает с `IllegalStateException` и отвечает 500. Это PUT и PATCH задачи, все запросы экрана планирования, превью и коммиты, список релизов, roadmap, история. Планирование проекта перестаёт работать, пока строку не поправят в базе. Так же ломается база, перенятая у прежнего мигратора, если в ней есть веха без даты. Тесты этого не видят: все вехи в `planning.test.ts` и `planning-view.test.ts` создаются с датой.
  Что предлагаю: `it.stringOrNull("date")`. Добавить HTTP-тест: веха без даты сохраняется, после неё загружаются `planning-view/groups` и timeline. Заодно проверить остальные чтения `Row.string(...)` на nullable-колонки (я прошёл по списку и других не нашёл).

- **F2** [P2] `products/sprintique/server/src/main/kotlin/com/sprintique/identity/application/EmailSignIn.kt:55-75` (HEAD) — лимиты кода считаются только по адресу почты, а не по тому, кто запрашивает код. Новый запрос к тому же адресу гасит действующий код из любого браузера: `UPDATE auth.email_challenges SET consumed_at ... WHERE email = $1`. Проверка `Origin` в `EmailSignInController` не мешает клиенту вне браузера. Бюджет входов `RequestLimitFilter` (20 в минуту на адрес клиента) пять запросов в час не останавливает.
  Сценарий: злоумышленник пять раз в час, раз в 30 с, отправляет `POST /auth/email/start {"email":"victim@example.com"}` с заголовком `Origin: <publicOrigin>`. Каждый запрос гасит код, который жертва только что получила. Шестой запрос жертвы получает `429 EMAIL_CODE_LIMIT` на час. Вход по почте основной и в production обязательный, поэтому человек фактически не может войти.
  Что предлагаю: считать лимит «30 с / 5 в час» по паре «адрес почты + клиент» и гасить только коды того же клиента. Коды и так привязаны к cookie браузера, так что чужой код ничего не даёт. Общий потолок на адрес оставить заметно выше. В рабочей копии уже лежит незакоммиченная правка в эту сторону: `client_hash`, миграция 022, дневной потолок на адрес. Её я не ревьюил. Если потолок на адрес останется, его по-прежнему можно исчерпать с разных адресов. Это стоит записать в 0002 как принятый риск.
  Решение: [fixed eaf1241]

- **F3** [P3] `products/sprintique/server/src/main/kotlin/com/sprintique/identity/application/EmailSignIn.kt:69,85` (HEAD) — прежний код гасится в уже закоммиченной транзакции до отправки письма. Если SMTP затем отказал, удаляется только новый вызов. Комментарий «The code never reached anyone: forget it, so it does not count against the address» верен лишь наполовину.
  Сценарий: человек получил код A и через 30 с нажал «Отправить код ещё раз». Реле временно недоступно, ответ `503 MAIL_UNAVAILABLE`. Cookie браузера по-прежнему указывает на вызов A, но A уже погашен. Ввод кода A из письма даёт `EMAIL_CODE_EXPIRED`, хотя A честно доставлен и срок не истёк.
  Что предлагаю: гасить прежние коды после успешной отправки, отдельным UPDATE. Второй вариант: при `MailUnavailableException` снимать `consumed_at` с кодов, погашенных этим запросом. Комментарий поправить.
  Решение: [fixed eaf1241]

- **F4** [P3] `products/sprintique/server/src/main/kotlin/com/sprintique/identity/api/SignInController.kt:40,112` — KDoc класса обещает, что при сбое браузер возвращается на экран входа с кодом ошибки. На деле это так только для отказов проверки и `ProblemException`.
  Сценарий: (1) Google или Apple недоступен при discovery. Тогда `identity.start(...)` в `login()` бросает `IOException` или `ParseException`, и пользователь, нажавший ссылку «Продолжить с Google», видит сырой JSON 500 вместо `/?sign-in-error=...`. (2) Два параллельных первых входа с одним Google `sub` без подтверждённой почты (не Gmail и без `hd`) обходят advisory lock: он берётся только при `verifiedEmail != null`. Оба доходят до `created()`, второй `INSERT INTO auth.identities` нарушает PK, в `finish()` это не `ProblemException`, и пользователь получает 500.
  Что предлагаю: в `login()` оборачивать сбой провайдера в `failed("LOGIN_UNAVAILABLE")`. В `Accounts.signIn` брать advisory lock по `issuer:subject` всегда, а по почте дополнительно. Другой вариант — `ON CONFLICT DO NOTHING` с повторным `known()`.
  Решение: [fixed eaf1241]

- **F5** [P3] `products/sprintique/server/build.gradle.kts:207-211` — образ Jib не задаёт `SPRINTIQUE_ENVIRONMENT`, и по умолчанию действует `development` (`application.yaml`: `${SPRINTIQUE_ENVIRONMENT:development}`). - **F6** [P3] `products/sprintique/scripts/check-local-sign-in.mjs:23,28` (HEAD) — в скрипте три дефекта, запуск их не покажет:

Проверка `code spent once` попадает в evidence без основания.
  (b) Повторный запуск на существующем стенде падает. PUT задачи всегда отправляет `createInBoard:true`, и при `baseRevision > 0` сервер отвечает `400 CREATE_ONLY` (`Tasks.put`). Кроме того, повтор в течение 30 с или шестой запуск за час получает 429 на `/auth/email/start`: адрес `sprintique-qa@example.invalid` фиксированный.
  (c) `backup-drill.mjs:57` требует хотя бы один приватный файл в S3, а скрипт входа его не создаёт. На свежем стенде без Keycloak (A5) учения падают, если файл не загрузили вручную.

Часть этого (b и c) уже есть в незакоммиченной рабочей копии. Я её не ревьюил, а (a) там не исправлен.
