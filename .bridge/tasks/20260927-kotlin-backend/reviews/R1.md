# Ревью R1

## Замечания

- **F1** [P2] `products/sprintique/server/src/main/kotlin/com/sprintique/identity/application/EmailSignIn.kt:47` — лимиты на адрес («не чаще 30 с» и «5 кодов в час») проверяются обычным `SELECT count(*) ... WHERE email = $1` без блокировки, в READ COMMITTED. Проверка и `INSERT` (строка 74) не сериализованы. `UPDATE ... SET consumed_at` (строка 67) не видит незакоммиченные вызовы-соседи, поэтому после гонки активными остаются все вставленные вызовы.
  Сценарий: атакующий шлёт пачку одновременных `POST /auth/email/start` с адресом жертвы (single-packet или несколько IP, лимит 20/мин на адрес клиента). Все запросы видят `n = 0` и `tooSoon = false`, и каждый получает свой challenge-cookie с пятью попытками. Вместо 25 угадываний в час на адрес получается 5 × размер пачки. Даже без гонки нет суточного потолка: 25 попыток в час без ограничения по времени дают около 0,06 % в сутки на один адрес. С гонкой это кратно больше, и шестизначный код становится подбираемым при целевой атаке.
  Что предлагаю: в начале транзакции `start` взять `pg_advisory_xact_lock(hashtextextended('email-code:' || $1, 0))`, как это уже сделано в `Accounts.signIn`. Добавить потолок неудачных попыток на адрес за сутки (например, 20), после которого коды не выдаются до конца окна. Добавить тест на параллельные `start`.
  Решение: [fixed eaf1241]

- **F2** [P2] `products/sprintique/server/src/main/kotlin/com/sprintique/identity/application/EmailSignIn.kt:55` — лимиты считаются только по адресу получателя, а не по браузеру или клиенту. Каждый `start` к тому же гасит действующий код адреса (строки 67–73: `UPDATE auth.email_challenges SET consumed_at ... WHERE email = $1`).
  Сценарий: кто угодно без аккаунта запрашивает код для `victim@example.org` 5 раз за 2,5 минуты. Дальше жертва час получает `EMAIL_CODE_LIMIT`, а её код, пришедший раньше, уже погашен. Повтор раз в час с одного IP полностью закрывает жертве вход по почте, основной способ входа. Жертва вдобавок получает поток писем.
  Что предлагаю: не гасить чужие вызовы. Каждый вызов и так привязан к своему cookie: новый код должен заменять только вызов того же браузера (по токену из cookie, если он есть). Лимит частоты считать по паре «адрес + клиент», а общий лимит на адрес сделать заметно выше пользовательского. Либо принять риск явно и записать это в ADR 0002.
  Решение: [fixed eaf1241]

- **F3** [P2] `products/sprintique/server/src/main/resources/db/migration/V20260928000021__add_sign_in_methods.sql:14` и `products/sprintique/docs/operations.md:25` — документация и ADR обещают: «People who signed in through the previous OIDC provider kept their accounts … a code sent to their address leads to the same person». Но прежний вход запрашивал только `scope: 'openid profile'`: в TS `backend/http/oidc.ts` и в Kotlin до `ad31251`, где стояло `Scope("openid", "profile")`. Стандартные провайдеры (Google, Auth0, Okta и другие) без scope `email` не отдают `email` и `email_verified`. Значит, у их людей `auth.principals.email IS NULL`. Их identity с прежним issuer больше никогда не встретится, потому что прежнего провайдера в конфигурации нет.
  Сценарий: инсталляция, где раньше вход шёл через Google-OIDC, обновляется. Человек входит кодом на свой адрес: `known` → null, `joined` → null (адреса у principal нет), `created` → новый пустой principal без членства в проектах. Старый аккаунт с проектами, задачами и авторством недоступен, и пользователь видит пустое пространство. `SignInMigrationIntegrationTest` проверяет только случай, когда почта уже заполнена. На Keycloak (email входит в default client scopes) дефект не проявляется, поэтому стенд его не ловит.
  Что предлагаю: до выката посчитать `SELECT count(*) FROM auth.principals WHERE kind='human' AND email IS NULL AND issuer IS NOT NULL`. В operations.md описать ограничение и ручную процедуру: связать identity почты с существующим principal после проверки владельцем пространства. Уточнить формулировку в ADR 0002 и operations.md.
  Решение: [fixed eaf1241]

- **F4** [P3] `products/sprintique/server/src/main/kotlin/com/sprintique/web/RequestLimitFilter.kt:71` — когда таблица окон заполнена (4096 адресов) и среди них нет истёкших, новый адрес сразу получает 429 (`if (windows.size >= MAX_WINDOWS) return false`). По тем же правилам вытесняются и окна обычных клиентов.
  Сценарий: клиент с большим пулом адресов (IPv6 /64 или ботнет) раз в минуту шлёт по одному запросу с 4096 разных адресов. Все новые пользователи получают 429 на `/api/` и `/auth/`, включая вход. Поведение перенесено из TS (`backend/http/limits.ts`) без изменений, то есть это не регрессия порта. Реальную эксплуатируемость за конкретным прокси не проверял.
  Что предлагаю: при переполнении вытеснять самое старое окно (LRU), а не отказывать новым адресам. Для IPv6 агрегировать адрес до /64.
  Решение: [deferred 20260927-kotlin-backend: унаследовано из TS; общий контроль допуска для нескольких экземпляров уже значится в operations.md «Observability and limits»]

- **F5** [P2] `products/sprintique/server/src/main/kotlin/com/sprintique/event/api/EventController.kt:69` — лимиты потоков SSE (100 на сервер, 3 на credential) проверяются через `streams.size` и `streams.values.count { it == identity }`, а сам поток добавляется в карту позже (`streams[emitter] = identity`, строка 77). Проверка и добавление не атомарны, а запросы обрабатываются параллельными потоками сервлета. В TS (`backend/http/events.ts:25-30`) это был один синхронный такт Node, то есть регрессия порта. Кроме того, в TS поток закрывался при очереди записи больше 256 KiB, а в Kotlin такого предела нет: клиент, который перестал читать, держит свой слот.
  Сценарий: одна сессия или токен агента шлёт N одновременных `GET .../events?stream=true`. Все они выполняют первый `read`, видят счётчик меньше 3 и открывают N потоков; повторными пачками можно превысить и лимит 100. Каждый поток раз в секунду открывает транзакцию (`read` → `authentication.run`), так что один credential может занять пул соединений БД.
  Что предлагаю: проверку и добавление делать под одной блокировкой (`synchronized`) или через `compute` на счётчике по identity. Вернуть предел на неотправленные данные.
  Решение: [fixed eaf1241]

- **F6** [P2] `products/sprintique/server/src/main/kotlin/com/sprintique/media/infrastructure/ImageIoImageTranscoder.kt:98` — при таймауте слот декодера освобождается (`finally { decoder.dispose(); slots.release() }`), а сама работа может продолжаться: `future.cancel(true)` не прерывает `ImageReader.read`, отрисовку Java 2D и нативный libwebp. Для JPEG (TwelveMonkeys, который делегирует JDK `JPEGImageReader`) вызов `abort()` или `dispose()` из чужого потока во время `read()` бросает `IllegalStateException`: так устроена потоковая блокировка в исходниках JDK, но сам запуск я не проводил. Тогда `dispose()` в `finally` бросает, `slots.release()` не выполняется, и слот теряется навсегда. В TS таймаут sharp действительно останавливал libvips, и ограничение «2 декодера» держалось.
  Сценарий: вошедший пользователь отправляет `PUT /api/v1/profile/avatar` (резервирование не нужно) с изображением, которое декодируется дольше 10 с при ≤40 МП, например прогрессивный JPEG с множеством сканов или 16-битный PNG. Если `read()` ещё идёт, два таких запроса дают вечный 429 `IMAGE_BUSY` на все загрузки изображений до перезапуска. Если таймаут срабатывает после `read()`, слот освобождается при живой работе, и повторные запросы копят неограниченное число фоновых декодирований (сотни МБ на каждое), вплоть до исчерпания памяти.
  Что предлагаю: освобождать слот только по фактическому завершению задачи (`whenComplete` или `finally` внутри задачи). Завернуть `abort()` и `dispose()` в отдельные `runCatching`. Создавать `Decoder` внутри `try`. Добавить тест с зависающим декодером.
  Решение: [fixed eaf1241]

- **F7** [P3] `products/sprintique/server/src/main/kotlin/com/sprintique/web/RequestLimitFilter.kt:27` — фильтр решает, что считать, по сырому `request.requestURI` (префиксы `/api/`, `/auth/` и список `LOGINS`), а Spring MVC сопоставляет маршруты по декодированному пути. По словам параллельного агента, `StrictHttpFirewall` не блокирует `%61`, но этого я не проверял запуском.

Подбор кода по-прежнему ограничен 5 попытками на вызов, но это усиливает F1. Вероятно, унаследовано из TS: там `limits.ts` тоже смотрел на сырой `r.url`.

  Решение: [fixed eaf1241]
