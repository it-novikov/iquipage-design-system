## Независимая проверка контрмоделей

Выполнена короткая Python-проверка целочисленных сравнений на данных **из frozen файла**. Перед вычислением скрипт через `git show` проверил наличие именно трёх исходных времён, `.500Z` у tied group, read-by-id первого item и cutoff первого item. Это анализ предикатов; не PostgreSQL/API-тест, не мок БД и не замена runtime gate.

Получены результаты:

| Предикат / порядок | Результат |
| --- | --- |
| Точный timestamp DESC, id DESC | Страница 1: `1,2,3,25,24,…,9`; страница 2: `8,7,6,5,4`. |
| Только id DESC | Отличается от expected; текущий тест отклонит. |
| Округление timestamp до ms с последующим id DESC | Отличается от expected; текущий тест отклонит. |
| Точный cursor и усечённый до ms cursor на текущей `.500Z` boundary | Оба возвращают `8,7,6,5,4`: F1. |
| Те же варианты на boundary `.500001Z` | Точный возвращает `8,7,6,5,4`; усечённый — `[]`. |
| Read-all `<=` и `<` после индивидуального чтения ordinal 1 | Оба оставляют unread `[26]`: F2. |
| Read-all `<`, если ordinal 1 ещё непрочитан | Оставляет unread `[1,26]`, то есть реальный ошибочный результат. |

Основу расчёта можно воспроизвести без сторонних зависимостей:

```python
rows = [(600002 if i == 1 else 600001 if i == 2 else
         600000 if i == 3 else 500000, i) for i in range(1, 26)]
ordered = sorted(rows, reverse=True)
cursor = ordered[19]
coarse = (cursor[0] // 1000 * 1000, cursor[1])
assert cursor == coarse == (500000, 9)
assert [i for at, i in ordered if (at, i) < cursor] == [8, 7, 6, 5, 4]
with_later = rows + [(600003, 26)]
assert [i for at, i in with_later if i != 1 and not at <= 600002] == [26]
assert [i for at, i in with_later if i != 1 and not at < 600002] == [26]
```

## Что проверено и почему основное решение подходит

- **Независимость oracle.** Ожидаемые IDs заданы из управляемой фикстуры, не получены сортировкой HTTP-ответа и не вычислены повторным запросом production SQL. Сравнение массивов проверяет весь порядок обеих страниц. IDs первых трёх строк противоположны timestamp order, поэтому простая замена на сортировку по id или срезание точности timestamp при сортировке не пройдёт (`notifications.test.ts:145–167`).
- **ID и граница.** `randomUUID().slice(0,24)` сохраняет корректный UUID-префикс с последним дефисом; 12 hex цифр ordinal дают валидные UUID и определённый порядок последнего компонента. Ожидаемая tied group — ordinals `25..4`, граница — `9/8`. Exact length `20/5`, полный ID oracle, `second.nextCursor === null` и отсутствие пересечений проверены статически.
- **Изоляция состояния.** Собственный `human` не наследует уведомление global `dan` из NT02. `before === 25` теперь обоснован управляемыми данными; `dan` остальных сценариев сохранён. Уникальные principal/project и prefix IDs предотвращают конфликты с соседними сценариями. Setup идёт через существующий `f.admin` только для ephemeral test data; чтение и действия по-прежнему идут по HTTP.
- **Сохранение существующих гарантий.** Есть unread count, read-by-id, чужой ID не изменяет целевое уведомление, bad cursor/empty command, отказ runtime-role INSERT и UPDATE(kind) с SQLSTATE `42501`. Проверено, что `RuntimeDatabase.authenticated` действительно использует runtime connection и transaction actor context; `afterMigrate.sql:99–100` отбирает INSERT/UPDATE и даёт только UPDATE(read_at). Политики `own_read`/`own_mark` в V42 согласованы с этим. Эти проверки сохранены, но они не являются исчерпывающим аудитом всех RLS/CSRF/permission сценариев.
- **Read-all за границей.** Новая строка `600003 µs` и cutoff `600002 µs` хорошо проверяют, что уведомление на 1 µs позже остаётся непрочитанным. Совместно count и exact unread ID отличат потерю точности cutoff, способную прочитать лишнее или оставить лишние старые строки. F2 касается отдельной включающей границы.
- **Реальный timestamp path.** В неизменённом `Transaction.kt:103` timestamp читается через `OffsetDateTime.toInstant`; `Notifications.kt:57–69` сравнивает пару timestamptz/UUID, `:166` выдаёт `Instant.toString`, `:195–205` сохраняет и разбирает точный instant cursor. Изменение runtime сортировки без свидетельства дефекта не требуется.
- **Legacy predicate.** Diagnostic выводит фактические три timestamp и результат старого сравнения строк (`notifications.test.ts:158–162`). Он не стал permanent gate. Это правильно: ожидаемый порядок данных должен сохраняться и при другой корректной записи дробной части. A1 в карточке остаётся открытым до observed runtime evidence. Нельзя по одной модели утверждать, что старый failing pair установлен.
- **Стоимость.** Два маленьких локальных helper внутри NT05, 26 управляемых insert и один дополнительный synthetic recipient; нет parser framework, зависимости, нового runner или production abstraction. Сокращать точный oracle до `Date.parse` не следует: это потеряло бы необходимое различение микросекунд.

## Разногласия ролей и решение

| Роль / возможное возражение | Оценка и решение |
| --- | --- |
| QA: исправление failing gate может лишь скрыть дефект | Exact IDs на противонаправленных timestamp/ID — содержательный regression oracle. Однако precision надо задать и на cursor boundary (F1), а cutoff оставить непрочитанным до read-all (F2). |
| Backend: тест должен учитывать точность и изоляцию | Runtime код и grants менять не нужно. Сохраняем реальные PostgreSQL/HTTP проверки; корректируем только данные, чтобы тест различал два точечных дефекта. |
| Maintainer: не раздувать NT05 и не добавлять инфраструктуру | Оба замечания исправляются существующими данными и выбором item. Общий date helper, новый test runner и отдельный full-gate ради намеренного FAIL не требуются. |
| Пользователь: при листании нельзя терять уведомления; read-all должен прочитать увиденное | F1 приоритетен из-за пропуска целого хвоста уведомлений. F2 закрывает обычное граничное поведение «Прочитать все». |
