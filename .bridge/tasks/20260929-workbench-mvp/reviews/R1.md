# Ревью R1

## Замечания

- **F1** [P1] `products/sprintique/server/src/main/kotlin/com/sprintique/workbench/application/Workbench.kt:453` — Откладывание скрывает запросы по `r.created_at <= s.snoozed_at`, то есть по времени создания запроса, а не по моменту, когда он стал адресован человеку. `AttentionRequests.change` (`AttentionRequests.kt:169-174`) переназначает запрос и возвращает сиротский в `open`, не меняя `created_at`, и не сохраняет, когда запрос назначен на текущего адресата. Поэтому запрос, переданный человеку после откладывания, прячется так же, как старый. Это нарушает ADR W5 п. 9 («новый запрос пробивает откладывание») и бьёт по полноте прямых запросов (§16, direct ask recall).
  Сценарий: Борис просит Алису ответить по задаче T (req1). Алиса откладывает T на 7 дней. Карина раньше создала на T запрос req2 для Дениса, Дениса понизили до reader (req2 → `orphaned`), и Карина через PATCH переназначает req2 на Алису. У req2 нет `neededBy`, `created_at < snoozed_at`, поэтому req2 7 дней не виден в «Нужно действие» (он есть только в списке «Отложенные»). То же случится, если Денис, оставаясь редактором, сам передаст req2 Алисе.
  Решение: [fixed 5031765] `attention_requests.addressed_at`: создание или переназначение на адресата; откладывание скрывает только дошедшее до него раньше; тест W14.

- **F2** [P1] `products/sprintique/tests/workbench.test.ts:75` — В матрице включения §15, которую критерий A3 требует держать зелёной, нет тестов на рискованные ветки, которые реализованы, но ничем не проверены: (а) блокировки: `your_work_blocked` (`Workbench.kt:546-552`, `Reasons.assigned`), `delegated_blocked` (`Reasons.waiting`, `Activity.isNewBlocker`) и триггер `record_dependency_activity`, который пишет события для обоих концов связи (`V20260929000029__add_task_activity.sql:66-79`); (б) подавление собственного шума по инициатору: `e.initiator_id IS DISTINCT FROM $1` (`Workbench.kt:493`) держится только на новом `set_config('app.initiator_id', …)` в `Authentication.kt:51`; (в) события `thread`/`resolution` из триггеров сообщений и обсуждений у подписчика. Все HTTP-сценарии правят задачи только сессиями людей, агент появляется лишь в проверке `403` (строки 268-272).
  Сценарий: если кто-то уберёт `app.initiator_id` из `Authentication` или перепутает `from_id`/`to_id` в триггере зависимостей, все тесты останутся зелёными. Первый случай засыплет «Изменилось» правками собственного агента человека. Второй покажет блокировку не на той задаче, и никто этого не заметит.
  Решение: [fixed 5031765] тесты W11 (блокировки обоих концов, `your_work_blocked`, `delegated_blocked`), W12 (свой агент по `app.initiator_id`), W13 (события обсуждения у участника).

- **F3** [P2] `products/sprintique/server/src/main/kotlin/com/sprintique/workbench/application/PersonalState.kt:379` — `ensureWatermark` двигает водяной знак только при `last_seen_sequence IS NULL`, а уже существующий оставляет. ADR W3 п. 5 требует ставить знак на текущую позицию при начале отношения (подписка, «Жду», свой запрос), «чтобы история до отношения не считалась новой».
  Сценарий: Алиса подписалась на T (знак 10), посмотрела и отписалась. Затем Борис 40 раз меняет статус и сроки. Алиса снова подписывается, и T сразу попадает в «Изменилось» с 40 «новыми» событиями из истории до подписки. То же с повторным «Жду» после `resolve`: причиной строки становится старое событие (например `delegated_blocked` из давней зависимости).
  Решение: [fixed 5031765] `startRelation` ставит знак на текущую позицию, если отношение начинается с нуля; в cd5b006 перенесено на «Участвую»; тест W14.

- **F4** [P2] `products/sprintique/server/src/main/kotlin/com/sprintique/workbench/application/Waiting.kt:69` — CAS при первом «Жду» не защищён. `SELECT … FOR UPDATE` не блокирует строку, которой ещё нет, а `INSERT … ON CONFLICT DO UPDATE` (строки 90-99) безусловно поднимает `revision`. `PersonalState.lock` решает ту же задачу правильно: сначала `INSERT … DO NOTHING`, затем `FOR UPDATE`.
  Сценарий: две вкладки одновременно отправляют `POST …/wait-state` с `baseRevision: 0`, разными ключами и разными `checkBackAt`. Обе получают `200`: вторая перезаписывает дату первой и получает `revision 2`. Первая вкладка молча теряет свою дату и на следующем PATCH получает `409`. Ожидалось `409 WAIT_ACTIVE` или `CONFLICT` для одной из вкладок.
  Решение: [fixed 5031765] advisory-блокировка первого старта; в cd5b006 таблица «Жду» убрана (производное от участия), гонка первого участия — тест W14 `[200,409]`.

- **F5** [P2] `products/sprintique/server/src/main/kotlin/com/sprintique/workbench/application/Plan.kt:155` — Запрос на утверждение, у которого истёк срок предложения, навсегда остаётся `status='open'`. Скрыт он только при чтении «Сейчас» (`Workbench.kt:458-459`), а в остальных местах живёт. «План» показывает его без фильтра по `approvals`: как просроченный `neededBy` в «Сегодня». `requireSnoozable` (`PersonalState.kt:312-320`) считает его открытым и позволяет «отложить» невидимое. `OPEN_LIMIT` (`AttentionRequests.kt:100-104`) засчитывает его в лимит адресата. Автору о тихом закрытии не сообщается: истечение не создаёт события.
  Сценарий: агентское предложение с `expires_at` через сутки. Борис просит Алису утвердить его с `neededBy` завтра. Предложение истекает. «Сейчас» у Алисы запрос не показывает, а «План» послезавтра показывает «просрочено: утвердить» по задаче, и сделать с ним ничего нельзя (`decide` вернёт `APPROVAL_STALE`).
  Решение: [fixed 5031765] запросы на истёкшие утверждения исключены из «Плана», проверки откладывания и лимита адресата (`auth.open_requests_for`).

- **F6** [P2] `products/sprintique/server/src/main/kotlin/com/sprintique/workbench/application/AttentionRequests.kt:100` — Лимит «500 открытых запросов на получателя» (ADR W1, W4 п. 6) считается под RLS того, кто спрашивает, то есть только в проектах, которые он видит, и без блокировки по адресату. Так же без сериализации считаются `FOLLOW_LIMIT` (`PersonalState.kt:88-91`) и `ACTIVE_LIMIT` (`Waiting.kt:85-89`). Лимит на адресата не соблюдается, а на нём держится оценка ёмкости выдачи («запрос ограничен числом отношений одного человека»).
  Сценарий: у Алисы по 400 открытых запросов в трёх проектах от разных авторов, каждый автор видит только «свой» проект. Всего 1200 открытых запросов при лимите 500. Параллельные `create` с одним адресатом тоже обходят проверку count-then-insert.
  Решение: [fixed 5031765] лимит адресата по всем проектам через `auth.open_requests_for` под блокировкой адресата (и при переназначении); лимиты участия — под блокировкой человека.

- **F7** [P2] `products/sprintique/server/src/main/kotlin/com/sprintique/workbench/application/Workbench.kt:450` — Флаги описаны как независимые (ADR W6 п. 7), но при `workbench_personal_state=off` и включённых `workbench_requests` или `workbench_waiting` CTE `personal` пуст (`$4::boolean`). Тогда `unseen` считает события от нуля (`coalesce(s.last_seen_sequence, 0)`, строка 492), хотя водяные знаки в базе есть: их пишут `create` и `Waiting.start`. А `PUT …/personal/seen` отвечает `404` (`PersonalTaskController.kt:109`).
  Сценарий: `SPRINTIQUE_FEATURES=workbench_read_internal,workbench_requests`. Автор запроса видит свою задачу в «Изменилось» со всей историей событий запроса с первого дня и не может отметить её просмотренной. Строка висит, пока не пройдут 30 дней после закрытия запроса.
  Решение: [fixed 5031765] водяные знаки читаются при любых флагах; `seen` доступен, если включены личное состояние, запросы или «Жду».

- **F8** [P2] `products/sprintique/server/src/main/kotlin/com/sprintique/workbench/application/PersonalState.kt:136` — Команда фокуса сначала берёт блокировку своей строки (`lock`, строка 133) и только потом общую advisory-блокировку `focus:<actor>`. Перенумерация (строки 198-207) обновляет все строки фокуса человека. Кроме того, тест утверждает, что проверяет перенумерацию, но не доходит до неё: `workbench.test.ts:301-303` чередует up/down одной задачи между одними и теми же соседями, середина каждый раз одна и та же, промежуток не исчерпывается, и ветка `move → UPDATE … row_number()` ни разу не выполняется.
  Сценарий: T1 (`up` по X, нужна перенумерация) держит строку X и advisory и ждёт строку Y. T2 (`add` по Y из другой вкладки) держит строку Y и ждёт advisory. PostgreSQL обрывает одну из транзакций с `40P01`, пользователь получает `500`. Если перенумерация сломается, тесты останутся зелёными.
  Решение: [fixed 5031765] блокировка человека до блокировки строки; тест перенумерации доходит до ветки `row_number()` (24 сдвига, ранги различны), W06.

- **F9** [P2] `products/sprintique/server/src/main/kotlin/com/sprintique/workbench/application/Workbench.kt:270` — Сервер и контракт ответа расходятся. `contracts/workbench.ts:46` объявляет `request.note: string` обязательным полем строки, а `item()` его не отдаёт, хотя SQL выбирает `request_note` (строка 521). Нужно решить явно: либо убрать `note` из контракта (delivery-plan §4.2 не советует тексты в строке первого экрана без отдельного решения), либо отдавать его.
  Сценарий: UI S4 по типу `WorkbenchRow` рендерит `row.request.note`, получает `undefined`, и заметка запроса молча пропадает. Типы TS этого не ловят, потому что ответ не валидируется.
  Решение: [fixed 5031765] `note` убран из контракта строки (delivery-plan §4.2), доступен в drawer через `/personal`.

- **F10** [P3] `products/sprintique/server/src/main/kotlin/com/sprintique/web/StaticWebController.kt:30` — Выключенный флаг скрыт не полностью. `/workbench`, `/workbench/plan` и `/workbench/tasks/…` всегда отдают интерфейс, даже при `workbench_read_internal=off`. У API флаг проверяется после аутентификации (`WorkbenchController.kt:38-39`), поэтому анонимный запрос получает `401` вместо `404`.
  Сценарий: в production без `SPRINTIQUE_FEATURES` `GET /workbench` отвечает `200` (страница затем получает `404` от API), а `GET /api/v1/workbench` без cookie отвечает `401`. Так можно узнать, что раздел существует, вопреки ADR W6 п. 7.
  Решение: [fixed 5031765] `FeatureFilter` до аутентификации: выключенная функция — 404 и для страниц, и для API; тест W14.
