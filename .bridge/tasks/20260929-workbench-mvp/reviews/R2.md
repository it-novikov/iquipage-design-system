# Ревью R2

## Замечания

- **F1** [P1] `products/sprintique/server/src/main/kotlin/com/sprintique/workbench/application/PersonalState.kt:130` — Личные команды и общие команды проекта берут блокировки в разном порядке, поэтому возможна взаимоблокировка, хотя ADR W3 п. 3 обещает её отсутствие. Личная команда сначала берёт блокировку человека `participation:<actor>` (строки 99, 180) или строку `task_personal_state` (`lock`, строка 413). Затем `PrivateLedger.once` вставляет квитанцию (`PrivateLedger.kt:59-73`), и FK `private_receipts.project_id → app.projects` берёт `FOR KEY SHARE` на строку проекта. Общие команды держат эту строку `FOR UPDATE` (`PlanningStates.lock`, `ProjectAccess.projectWriteFence`) и затем ждут личную блокировку того же человека: `Tasks.kt:117` → `Tasks.kt:187` → `joinCreatedTask` (advisory, строка 130), `Planning.kt:503` так же, `AttentionRequests.kt:80` → `AttentionRequests.kt:105` → `startRelation` (`ON CONFLICT DO UPDATE` блокирует личную строку). `FOR KEY SHARE` конфликтует с `FOR UPDATE`, поэтому ожидание получается круговым. PostgreSQL обрывает одну транзакцию с `40P01`, а `ProblemResponses` отдаёт на это `500`. Выключение флага `workbench_personal_state` не помогает: см. F4.
  Сценарий: (а) Алиса в одной вкладке двигает «Участвую»-задачу X проекта P (`PUT …/personal/rank`), а в другой создаёт задачу Y в том же P (или применяет план с новой задачей). (б) Алиса открывает drawer задачи T (`PUT …/personal/seen`) и сразу отправляет по T запрос Борису (`POST …/tasks/T/requests`). В обоих случаях одна из двух команд падает с `500`. Теста на это нет.
  Решение: [fixed c626df5] один порядок блокировок: `PrivateLedger.once` первой берёт строку проекта `FOR KEY SHARE`, затем человек и его строка (ADR W3 п. 3); тест W15 (8 пар «ранг + новая задача» и «seen + запрос» параллельно, все 200).

- **F2** [P2] `products/sprintique/server/src/main/kotlin/com/sprintique/workbench/application/Workbench.kt:500` — В `delegated` фильтры `detail->>'to' IS NOT NULL AND detail->>'to' <> $1` применяются до `ORDER BY … LIMIT 1`. Поэтому берётся не последнее назначение, сделанное человеком (ADR W5 п. 5), а последнее назначение на другого человека. Если человек потом забрал задачу себе или снял исполнителя, эти события пропускаются, и снова находится старое поручение. Та же ошибка в `PersonalState.delegation` (`PersonalState.kt:72`), значит и в проверке `check-back`. Путь «назначил мой агент» (`e.initiator_id = $1`) не покрыт тестом: W12 проверяет только подавление шума.
  Сценарий: Алиса поручает T Борису, потом берёт T себе (событие `owner` с `to=Алиса`), потом Карина передаёт T Денису. У Алисы T стоит в «Жду» с текстом «Поручено: Борис, сейчас исполняет Денис», хотя сама Алиса Борису T больше не поручала. Должно быть обновление «сменился исполнитель». Если Алиса сама сняла исполнителя (`to=null`), T остаётся в «Жду» как «исполнитель снят».
  Решение: [fixed c626df5] берётся последнее событие `owner` самого человека (или его агента) без фильтра по `to`; поручение действует, только если оно ушло другому; то же в `PersonalState.delegation` и в «Плане»; тест W16 (взял себе, снял сам, снял коллега, назначил мой агент).

- **F3** [P2] `products/sprintique/server/src/main/kotlin/com/sprintique/workbench/application/PersonalState.kt:238` — `rankOrder` строит порядок из всех участий в фильтре, в том числе из задач, которые показаны в группах «В работе», «Жду» и «Изменилось». Группа «Участвую» показывает только задачи без более сильной причины (`Workbench.kt:539`, вес 5). Поэтому `up`/`down` меняет порядок относительно невидимых соседей: команда отвечает `200`, ревизия растёт, а видимый порядок не меняется. Тест W06 проверяет только невидимые строки из других проектов (строки 313-314), где такое поведение принято сознательно. Внутри одного проекта из-за автоучастия это обычная ситуация. `RANK_EDGE` тоже считается по невидимому списку. ADR W3 п. 3 и W5 п. 4 обещают перемещение «внутри видимого списка».
  Сценарий: Алиса создаёт A, потом B с исполнителем Борис (B в «Жду»), потом C. Группа «Участвую»: A, C. Первое «вверх» по C ставит C между A и B, и на экране ничего не меняется. Переставляет только второе нажатие.
  Решение: [fixed c626df5] `up/down` считаются по группе «Участвую» ровно как в конверте (`Workbench.joinedOrder`, тот же SQL и фильтр); задача вне группы — `422 RANK_NOT_LISTED`; тест W17.

- **F4** [P2] `products/sprintique/server/src/main/kotlin/com/sprintique/task/application/Tasks.kt:187` — Флаги после смены модели не сходятся с поведением. (а) Автоучастие (`Tasks.kt:187`, `Planning.kt:503`) выполняется при любом значении `workbench_personal_state`. В production при выключенных флагах каждое создание задачи человеком добавляет advisory-блокировку, `count(*)` и две записи в `task_personal_state`. Выключенный флаг не останавливает этот путь и поэтому не работает как откат (ADR W6 п. 7), в том числе для F1. (б) «Жду» теперь выводится из участия: `delegated` читает CTE `participating`, которое пусто без `$4` (`Workbench.kt:492`). Плану `waits` тоже нужно `$4` (`Plan.kt:159`). При `workbench_waiting=on, workbench_personal_state=off` конверт отдаёт `features.waiting=true` (`WorkbenchController.kt:86-90`), «Жду» всегда пусто, а `PUT …/check-back` при этом принимает дату (`PersonalState.kt:381`).
  Сценарий: `SPRINTIQUE_FEATURES=workbench_read_internal,workbench_waiting` показывает включённое «Жду», в котором никогда ничего нет. Откат флага `workbench_personal_state` при инциденте из F1 ничего не меняет.
  Решение: [fixed c626df5] (а) `WorkbenchSwitches` включает автоучастие только при `workbench_personal_state`; (б) «Жду» = `waiting && personal` в конверте, `/personal` и фильтре `check-back`; тест W10 (без автоучастия, `features.waiting=false`, `check-back` 404).

- **F5** [P2] `products/sprintique/server/src/main/kotlin/com/sprintique/workbench/application/PersonalState.kt:153` — Выход из участия сбрасывает `rank`, но оставляет `check_back_at`. ADR W5 п. 8 говорит: «Прекратить контроль = выйти из участия». Старое поручение в журнале событий остаётся навсегда (F2), поэтому при повторном участии старая дата проверки снова действует.
  Сценарий: Алиса поручила T Борису с проверкой 01.10, 02.10 вышла из участия, а в декабре снова нажала «Участвую», чтобы видеть новости. В «Плане → Сегодня» сразу появляется «просрочено: проверить» с датой 01.10 (`Plan.kt:166-170`), и T встаёт в начало «Жду» по старой дате.
  Решение: [fixed c626df5] выход из участия сбрасывает `check_back_at` (ревизия поля растёт); тест W07.

- **F6** [P2] `products/sprintique/server/src/main/kotlin/com/sprintique/workbench/application/Workbench.kt:497` — Для каждой задачи с участием LATERAL в `delegated` идёт по всей истории событий задачи (индекс `task_activity_task`, `V20260929000029__add_task_activity.sql:17`), пока не встретит `owner` от человека. Для задач, которые человек никому не поручал, это полный проход истории. С автоучастием таких задач до 2000 на человека, а конверт клиент опрашивает (ADR W4 п. 7). Тест ёмкости проверяет около 60 участий по 30 событий (`WorkbenchCapacityIntegrationTest.kt:168-208`), то есть не тот режим, на котором строится оценка «запрос ограничен числом отношений».
  Сценарий: человек, создавший 2000 задач с историей по 300 событий, на каждый опрос конверта сканирует около 600 000 строк `task_activity` и приближается к бюджету 5 с. Нужен частичный индекс по событиям `owner` (например `(project_id, task_id, sequence DESC) WHERE kind='owner'`) и тест ёмкости на лимите участий.
  Решение: [fixed c626df5] частичный индекс `task_activity_owner (project_id, task_id, sequence DESC) WHERE kind='owner'`; интеграционный тест на лимите: 2000 участий, 300 000 событий, план использует индекс, конверт < 2 с.

- **F7** [P2] `products/sprintique/server/src/main/kotlin/com/sprintique/workbench/application/Plan.kt:104` — `docs/adr/README.md:16` обещает, что API отдаёт «категорию статуса, даты и причины, достаточные для доски, календаря и списков без лишних запросов». Элемент плана этого не даёт. В нём нет исполнителя, приоритета и причины: почему задача в моём плане (исполнитель, участие, «Жду: Борис», запрос). Элемент `due` не несёт `plannedStart/End`, элемент `planned` не несёт `due`. «Без времени» молча обрезается до 50 (`Plan.kt:84`, `209`) без признака `truncated`. В строке «Сейчас» SQL выбирает `status_entered_at` (`Workbench.kt:577`), но в ответ его не отдаёт, хотя доске нужен возраст стадии.
  Сценарий: карточке календаря «Сделать X, срок сегодня» нужно знать, моя это работа или я жду Бориса. Без второго запроса `/personal` на каждый элемент этого не показать.
  Решение: [fixed c626df5] элемент плана: `relation`, `task.owner/priority/due/plannedStart/plannedEnd`; `summary {itemCount, overdueCount, undatedCount, undatedTruncated}`, `undated=count`; `statusEnteredAt` в строке; тест W09.

- **F12** [P3] `products/sprintique/server/src/main/resources/db/migration/V20260929000028__add_workbench.sql:69` — Остатки после смены модели. `CHECK(participating OR rank IS NULL)` допускает участие без ранга, и тогда `sort_key` получается NULL (`Workbench.kt:597`), а `row.string("sort_key")` роняет весь конверт с `500`.
