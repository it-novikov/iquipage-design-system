# Метод проверки качества IQUIPAGE

## Сначала охват и доказательства
Создать реестр поверхностей: route + overlay/variant + role/permission + platform. Источники: routing, links, modals, menus, feature flags, admin/auth/recovery, empty/error. Сверить с существующими функциями и согласованным scope. У каждой поверхности — owner, главный сценарий, DS composition, нужные состояния и доказательства. Не исключать сложные экраны ради зелёного отчёта.

Значения результатов: PASS, FAIL, BLOCKED, NOT_RUN, NOT_APPLICABLE (с причиной). Скриншот доказывает кадр, а не сохранение. Тест проверяет свои assertions, а не всю функцию. Исходник доказывает наличие кода, а не успешное runtime-поведение. Для прежнего DS-отчёта писать «отчёт поставщика», не «проверено в приложении».

Доказательство содержит build/source fingerprint, точный DS hash, поверхность, шаги, ожидаемое/фактическое, данные, theme/viewport/browser/input, screenshot/trace/log/API state, timestamp. После изменения повторить затронутые проверки на новой сборке. Старые снимки не маркировать новым SHA.

## Слои приёмки
A. Provenance: архив, MANIFEST, единственный vendor boundary, exports/types, реальные imports.
B. Код: data model mapping, controlled lifecycle, cleanup/abort, safe content, permissions, отсутствие обходов DS, правильный ESM split, без demo/runtime смешения.
C. Поведение: happy/empty/loading/error/retry/disabled/readonly/denied/pending/conflict/cancel/undo/reload; вложенные popup/dialog; устаревшие и повторные ответы; IME.
D. Visual: actual render, grid, alignments, density, typography, semantics, consistent emphasis, оба оформления, длинные значения, плохие/отсутствующие изображения, альтернативный шрифт, локализация.
E. Human/agent UX: первый полезный результат, discoverability, обратимость, role clarity, работа без drag, понятные ошибки и подтверждение реального сохранения.
F. Performance: clean install/build, initial JS network, lazy load, own app budget, profiler/frames/long tasks, idle, large realistic data, reduced motion.

## Матрица
Базовые ширины web: 320, 390, 768, 1280, 1440 CSS px, плюс целевые размеры продукта. Рабочая площадь: 1280×720 и 1440×900. Оба оформления; длинное название и переполненные списки; pointer, keyboard, touch. Для web — Chromium, Firefox, WebKit если входят в target; настоящий Safari/устройство учитываются отдельно. Проверить реальный 200% zoom/text sizing, и reflow где применимо при 320 CSS px. CSS zoom/эмуляцию подписывать точно.

Для простых декоративных комбинаций допустимо риск-ориентированное покрытие с объяснением. Для critical paths, связанных состояний hover+selected+focus и known regressions нужны прямые сценарии. Не обещать «все возможные состояния» произвольного приложения. NOT_APPLICABLE требует конкретного контракта, не общей отговорки.

## Измерения и оформление
Текст обычного размера: ориентир WCAG AA 4.5:1; крупный текст 3:1 при реальном достижении порога 18 pt либо 14 pt bold. Не округлять провал в проход. Необходимые иконки и различимость контролов — 3:1 к соседнему фону с учётом применимых исключений. Disabled-контент имеет нормативные исключения, но всё равно оценивается на практическую понятность. Измерять фактическую составную поверхность, не только пару токенов. Градиент, изображение, прозрачность или неизвестный фон → sampled/manual measurement, а не автоматический PASS.

Видимый клавиатурный фокус обязателен; придерживаться поставленного решения DS, не выключать его `outline:none` без замены. Не засчитывать focus мышью за :focus-visible. Target size AA — 24×24 CSS px или допустимые исключения; 44×44 — удобная повышенная цель, не универсальное требование AA. Проверить реальную clickable область, не размер SVG.

Геометрия: общие оси заголовков/данных/действий; равные боковые поля; смысловые расстояния; перенос полных названий; устойчивая ширина статусов; отсутствие orphan-разделителей; 1:1 контейнеры иконок; пустые блоки; крайние значения; нет глобального horizontal overflow. Нельзя фиксированной высотой скрыть текст ради «идеального» снимка.

Реальный рабочий экран должен показывать работу до первой прокрутки в согласованных условиях. Использовать публичный work-layout/density, а не индивидуально уменьшать шрифт. Canvas может иметь внутреннее pan/zoom и текстовую/клавиатурную альтернативу; не требовать у двумерного содержимого невозможной линейной reflow-перекомпоновки.

## Ревью, исправления и выпуск
Каждая подтверждённая находка: ID, P0/P1/P2/P3, поверхность, symptom, причина/гипотеза, источник/строка или selector, доказательство, правило DS, вред человеку/агенту, требуемая переделка, уровень исправления (app-adapter/composition/DS), приёмка и regression test.

P0: потеря/раскрытие данных, опасный несанкционированный эффект. P1: основной путь недоступен, функциональный паритет потерян, существенная недоступность, confirmed bypass DS. P2: заметное нарушение композиции, состояний или удобства. P3: локальный polish без потери действия. Гипотезу не выдавать за подтверждённый баг.

Исполнитель получает findings → исправляет по одному root cause → добавляет проверку → повторяет affected matrix → рецензент закрывает только после новых доказательств. Audit-only не меняет код. Исправлять в review можно только по явному запросу «исправь» или в уже разрешённом цикле implement/review. Пользователь не обязан повторно утверждать каждое безопасное исправление в разрешённом scope.

Готовность не средний балл. Нельзя выпускать как полное внедрение при missing surface, открытом P0/P1, confirmed unapproved bypass, незакрытом обязательном DS-GAP, устаревших доказательствах или непроверенном required target. P2-риск можно принять только явно, с owner/scope/reason; он остаётся виден. Красивый скриншот не компенсирует слабый UX.

Скрипты пакета — помощники. Статический scanner создаёт кандидатов, а не экспертный вердикт; report validator проверяет структуру и ссылки, не истинность assertions; пассивный browser capture не является полным accessibility-аудитом. Не использовать их числа для ложного «всё идеально».

## Дополнение 1.1: границы уровня приёмки
Обязательность конкретных checks фиксируется в независимом acceptance plan до прогона. Полный inventory нельзя подменить перечислением удачных cases. Targeted verdict ограничен выбранным scope; full-integration требует всех согласованных поверхностей. Все dimensions explicit, но неподходящая продукту agent dimension — approved N/A, не придуманный PASS. См. execution-contract.md.

Правка finding не равна закрытию: нужна новая текущая evidence, связанность surface/dimension и reciprocal finding/check IDs. Для неприменимой гипотезы используется investigated dismissal, не фиктивное исправление. Свежие hashes сами по себе не доказывают, что изменения проверены.
