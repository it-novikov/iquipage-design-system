# Полное внедрение IQUIPAGE

## Результат и граница
Пересобери весь согласованный UI на существующей IQUIPAGE, сохранив предметную семантику и функции. Не ограничивайся skinning. Не меняй продуктовые правила и DS без решения владельца. «Все возможности» означает рассмотреть весь каталог и выбрать нужное каждому сценарию, а не показать все компоненты.

Прочитай [конституцию](references/constitution.md), [карту поставки](references/release-map.md) и [протокол пробелов](references/gap-protocol.md). Для сценариев агентов используй [human-agent](references/human-agent.md). Для приёмки — [метод качества](references/quality-method.md). Пути скриптов разрешай от каталога этого SKILL.md, а не от cwd проекта.

## 1. Установи базу до правок
Найди репозиторий, неизменённый DS-архив, одобренный scope/бриф и текущие отчёты через доступные чтение/search. Не проси повторно загрузить то, что можно прочитать. Если нужный источник отсутствует, назови конкретно его и заблокированное действие.

Зафиксируй repo revision + dirty state, текущий стек, целевые платформы, команды сборки, действующую авторизацию. Прочитай инструкции проекта перед запуском его команд. Не меняй несвязанные правки пользователя. Создай migration ledger из `assets/migration-plan.md`.

Проверь пакет без исполнения его кода:
```sh
python3 SKILL_ROOT/scripts/verify_release.py --ds-root PATH_TO_DS --archive PATH_TO_ZIP --out WORK_DIR/ds-verification.json
```
`SKILL_ROOT`, `PATH_TO_DS`, `WORK_DIR` — заполнить установленными путями. Пин 05.7 поставлен в `assets/ds-release-lock.json`; несовпадение нельзя обходить изменением ожидаемого SHA. Новую одобренную поставку сначала исследовать и перепривязать явно. Известное несовпадение version literal в types фиксировать, не молча исправлять.

## 2. Инвентаризируй продукт, не только красивые маршруты
Пройди route tree, auth, navigation, deep links, overlays, feature flags, settings/admin, error/recovery и скрытые действия. Запиши все поверхности в `assets/surface-inventory.csv`: роль, основной объект/задача, текущие функции, states, DS composition, статус миграции/проверки.

Не теряй: создание/редактирование/удаление, вложенность, bulk actions, фильтр/sort/page, импорт/экспорт, сохранённый вид, уведомления, результат агента, обсуждение, права, отмену и reload. Определи обязательные тестовые роли и данные. Не засчитывай неподключённый demo за существующую функцию.

При неясной проблеме запусти `iquipage-discovery`, если он установлен, либо его логику: уточни только блокирующее, подготовь краткий бриф и дождись утверждения. При очевидной корректировке по уже принятому отчёту не начинай опрос заново.

## 3. Спроектируй целевую систему экранов
Определи информационную архитектуру вокруг рабочих объектов, не вокруг структуры API. Для каждого journey опиши: вход → основная работа → проверяемый результат → восстановление. Выдели первичное действие, secondary properties и progressive disclosure. У новичка путь не должен требовать знания runId/внутреннего workflow.

Составь capability map **всех релевантных семейств** из `references/capability-index.json`, проверяя реальные props/events/docs. На каждый фрагмент выбери supplied component, supplied composition или обоснованный adapter. Маркетинговый, ежедневный, пространственный и reading режимы не смешивай.

Покажи до широкого внедрения один вертикальный сценарий на реальных/обезличенных данных: общий shell → список → объект → изменение → сохранение → отказ/отмена, в light/dark и узком виде. Утверди композицию, если она меняется за пределами уже согласованной. Не переименовывай доменные сущности ради валидации DS.

## 4. Останови локальное изобретение компонентов
Для непокрытого сценария создай `assets/ds-gap.md`, приложи точный публичный контракт и минимальное воспроизведение. Сообщи пользователю до реализации обхода. Разрешённую альтернативу запиши с влиянием на функциональный паритет. Не называй весь проект заблокированным, когда пробел локален.

Adapter может связывать state/events/framework lifecycle, нормализовать данные и использовать нативные platform services. Он не может перерисовывать календарь, popup, canvas, error state или кнопку вне supplied pattern. Не использовать private selectors, shadowRoot patches, DOM replacement или !important. Не ставить другую UI-library без запроса.

## 5. Внедряй один общий источник оформления
Подключи единый неизменённый vendor boundary. Используй `core`, а `advanced`/`whiteboard` загружай при открытии соответствующей функции. Full entry допустим только при обоснованном отсутствии lazy budget. CSS и JS одной выдачи; не включай catalog, stories и демонстрационное state в app runtime.

Передавай модели свойствами. В framework adapter подписывайся на public events, снимай слушатели, отменяй pending requests, освобождай URL. Не допускай controlled event loops, поздних accept после cancel и потери разрешённых прикладных полей. Событие intent не равно подтверждённой записи; UI отражает реальный API outcome.

Сначала общий app shell/layout/header/navigation/density, затем все согласованные поверхности через один mapping. Не оставляй старые uncontrolled стили в overlays, auth, settings или mobile. Изменяй business logic только по утверждённой необходимости и с tests. Названия, даты и строки растут по содержимому, не обрезаются для фиктивного равенства.

## 6. Пройди цикл независимого ревью
Запусти `iquipage-review` на всей финальной поверхности/диффе. Если отдельный агент недоступен, проведи явно обозначенный self-review, не выдавай его за независимое. Дополнительно используй `iquipage-experience-audit` для человеческих сценариев, если менялась композиция.

Преобразуй каждую подтверждённую находку в correction task с ID. Исправь root cause, повтори affected cases и соседние контексты. Новый визуальный компонент, обнаруженный при исправлении, снова проходит DS-GAP, а не локальный workaround. Не закрывай defect изменённым ожиданием теста без объяснения изменения контракта.

## 7. Выдай проверенный результат и честные границы
По методу качества: все surfaces/scope, обе темы, нужные роли/permissions, keyboard/touch/zoom, combined states, реальный backend reload, сохранность черновика и прогресс. Сохрани before/after, конкретные измерения и реальные тесты на текущем fingerprint.

Обнови migration ledger, mapping, gap register, adaptation records и handoff. Укажи завершённое, blocked, not run, принятые риски, команды и файлы. Гейт готовности проверяется `iquipage-review`, не количеством DS-imports. Не обещай «полностью внедрено», если хоть обязательная поверхность не пройдена. Не делай push/deploy без отдельного разрешения.

## Выходные документы
`migration-plan.md`, `surface-inventory.csv`, `capability-map.csv`, `gap-register/`, `adaptations/`, `implementation-handoff.md`, assessment/fix ledger от review. Пользователю — итог, реальные пути/архив, открытые блокеры, область тестов. Не изменять сам DS-пакет при установке этого скилла.
