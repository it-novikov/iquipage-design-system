# Протокол отсутствующих возможностей и дефектов

## Диагностика до сообщения пользователю
Проверить последовательно: публичные exports → декларации → документация текущей версии → реальный живой образец → воспроизводимая isolated fixture на точных файлах DS. Поиск одного названия в каталоге недостаточен. Прочитать не только пропсы, но и события, реактивность, readonly/permissions, данные, лимиты, accessibility и отложенное принятие изменений.

Отнести каждый спорный участок к одному виду:

| Вид | Действие |
|---|---|
| `supplied-component` | Использовать существующий публичный компонент. |
| `supplied-composition` | Собрать из поставленных exact markup/slots/helper без нового внешнего языка или механизма. Указать доказательство композиции. |
| `platform-adaptation` | Ограниченный lifecycle/interop/native bridge с сохранением DS-семантики; оформить adaptation record. |
| `application-integration` | Авторизация, API, routing, shared state, persisted preferences, runId; реализовать в приложении, не объявлять пробелом DS. |
| `missing-component` | Настоящего visual/interaction контракта нет; DS-GAP пользователю. |
| `missing-capability` | Компонент есть, но конкретного поведения/типа/состояния нет; запросить минимальное расширение. |
| `ds-defect` | Ошибка воспроизводится без app CSS/React/адаптера на точном пакете; отдельный баг владельцу DS. |
| `unclear-contract` | Документация, декларации и runtime расходятся; не угадывать, запросить уточнение. |

## Обязательная форма DS-GAP
ID; affected requirements/surfaces; priority; user problem; exact DS package/version/archive SHA; searched symbols/files/lines; ближайший поддерживаемый путь; конкретное отсутствующее свойство/состояние; минимальный ожидаемый контракт (как предложение, не существующий API); acceptance cases; влияние на функциональный паритет; безопасная временная альтернатива; решение владельца и дата.

Сообщение пользователю короткое и предметное:
«Для [сценария] в принятой [поставка] не найден [конкретный контракт]. Проверены [источники]. Ближайший [паттерн] не сохраняет [обязательная возможность]. Локальную замену не добавляю. Предлагаю [расширение DS] либо [согласуемое ограничение/альтернатива]. Затронуты [экраны]; остальное продолжается.»

Пользователь должен явно выбрать: расширить DS отдельной задачей; отложить эту возможность без объявления полной миграции; принять перечисленную семантически корректную альтернативу; одобрить bounded platform adaptation. Согласование всего redesign не равно разрешению создавать missing components.

## Расширение после согласования
Отдельная ветка/задача DS → общий API → оба оформления и состояния → изолированные тесты → документы/типы → новый пакет/хеш → повторная приёмка в приложении. Нельзя объявить локальную реализацию частью DS задним числом или положить её в `shared/` ради формального прохождения проверки.

## Не допускать ложных блокеров
- `iq-plan` — срок; `iq-roadmap` — интервал. Это разные цели, не взаимозаменяемые имена.
- `iq-whiteboard` — свободные objects/connections; `iq-graph` — nodes/edges структурированного процесса. Не копировать одну модель в другую без явного domain mapping.
- Отсутствие готового React-wrapper — задача interop, если публичный Web API покрывает потребность. Самодельный React-календарь вместо `iq-date-field` — не interop.
- Сохранение формы по backend API, роли и tenant boundary — ответственность приложения. Вычисленный архивный кластер не равен обычной визуальной группе.
- Нельзя заменить необходимый пространственный сценарий таблицей и назвать это паритетом без согласования; доступная текстовая альтернатива дополняет основной сценарий.
- Не объявлять весь assignee picker отсутствующим, если задача покрывается поставленной композицией dialog + search + list. Но не называть её remote-combobox без нужных событий и состояний.
