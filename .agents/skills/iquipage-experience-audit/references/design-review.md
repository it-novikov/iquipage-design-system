# Проверка концепции: измерения и профессиональная оценка отдельно

Это рубрика применения принятой IQUIPAGE, не новая палитра и не универсальная численная оценка «премиальности». По каждому применимому пункту сохранить кадр, наблюдение, вред, конкретное решение, публичную композицию DS и acceptance. Недоступный рендер — NOT_RUN. Ни сумма баллов, ни корректные импорты не закрывают эти вопросы.

| Линза | Что наблюдать | Пример требуемой переделки |
|---|---|---|
| Рабочий объект | Что получает первый взгляд; где действие и результат | Объединить служебные ряды в `iq-work-layout`; свойства рядом, не вместо документа |
| Сетка и ритм | Общие оси, смысловые интервалы, внутренние отступы, вложенные scrollers | Использовать public density/slots; убрать дублирующие toolbar, не уменьшать локально шрифт |
| Типографика | Иерархия, длина строк, полные названия, шрифтовый fallback | Обеспечить перенос и правильный уровень heading, а не ellipsis ради красивого скрина |
| Семантический акцент | Ошибка/warning/статус/приоритет, обычные строки нейтральны | Применить supplied taskEmphasis; не суммировать все цветовые сигналы |
| Различимость | Комбинации selected + hover + focus-visible, disabled отдельно | Измерить составную пару после анимации; зафиксировать engine/input |
| Работа с формой | Сохранность, IME, ошибки по месту, cancel/retry, no fake saved | Проверить реальное API подтверждение и reload, не только тост |
| Пространственный UX | Понятен ли вопрос доски, доступно ли без drag, ясна ли связь | Не подменять brainstorming редактором процесса; использовать whiteboard/graph по назначению |
| Голос и помощь | Человеческие термины и действие, не runId в главном потоке | «Что исправить и что сохранилось» вместо общей ошибки |
| Человек и агент | Мандат, исполнитель, результат, принятие, сохранение | Развести состояния и опасные эффекты, не создавать новую agent-фичу без scope |
| Движение и качество | Причинность, отменяемость, idle, reduced motion, читабельные материалы | Обосновать эффект задачей; не обещать FPS по JS-duration |

## Как не согласовать слабый дизайн формально
Сравнивать before/target на одинаковых реалистичных данных, теме и размере, включая длинное название и отказ. В отчёте отделять **нарушение принятого контракта**, **наблюдаемый барьер** и **эстетическую гипотезу**. Для спорного направления показывать две альтернативы только если это решение действительно нужно; не перепроектировать уже утверждённую поверхность из-за вкуса рецензента.

Для полного внедрения нужен отдельный visual/UX вывод по каждой изменённой композиции: чему служит каждый контейнер, почему понятен следующий шаг и что доказано просмотром. Скрипт геометрии не видит всю смысловую иерархию. Структурный gate требует ссылки на реальное visual evidence, но не умеет сам оценить композицию.
