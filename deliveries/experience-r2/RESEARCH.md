## 2. Внешние источники: что берём, чего не копируем
Ссылки фиксируют чтение документации, не выбранный платный стек. Совместимость с конкретным агентом требует отдельной contract-проверки и разрешения подключения.
| ID / первичный источник | Что источник действительно поддерживает | Вывод для Sprintique, не свойство источника |
|---|---|---|
| S01 [Linear Display options](https://linear.app/docs/display-options) | Группировка, сортировка, свойства отображения и фильтры имеют разные функции; заголовки групп закрепляются | Не смешивать «Вид» и «Фильтры»; не копировать весь перечень полей |
| S02 [Jira bulk backlog actions](https://support.atlassian.com/jira-software-cloud/docs/edit-multiple-issues-at-once-from-the-backlog/) | Несколько выбранных задач можно менять/перемещать контекстно; доступность зависит от операции и прав | Массовые действия появляются после выбора; Jira-лимиты не становятся нашими продуктовыми лимитами |
| S03 [Miro board search](https://help.miro.com/hc/en-us/articles/360018109534-Searching-text-on-the-board) | Поиск даёт список объектов, подсветку и переход к конкретному объекту; результаты фильтруются | Явный поиск карты важнее добавления ещё одной AI-панели; не копируем скрытое расположение входа |
| S04 [NN/g Progressive disclosure](https://www.nngroup.com/articles/progressive-disclosure/) | Частые функции должны оставаться на первом уровне, переход к редким — быть очевидным | Простота — не сокрытие всего в троеточии; ежедневные действия и acceptance видны |
| S05 [Linear Agents](https://linear.app/developers/agents) | Delegation агенту отделена от человеческого assignee; доступ управляется scopes | Разделить исполнителя поручения и ответственность за задачу; это не предписание всех правил полномочий Sprintique |
| S06 [Linear agent interaction](https://linear.app/developers/agent-interaction) | AgentSession и активности делают видимыми работу, ожидание входа, завершение и внешние артефакты | Отдельное состояние запуска рядом с задачей; не помещать полный технический журнал на карточку |
| S07 [GitHub review agent output](https://docs.github.com/en/copilot/how-tos/copilot-on-github/use-copilot-agents/review-copilot-output) | Результат coding agent требует проверки; workflow и ревью — отдельные операции | PR/diff и проверки должны быть артефактами принятия, не самоотчётом «готово» |
| S08 [GitLab Flows](https://docs.gitlab.com/user/duo_agent_platform/flows/) | Flow объединяет одного/нескольких агентов; есть готовые и настраиваемые процессы, execution и sessions | Полезны предметные сценарии разработки и разделение настройки/исполнения; CI остаётся внешним исполнителем |
| S09 [GitLab composite identity](https://docs.gitlab.com/user/duo_agent_platform/composite_identity/) | Разделяются человеческий инициатор и service account, права не расширяются объединением identity | Мандат и авторство важнее общей аватарки «AI»; не переносить специфический GitLab token protocol |
| S10 [Anthropic Building effective agents](https://www.anthropic.com/engineering/building-effective-agents) | Рекомендуется простейшее достаточное решение; workflows и автономные агенты различаются; сложность имеет цену | Не использовать модель для детерминированных переходов; дополнительные шаги требуют измеримой пользы. Статья датирована 2024 и сама предупреждает об изменении tooling |
| S11 [Claude Code agent teams](https://code.claude.com/docs/en/agent-teams) | Команды полезны для независимой работы, несут расходы координации/токенов; same-file работа хуже параллелизуется | Default — не «десять агентов на всё»; отдельные области изменений и осознанный параллелизм |
| S12 [OpenAI scheduled tasks](https://developers.openai.com/codex/app/automations/) | На дату чтения URL перенаправляет на официальную страницу Scheduled tasks: отдельные настройка/запуски, проверка промпта, scope доступа | Не ссылаться на прежнюю страницу как на неизменённый API Codex; важны ручная проверка до расписания и разделение процесса/запуска |
| S13 [W3C dragging movements](https://www.w3.org/WAI/WCAG22/Understanding/dragging-movements.html) | Для dragging нужна альтернатива одиночным указателем; только keyboard parity её не заменяет | Перенос/порядок/связи доступны также через кнопки и поиск |
| S14 [Chrome rendering performance](https://web.dev/articles/rendering-performance) | Frame budget зависит от частоты дисплея; layout/paint/composite имеют разную стоимость | Мерить кадры на целевых устройствах, не обещать 120 FPS по headless-тесту |

Запрошенная граница «не превращаться в n8n» является требованием пользователя. Попытка открыть текущую основную workflow-страницу n8n дала Page Not Found; отдельный mirror не использован как источник продукта. Специфические возможности/ограничения текущего n8n этим пакетом не утверждаются.

## 3. Прилагаемые материалы и изменения относительно прежнего плана
Архитектура vNext (Proposed r1) задаёт новую платформу, самостоятельную DS, actor/mandate/proposal/approval, разделение execution/result/persistence, общий policy и отсутствие paid/MCP runtime по умолчанию. UX R2 сохраняет эти границы. Последняя просьба пользователя пересматривает одобрение старой композиции фронта, но не разрешает стирать функции, менять стек и повышать полномочия агентов.
HTML-поставка IQUIPAGE подтверждает motion 120/180/280/360 ms, шкалу отступов 4/8/12/16/24 px, compact row 56 px, рабочие header/navigation/whiteboard/roadmap/editor primitives. Это входные токены и компоненты, не доказательство удобства их текущей композиции. Два приложенных HTML — образцы библиотеки, не новое production-приложение.

## 4. Неизвестное и необходимая проверка
Не проведены пользовательские интервью, независимое агентное ревью, запись реального пути карты, тест нового host login/logout и замеры нового макета. Предлагаемые цели плотности/времени выполнения — гипотезы для приёмки. Следующий этап должен проверять не только «кнопка сработала», но и то, что человек без подсказки нашёл действие, понял последствия и вернулся к работе без потери данных.
