# Агент — полноценный участник Sprintique

## 1. Зачем человеку это нужно
Базовый эпизод: основатель описывает исправление, выбирает знакомого исполнителя, занимается другой работой и возвращается к проверяемому результату в той же задаче. Сегодня он переносит контекст в чат, объясняет роль заново, запускает инструменты отдельно, затем вручную возвращает артефакты и статусы. Автономные графы сами по себе этот разрыв не решают.
Другие эпизоды: QA получает конкретный PR и готовит проверяемые тесты; аналитик разбирает прикреплённую обратную связь с источниками; технический писатель обновляет документацию по принятому diff. Универсальная «команда агентов» для каждой мелкой задачи — не цель. Применимость каждого эпизода требует пилота, не подтверждена интервью в этой сессии.

## 2. Модель участника и ответственности
Создание: `Команда → Добавить участника → Агент`. Имя, роль, зона ответственности и разрешённые проекты. В одном списке с людьми, всегда с отметкой «Агент» и состоянием подключения. Может быть основным assigneeId задачи, автором сообщений и изменений, участником проверки. Не требуем скрытого человеческого assignee у каждой его задачи; это отличается от Linear delegate-only.
Agent principal получает собственный неизменяемый ID. Переименование, смена модели или подключённого runner не меняют автора старых задач. Шаблон роли не является участником; его применение создаёт отдельный профиль. Копирование профиля не копирует доступ, секреты и частную память. Агент по умолчанию ограничен одним пространством; членство в проектах явно выдаётся.
У профиля есть администратор/спонсор, который отвечает за конфигурацию, доступ, оплату и отзыв. У исполнения отдельно записаны initiator, actor и approver. Полноценное участие не означает право самому выдать себе полномочия, принять собственное повышение прав или скрыться под именем человека.
`Роль`: назначение, обязанности, стандарт качества, типы результатов, границы. `Личность` — необязательный стиль общения, язык и подробность. Не выдаёт доступ, не ослабляет проверки и не предлагает модели выдумывать чувства/биографию. Отдельно видны реальные инструменты и возможности исполнения.
Профиль: **Обязанности / Контекст / Доступ и инструменты / Работа / Настройки**. Для первых трёх разделов хорошие defaults; модель, инструкция, параметры, параллельность и лимиты раскрываются при необходимости. Карточка показывает назначенные задачи, ожидаемые ответы, доступность и последнюю успешную работу, а не бесконечную анимацию «думает».

## 3. Собственный контекст — не бесконечный чат
Слои: правила платформы и доступа → профиль/роль → разрешённый контекст проекта → задача, её файлы, принятые решения и выбранные ссылки → рабочая история текущего запуска. Задачи других проектов не добавляются потому, что участник знаком с пространством.
Постоянная память — управляемые записи с sourceRef, revision, scope, автором, сроком/состоянием и возможностью исправить/забыть. Пример: «В проекте используем Kotlin Coroutines; решение в задаче SPR-18». Предложение агента сохранить новую норму требует принятия; очередное сообщение не становится системной инструкцией автоматически.
Контекст собирается сервером по доступу, актуальности и бюджету. Manifest содержит источники и версии, объём/исключения. Пользователь может увидеть «Что знает агент», исправить устаревшее и исключить материал. Полный архив переписки не посылается на каждый вызов. Поиск и выборка без LLM, summary только при полезной экономии. Кэш привязан к scope, provider, модели, версии policy и источников; отзыв доступа инвалидирует его.
Память отдельной задачи и глобальные нормы проекта не смешиваются. Новая задача не наследует приватный разговор прошлого заказчика. Смена модели не переносит raw reasoning или скрытый chain-of-thought; переносим подтверждённые факты, исходные данные и краткие рабочие резюме. Срок хранения, экспорт и удаление задаются владельцем пространства.

## 4. От модели к действию: конкретная обвязка
**Модель** генерирует текст и запросы инструментов; сама по себе не является автономным разработчиком. **Execution profile** определяет loop, инструменты, окружение и форматы результата. **Run** выполняет конкретное поручение. UI отделяет эти понятия, не выдавая выбор имени LLM за подключённую рабочую среду.
Первый управляемый путь: backend worker → проверка principal/mandate/revision → резерв бюджета → разрешённый context manifest → provider adapter → ограниченный tool loop → проверенные артефакты/proposal → task thread и приёмка. Секреты только через серверный secret reference; браузер получает возможности и состояние, не API key.
Для кода требуется изолированный runner: отдельный checkout/worktree задачи, CPU/memory/time/network quota, scoped repo token, git diff, тесты/linters, сборка и создание draft PR. Контейнер без ограничений сети/секретов не считается sandbox. Обычный LLM endpoint без shell/git не рекламируется как исполнитель разработки.
Второй путь: подключённый внешний coding agent возвращает подписанные события/артефакты через adapter. Ему выдаётся узкий временный мандат и минимальный контекст. Нельзя обещать одинаковые функции всем внешним исполнителям: capabilities обнаруживаются и проверяются при подключении.

## 5. Подключения, модели и оплата
Первое предлагаемое подключение для пилота — серверный OpenAI Responses + Agents SDK для управляемого loop, либо отдельный Claude Agent SDK runner для coding-ролей. Это альтернативные адаптеры, а не обязательная связка двух SDK. Последовательный pilot сначала принимает один provider; выбор конкретной модели и версии делается по evals задач, а не жёстко прошивается в карточку роли.
Администратор один раз создаёт подключение в пространстве: provider, secret reference, разрешённые модели/регионы/инструменты, счёт/лимиты, политика хранения и доступные проекты. Затем агент выбирает это подключение; пользователь задачи не вставляет ключ. Возможен BYOK; оплата через платформу — отдельный коммерческий профиль после согласования, не скрытая перепродажа API. Подписка на чат не считается API-квотой.
ModelConnection и ExecutionProfile разные: API-модель + безопасные task tools подходит аналитику, а разработчику нужны repo/runner/checks. UI показывает «Не подключён», «Нужен доступ к репозиторию», «Готов», «Приостановлен», «Лимит исчерпан» по подтверждённым capabilities, не фальшивое присутствие online.
Провайдерные адаптеры нормализуют запрос, usage, tool proposals, cancellation capability и ошибки. Не обещаем полную взаимозаменяемость tool calling/контекстного окна/JSON mode. Fallback на другую модель или регион — только по разрешённому правилу; секреты и исходники не пересылаются новому провайдеру молча.
Обёртка хранит checkpoint текущего запуска, pending tool calls, task revision, профиль/модель version и журнал результатов. Durable-очередь принадлежит worker. SDK Session — техническая история беседы; доменная память участника, полномочия и долговременная очередь не делегируются памяти процесса SDK.

## 6. Назначение не должно неожиданно тратить деньги
По умолчанию назначить на агента означает положить в его очередь. Кнопка «Начать» показывает результат, разрешённый контекст и лимит; черновик не запускается. У роли можно явно включить «Начинать подготовленные задачи автоматически», выбрать проекты, бюджет и предел одновременных задач. У каждой задачи видно, включено ли это правило. Импорт, перетаскивание фигуры и простой mention не запускают LLM.
В работе отображаются реальный шаг, вопрос, ограничения и артефакты. Если нужен ответ, агент создаёт обычный тред «Требует решения» в задаче и ждёт; ответ владельца продолжает тот же run по конкретной версии, без нового бессвязного чата. Пустое назначение без подключённого исполнителя не имитирует выполнение.
Reassign при текущем run останавливает новые эффекты прежнего исполнителя, уточняет уже начатые внешние операции и сохраняет их авторство; только затем новый участник принимает работу. Удаление/пауза профиля не стирает историю, файлы и комментарии. Сервер проверяет отзыв перед каждым effect, а не только в момент старта.
Статусы run: в очереди, выполняется, нужен ответ, ожидает проверку, останавливается, остановлен, ошибка, завершён. Статусы workflow задачи остаются прежними: завершённый run с предложенным PR не означает «Готово к релизу». Принятие результата/merge/deploy — независимые разрешённые решения.

## 7. Конкретные полезные кейсы
| Эпизод | Участник и вход | Проверяемый выход | Следующий шаг / отказ |
|---|---|---|---|
| Исправить сортировку списка | Агент-разработчик; задача, выбранный repo, base SHA, критерии, рамки изменения | Ветка/PR, diff, команды и результаты тестов, ограничения | Человек принимает конкретный diff; если проблема не воспроизводится — вопрос в той же задаче |
| Подготовить тесты новой формы | QA-агент; задача, принятые критерии, PR/preview, тестовый контекст | Добавленные тесты и сценарии, успешные/непройденные проверки с воспроизведением | Failed CI не исправляется словами; на реальные touch/screen-reader проверки ставится задача человеку |
| Разобрать отзывы | Агент-аналитик; только разрешённые вложения задачи, период и вопрос | Группы проблем с точными ссылками на источники, предложения задач без автоматического создания | Человек принимает/исправляет набор; неизвестные факты помечены, не додуманы |
| Обновить документацию после merge | Агент-документатор; подтверждённый SHA и связанные решения | Изменения документации, примеры, список непроверенного | Нет права менять продуктовый код/публиковать сайт, если это не выдано отдельно |
| Отредактировать план релиза | Агент-планировщик; scoped состав/зависимости и цель | Предложение последовательности с последствиями по задачам и срокам | Владелец утверждает active-scope changes, агент не раздаёт мандаты другим агентам самостоятельно |

Первый pilot — один разработчик и один человек-reviewer. Второй агент нужен только после сравнения качества/цены с простыми CI-проверками. Независимые параллельные подзадачи получают разные workspace/ветки, общий бюджет и явную точку сборки. Неограниченных циклов self-review/self-retry нет.

## 8. Деньги, безопасность и надёжность
Квоты по пространству, участнику и запуску; отдельный лимит concurrency и tool/runtime cost. До вызова резервируем верхнюю оценку там, где контракт провайдера позволяет её вычислить; фиксируем фактическое usage после ответа. Цена модели, токены, runner и внешний агент могут выставлять разные счета. Неизвестное usage — неизвестно, не ноль. Лимит приложения без провайдерной гарантии не называется абсолютным потолком уже запущенного запроса.
Ожидание человека не держит дорогой цикл polling модели. Детерминированные фильтры, подсчёты, HTTP/webhook обработка, сортировка и цикл расписания не используют LLM. Уже принятый результат не пересчитывается при открытии карточки. Дополнительная роль/модель запускается за понятную новую ценность, а не для анимации «команда работает».
Мандат ограничен операциями/ресурсами/TTL/версией. Текст задачи, комментарий, файлы, найденная web-страница и output другого агента — недоверенные данные; не меняют инструменты, доступ, бюджет и список endpoints. Артефакты сохраняются как task attachments/proposals с provenance, не выполняются в браузере.
Callback внешнего агента проверяется и привязывается к run/task/base revision. Lease предотвращает конкурирующее подтверждение одного запуска. Потеря ответа приводит к reconciliation; слепой retry внешнего создания PR запрещён без idempotency контракта. Автоматизация GitHub/GitLab использует provider delivery ID, конкретные repo/branch/SHA; новый commit делает старую проверку неприменимой. Несколько MR у задачи учитываются явно.
Сопоставление person/agent сохраняется в audit: agent principal, инициатор, спонсор, мандат, версия инструкции/контекста/модели, использованные источники, результат и approver. Храним краткое основание и действия, не приватные цепочки рассуждений модели. Сырые секреты, provider session tokens и чужой контекст в логи не включаются.

## 9. Вход, повторное использование и привычка
Первый успешный опыт: добавить готовую роль → подключить разрешённый исполнитель → назначить одну ограниченную задачу → увидеть PR/тесты/вопрос → принять результат в знакомом документе. Большую форму инструкций/граф запрещено делать обязательной первой ступенью.
Повторный опыт: контекст и нормы уже известны, роль и качество предсказуемы, артефакты и решения находятся в задаче, назначение занимает столько же действий, сколько человеку. Это проверяемая гипотеза полезности, не обещание удержания.
Измерения pilot: время до первого принятого результата, доля задач без переноса контекста в сторонний чат, число уточнений, отклонения/переделки, цена принятого результата, доля добровольных повторных назначений, инциденты неверных прав и необходимость ручного восстановления. Не оптимизируем сообщения/агентные вызовы/время в приложении сами по себе.
Экспорт задач, профиля и принятой памяти должен оставаться возможным. Полезная привычка строится на сокращении работы, не на невозможности забрать собственные данные. Ошибка агента видна и исправима; false success разрушает этот сценарий.

## 10. Контракт для backend-агента
Одна каноническая модель Principal/Membership/Grant из vNext. Добавить AgentProfile (роль, версия, стиль, источники контекста, execution connection reference), назначение task.assigneeId и run/session projection. Не делать второй Users/Agents каталог с независимыми правами.
Команды с revision и idempotency: создать/изменить/приостановить профиль; назначить задачу; подготовить и начать run; ответить на вопрос; остановить; проверить/принять/отклонить proposal; предложить/принять/забыть запись памяти. Конкретные URL и SDK operation IDs определяет backend, UI не выдумывает universal PUT.
Первый end-to-end gate: principal agent реально назначен на задачу, читает только разрешённые источники, запускает один ограниченный runner, возвращает PR/артефакт, человек принимает именно эту версию; чужой tenant, отзыв и повтор после потери ACK не создают эффектов. До этого профиль UI — конфигурационный consumer, а не функционирующая агентская команда.
Непроверенные вопросы для pilot: какой провайдер/регион допустим, кто оплачивает API, хранение исходников/контекста у провайдера, политика инструментов/сети runner, sandbox host, SLA, минимальные eval tasks и роль первого исполнителя. Эти настройки не подставляются случайно из профиля пользователя или его наличных ключей.
