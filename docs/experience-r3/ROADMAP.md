# Дальний горизонт: нужен ли отдельный roadmap?

## Проблема и границы знания
Запрос владельца — Q1–Q4 и стратегическое планирование. Подтверждённой аналитики поведения клиентов нет. Рассматриваем три задачи: основателю понять очередность крупных результатов; руководителю согласовать несколько проектов; исполнителю/агенту увидеть, зачем нужна текущая задача. Сам календарь с сотней тысяч карточек этого не решает.
Для человека с одним коротким релизом глобальный roadmap не нужен. Для 3–5 направлений полезен обзор, но не новая обязательная методология. Поэтому используем progressive disclosure: тот же раздел Планирования на уровне пространства, а не глобальную четвёртую вкладку для всех проектов.

## Рекомендуемая первая версия
В переключателе контекста: `Пространство → Все проекты → Планирование → Сроки`. Это явный scope внутри одного tenant. Внутри одного проекта остаётся его обычное Планирование. Переход не объединяет права пространств и не разрешает перенос между ними.
Представления Сроков — Гант и Календарь. У Ганта отдельная настройка масштаба: неделя / месяц / кварталы / год. Q1–Q4 — деления оси времени, не спринты, релизы или самостоятельные контейнеры задач. По умолчанию годовой обзор показывает релизы; раскрытие добавляет эпики, ещё одно — задачи. Выделение сохраняет один ID при смене масштаба.
`План 2027` — сохранённый вид: название, описание решения, разрешённый набор проектов, фильтр, группировка, уровень и горизонт. Не копия релизов, задач и дедлайнов. Смена названия вида не переименовывает работу. Сохранение вида не запускает работу. Текстовое описание можно открыть рядом с планом, не возвращая раздел «Материалы».
Типовой путь: выбрать Все проекты → открыть Сроки → Кварталы → оставить 3 проекта → сохранить как «План 2027». Для проекта без нескольких направлений эти настройки не появляются обязательным onboarding.

## Какие данные показывать
Полоса релиза показывает ожидаемый результат, проект, владельца и период. Точный статус/состав открываются в том же релизе. У задачи один документ; у релиза один состав. Релиз, пересекающий два квартала, рисуется одной полосой, а не двумя учитываемыми копиями. Задача, связанная с несколькими стратегическими обсуждениями, не дублирует объём работы.
Отдельное событие на день отображается маркером и называется его содержимым, например «Закрытая бета». Команда создания — «Отметить событие». Срок/дедлайн задачи остаётся полем задачи. Событие не автоматически завершает задачу и не означает деплой.
Неполные данные не маскируются. `Без периода` — доступная секция, `Нужна оценка` — явное состояние. Завершение 10 из 20 задач не доказывает достижение бизнес-цели; процент работ и фактический результат не смешиваются.

## Точность и изменение планов
Если команда знает только «во втором квартале», нельзя записать фиктивное обещание 30 июня. Потребительский контракт должен передавать precision (`day`, `month`, `quarter`, `unscheduled`) и значение периода отдельно от обязательного дедлайна. Сетка может вычислить границы для рисования, но эти границы не становятся каноническими датами.
Точный интервал — существующие start/end. Пока они заданы, квартальная группировка является только представлением. Для приблизительного назначения нужен согласованный backend-контракт coarsePeriod; до его появления UI не предлагает ложную возможность редактирования квартала.
Перенос Q1→Q2 меняет только плановый период выбранного объекта, после явного предпросмотра. Даты задач и обязательства не сдвигаются. Для активного релиза действует тот же контроль изменений. Менять zoom — без записи, двигать полосу — команда; отмена не создаёт событий.
Финансовый год — настройка пространства. Подписи FY/Q1 и календарный год различаются; startMonth и timeZone читаются из проекта/пространства, не угадываются по языку браузера.

## Когда действительно понадобится «Цель»
Не вводим сейчас Portfolio/Initiative/Objective/Theme ради сходства с enterprise-трекером. Проверим отдельную проблему: команда должна хранить бизнес-результат с метрикой и владельцем до появления релизов, связывать несколько проектов с одной целью, пересматривать гипотезы и историю оценки. Если этот сценарий подтверждается, одна сущность «Цель» оправдана и НЕ должна притворяться эпиком без задач.
До этого — описание сохранённого плана и ссылки на существующие эпики/релизы. Это позволяет видеть стратегию, не обещая полноценное управление OKR. Нельзя утверждать, что saved view заменяет измеримую бизнес-цель.

## Агенты в общем плане
Агент читает ту же разрешённую проекцию: цель текста, этап, связанные релизы, зависимости, ограничения, автор и revision. Он может предложить иной порядок или выявить конфликт, но не меняет квартал/дедлайн массово из одного текстового ответа. Предложение содержит причины, ссылки и список изменений; принятие через общий command/approval. Простая выборка, подсчёт и проверка циклов выполняются без LLM.
Квартальный обзор не загружает все тексты/файлы/треды. Нужен отдельный агрегированный запрос SDK с уровнем детализации, cursor и scope; раскрытие запрашивает детей. Оконный UI не заменяет серверные пределы ответа. Счётчики не раскрывают недоступные проекты. Отзыв доступа удаляет элементы и результаты поиска, а не оставляет их в клиентском кэше.

## Проверка потребности до расширения
Пять предложенных заданий для исследования, ещё NOT_RUN: распланировать запуск трёх продуктов на год; объяснить, почему задача входит в текущий релиз; перенести только неопределённое направление на квартал; найти зависимость, угрожающую выпуску; согласовать план без раскрытия чужого приватного проекта. После каждого задания проверяем понимание обещанной даты и отличие цели от объёма работ.
Сравнить вариант только на релизах с вариантом, где есть отдельные цели, на одинаковых данных. Отдельную цель добавлять при повторяющемся незакрытом сценарии, а не по эстетическому предпочтению. Не заявляем исследований пользователей по результатам этой экспертной гипотезы.

## Техническая передача
Backend-владелец согласует saved views, permission-filtered multi-project projection, date precision и ссылки. DS-владелец — публичный quarter/year scale и текстовые labels для событий. Текущий `IqRoadmap.scale` поддерживает fit/day/week/month: поддержка quarters не подтверждена и не будет имитироваться приватными DOM-патчами. До расширения DS годовой диапазон допускается только в существующем scale; это не готовый квартальный UX.
Приёмка: один ID во всех видах, видимые границы прав, сохранённые фильтры, нет выдуманных точных дат, отрицательные/нулевые интервалы проверены, DST/leap/year-boundary, 200 групп и раскрытие без полного скачивания, конфликт/отмена/undo и совместная проверка с новым backend. Многопроектное изменение должно перечислять изменяемые проекты и не выполнять частичный перенос под видом полного успеха.
