# Sprintique Board — план B1–B5
Статус: реализация разрешена пользователем 10.09.2026. Заменяет прежний предварительный план. База main 67cd26b: PR Maps R4 уже объединён владельцем. Работа — feature/board-production; main и исходная DS не меняются.

## Обязательные исключения
Нет WIP-лимитов и предупреждений о переполнении, общего количества задач, агрегатов колонок, сворачивания колонок, собственного вертикального скролла каждой колонки, Comfortable и массовых действий на доске. Бэклог — отдельное будущее ТЗ. Нет раздела «Материалы» и типов «идея», «исследование», «действие», «согласование», «материал», «рефакторинг». Отсутствие лимита задач не означает загрузку всей БД/всех DOM-узлов одновременно.

## Навигация
Основные разделы: Доска задач, Карты. Настройки проекта/пространства — подписанная кнопка возле профиля. Автоматизация и интеграции — в настройках проекта с контекстным входом из доски/карты, не основной раздел. Логотип Sprintique: авторизован → доска; гость → landing. Стенд может явно мокировать landing/auth, но не выдаёт это за серверную защиту. Прямые ссылки, Back/Forward, смена проекта, выход защищают черновики и сохраняют фильтры/прокрутку.

## Доска и карточки
Один scroll root по двум осям, полноширинная поверхность с отступами DS 24/16px, шесть закреплённых заголовков. Содержимое колонок растёт, карточки не сжимаются по высоте. Счётчик колонки считает уникальные задачи своего статуса, в том числе свёрнутые дочерние; при фильтре — найдено/всего этой колонки. Готово к релизу НЕ означает опубликовано: релиз/закрытие — отдельный lifecycle, не неявная седьмая колонка.
Compact-карточка: короткий ID/тип, заголовок, нужные теги/релиз/срок и исполнитель. Источника нет ни здесь, ни в документе задачи. Critical/high используют taskEmphasis и семантические роли DS. Epic имеет отдельную типовую фиолетовую метку, не второй конкурирующий сигнал срочности. У родителя — уникальные исполнители детей: три аватара + N по примеру «Выпуск 2.4». Пустая колонка — уменьшенная композиция file-empty DS, короткая фраза без инструкции.

## Типы, дерево и связи
Канонические типы task/bug/epic. Подзадача — роль связи parentId, не отдельная сущность/таблица. Родитель назначается, меняется и снимается в «Связях» без смены ID, потери файлов, тредов, истории и текста. Один родитель, без циклов и чужих/недоступных задач. Смена типа не удаляет связи; перенос родителя не переносит детей. Незавершённые дети проверяются только явно настроенными правилами, не скрытым каскадом.
Одна задача имеет одно каноническое место в колонке своего статуса. Дети того же статуса раскрываются под родителем с направляющей; дети других статусов остаются в своих колонках. Под родителем ссылка «В других столбцах: N», не копии draggable-карточек. Совпавший с фильтром ребёнок не исчезает из-за родителя; контекст родителя не увеличивает счётчик. Раскрытие сохраняется персонально. Глубокое дерево ограничивает визуальный отступ, не количество задач. Перетаскивание никогда не меняет родителя.
Три пользовательских смысла связи: «В составе» (родитель), «Зависит от» (направленное ребро), «Связана с» (симметричное ребро). Обратные подписи вычисляются. Дубликат — отдельное действие разрешения задачи. Граф, права и версии проверяются на сервере в транзакции. Task общий для Board, Maps, будущего Backlog и автоматизации; представления не создают свои копии задач.

## Порядок и перемещение
По умолчанию «По приоритету»: critical/high/normal/low, затем время ожидания в статусе, затем стабильный ID. Дополнительно срок (пустые в конце), дата создания и явная ручная очередь. В автоматической сортировке drop меняет статус, положение вычисляется тем же компаратором; внутри колонки нет ложного обещания свободного reorder. В ручном режиме rank относится к доске/статусу, не индексу отфильтрованного DOM. Изменить приоритет можно только явной командой. Уведомление после перемещения объясняет исчезновение из активного фильтра.
Состояния: idle → armed → dragging → allowed/denied → saving → accepted/rejected/conflict. Escape, pointercancel, drop снаружи, потеря страницы и прав не записывают статус. Клавиатура и меню перемещения равноправны мыши. Заголовки — доступные drop-target; общий auto-scroll. Optimistic feedback не равен сохранению; отказ восстанавливает именно затронутую задачу, не чужие изменения. События автоматизации возникают только после commit, не на dragover. Во время drag удалённые изменения буферизуются с проверкой revision перед записью.

## Документ задачи
Панель и полный экран разделяют один документ/редактор. Markdown — публичный DS editor: превью, явное редактирование, Cmd/Ctrl+Enter сохранить, Escape отменить с защитой черновика. Ссылки не включают режим ввода; переключение сохраняет IME, курсор, выделение и историю. Несколько независимых checklist со стабильными ID, не принудительная перепись markdown. Файлы принадлежат задаче: выбрать/отменить/прогресс/повтор/просмотр/удаление; production требует blob storage, прав, безопасной загрузки и карантина, не хранения больших base64 внутри task JSON.
Релиз выбирается поиском из сущностей проекта; создать недостающий по праву и вернуть ID в незакрытую задачу. Теги — общий проектный справочник ID/имя/цветовая пара/архивность; переименование не ломает связи. Фильтры — поиск + видимые редактируемые условия «Исполнитель», «Релиз», «Теги», остальное через «Добавить условие», без JQL и LLM-парсинга. Несколько значений одного поля — ИЛИ, разных полей — И; теги имеют понятное «любой/все». Нет пресетов для отдельных колонок.
Треды — отдельные обсуждения с ответами: обычный комментарий или требующий решения, open/resolved, автор и решивший. Сначала открытые требующие решения, затем остальные по активности; закрытые свёрнуты. Закрыть тред ≠ закрыть задачу. Курсорная загрузка, anchors и сохранение черновика ответа при изменениях; повтор сети не дублирует комментарий.
Базовый шаблон и шаблон типа компилируются однозначно: scalars override, описание/checklists — явные inherit/append/replace/exclude с section IDs. Эффективное превью в настройках. Версия фиксируется на создании; старые задачи не меняются. Смена типа не перезаписывает введённое. Подзадача использует шаблон реального типа, без четвёртого конфликтующего шаблона.

## Интеграция и автоматизация
MapTaskReference {mapId, objectId, taskId} хранит связь отдельно от пользовательского содержания задачи. Карта показывает ссылку/проекцию актуального статуса; архивный снимок не перезаписывается. Удаление связи не удаляет задачу; идемпотентный повтор преобразования не создаёт дубль. Технические sourceRunId/история сохраняются для аудита, но блока «Источник» в задаче нет.
Редактор автоматизации использует общую карту с типизированными событиями/условиями/действиями. Опубликованная версия, тест без побочных эффектов, симуляция причины выполнения, журнал, пауза, повтор и ошибки — обязательны. Настройка в проекте; пользователи работают с результатами на доске. Простые правила не требуют LLM. Операции: статус/исполнитель/релиз/тег/уведомление/тред; действие применяет те же команды и права, что человек. Одновременные противоречивые правила не решаются случайным last-write-wins: явный приоритет и политика остановки/конфликта. Root/correlation/causation IDs и visited-rules предотвращают петли.
GitHub/GitLab обязательны: события создания PR/MR, готовности к ревью, изменений/отзыва approvals, новых commits, закрытия без merge, merge, CI, release/deployment. Единый envelope нормализует провайдера, установку, репозиторий, delivery ID, revision/head SHA, время и task IDs. Связь через явный ключ задачи/подтверждённую привязку, не случайное упоминание числа. Один task может иметь несколько PR/MR: правило должно явно выбирать «любой» или «все обязательные». Merge ≠ публикация; CI старого SHA не переводит текущую задачу; новые commits сбрасывают устаревшие approvals. Перестановка, повтор, задержка, удаление webhook и отключение интеграции обязательны в тестах.
Секреты на сервере, GitHub подпись raw body, GitLab проверка поддержанного режима своего подключения; не приписывать одинаковый алгоритм всем версиям GitLab. Перед быстрым ACK событие сохраняется в inbox, затем обрабатывается очередью. Idempotency включает connection/repository/delivery; сверка текущего состояния провайдера при устаревшем событии. Права automation bot ограничены проектом; untrusted PR description не является инструкцией для агента. Live-подключения создаются только после настройки владельцем; фикстуры не выдаются за действующий webhook.
LLM в первой полезной версии: по запросу черновик описания/критериев из выделенного контекста; по запросу сводка длинного обсуждения с нерешёнными вопросами и ссылками. Никаких вызовов на hover, drag, открытие задачи, сортировку или каждый webhook. До отправки виден контекст/оценка токенов; лимит бюджета и размера, кэш по версии, отмена, отсутствие повторной оплаты из-за retry, подтверждение diff человеком. Не используем LLM для выдачи прав, принятия результата или решения о выпуске.

## Motion, производительность и качество
Используем DS: fast=120ms, standard=180ms, enter=280ms, layout=360ms и экспортированные кривые; существующий bindBoard уже имеет FLIP/ghost/keyboard/auto-scroll. Не заменяем это второй UI/DnD-библиотекой. Карточки/соседи двигаются через transform/opacity, не анимацию blur/box-shadow на каждом кадре. Незавершённая анимация отменяема. Reduced motion и forced colors обязательны. Конкретные длительности служат ролями DS, не обещанием FPS.
Бюджет приёмки: common scroll/drag без main-thread long tasks >50ms на согласованном устройстве; цель frame p95 <=16.7ms для 60Hz, для 120Hz <=8.3ms после профилирования. Интерактивный ответ p95 <100ms без времени сети, сохранение независимо измеряется. Наборы 50/1000/10000 задач, перекошенная колонка, глубокие связи, 100+ тредов. Сначала замеры; затем виртуализация переменной высоты с одним scroll root и закреплением активного drag/focus. Не обещаем «120 FPS» по Node-бенчмарку. Нет O(N²) фильтров в каждом рендере/геометрии всех карточек каждый pointermove; индексы, батчи reads/writes, ленивый документ, очищаемые listeners, отмена запросов.
Production gate: реальные host API/auth/ACL, транзакционные команды и inbox/outbox, миграции и backup/restore, observability, защищённые вложения, live SCM staging, perf на реальных устройствах, keyboard/screen reader/touch, light/dark/узкий экран. Локальный FileRepository и мок входа не считаются выполнением этого gate.

## Очередь реализации
B1 — реестр требований, воспроизведение сбоя карточек, навигация, компактная геометрия/общий scroll/sticky, модель дерева и сортировки с тестами, запрет путать порядок со статусом. Сохраняем читаемость существующих task IDs и работу Maps R4. Любое недостающее поведение DS — отдельный source-candidate и GAP, не патч внутреннего DOM.
B2 — полноценный документ задачи: DS Markdown, несколько checklists, треды, связи/reparent, исполнители детей, теги/релизы/шаблоны проекта и эффективное превью. Сначала транзакционные сервисные контракты, потом UI; источника нет, технические ссылки остаются.
B3 — проекция дерева на доске, понятные фильтры, сортировка-aware DnD и корректные pending/conflict/rollback, стрелки/меню, общий автоскролл, автоматизация переходов. Проверки именно 5+ карточек в коротком viewport обязательны: прежние smoke-тесты не обнаружили flex-shrink дефект.
B4 — редактор правил через карту, GitHub/GitLab inbox+normalization+действия, уведомления, защита циклов/конфликтов, staging webhook. Не писать токены в репозиторий. LLM только два ограниченных сценария после измерения ценности.
B5 — интеграционная, доступностная и производительная приёмка, миграции/безопасность файлов, error budget, полная ZIP/HTML поставка и PR. Бэклог не разрабатывается в этом scope.

## Команда и рабочий процесс
Потоки: Product/UX (сценарии и исключения); Task Domain (граф/команды/миграции); DS/Motion (публичные контракты); Board UI (проекция и документы); Integrations (SCM/automation); QA/Accessibility/Performance (независимая матрица); Delivery (commits, evidence, ZIP). Реальных параллельных агентов в этом проходе не запускали: доступного подходящего инструмента делегирования не обнаружено; роли — разделение ответственности и handoff, текущая проверка — self-review.
Цикл каждого этапа: зафиксировать acceptance → воспроизвести проблему на синтетических данных → общий root-cause fix → тесты модели/HTTP/браузера → скриншоты и perf trace → commit/push → manifest/fingerprint/архив. Нельзя менять assertions ради PASS или выдавать следующий этап за законченный по одному макету. Данные пользователя и main не изменяются тестами. У каждой промежуточной поставки есть явный остаток scope.

## Основания и исследования
Пользовательские замечания и приложенные скриншоты — первичные проблемы, не интервью с придуманными респондентами. Контракты DS проверяются по фактической 05.7 и файлу index(20260907-180030)(2).html. В ней заданы motion tokens, taskEmphasis, avatar stack, file-empty и Markdown. Пример «Выпуск 2.4» — пример продукта, не версия принятой DS. Внешние первичные источники: https://docs.github.com/en/webhooks/using-webhooks/best-practices-for-using-webhooks ; https://docs.gitlab.com/user/project/integrations/webhook_events/ ; https://docs.gitlab.com/user/discussions/ . Эти источники помогают контрактам; конкретные решения интерфейса выше — проектные решения по замечаниям пользователя, не результат проведённого UX-эксперимента.
