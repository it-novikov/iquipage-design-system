# Sprintique / IQUIPAGE — инженерный аудит R4

Дата исследования: 12 сентября 2026. Исходный снимок: `8e189329b84649e20c8e02b70ba7f94f69af8c4d`. Ветка исправлений: `feature/sprintique-vnext-audit`. Это аудит нового продукта и его библиотечной границы, не старой платформы и не production.

## Краткий вывод

Архитектурная основа подходит для чистого запуска: переносимый модульный монолит, отдельная версия UI-библиотеки, PostgreSQL с ограниченной runtime-ролью, явные команды, ревизии, квитанции повторных запросов и транзакционный outbox. Полную смену стека или микросервисное разделение исследование не обосновало.

Главные подтверждённые проблемы оказались на стыках: разные правила у двух путей записи задачи, несовместимые ограничения записи/чтения иерархии, обратный порядок SQL-блокировок, устаревшие ответы при переключении карты, неверная интерпретация истории событий доступа и восстановление UI после уже сохранённой команды. Исправления устраняют причины, а не скрывают ошибки интерфейса.

Отдельно ускорены чтение обсуждений и построение Planning, сокращены повторные загрузки фронта, добавлено безопасное кэширование публичных сборочных ресурсов и усилена достоверность CI. Таблица ниже отделяет законченные исправления от частично улучшенных архитектурных направлений.

**Security workflow на момент подготовки этого документа ещё выполняется.** Его результат и окончательные проверки будут зафиксированы отдельно до передачи PR. Отсутствие результата не означает отсутствие уязвимостей.

## Команда, метод и границы исследования

Три независимых AI-специалиста: backend/архитектура/SQL; frontend/DS/жизненный цикл; глубокая security-проверка. Ведущий интегратор проверяет CI, зависимости, кэширование, контейнер и итоговый diff. Backend-специалист дополнительно проверил исправления ведущего; ведущий проверил backend/frontend. Это не исследования с реальными респондентами и не внешний penetration test.

До реализации зафиксированы [план и критерии](PLAN.md). Отчёты исследования сохраняют исходные доказательства и номера строк именно базового снимка: [backend](backend-research.md), [frontend](frontend-research.md), [сборка и поставка](release-research.md). Номера строк в рабочей ветке после исправлений могут отличаться. [Запись frontend-проверки](../../../products/sprintique/docs/frontend-audit-r4.md) описывает принятые исправления и ограничения.

Использовались чтение кода и контрактов, воспроизведения на настоящем временном PostgreSQL 18, проверки приватного S3, управляемый порядок Promise/EventSource без HTTP, actual-component сценарии Chromium, текущая production-сборка на локальной QA-инфраструктуре и изолированный Docker-контейнер. Результаты прежних R1–R3 не выдаются за новый прогон.

Зафиксированный `design-system/`, ранее поставленный DS tarball и ветка PR #3 не изменялись. Продукт импортирует публичный `@iquipage/web`; SQL/авторизация не переехали в DS. Из PR #3 принят только относящийся к подтверждённому дефекту temporal recovery upstream-коммит `983de1319266cd2c8ff3ff4a87260e3efc8e90e0`, с provenance. Поздние UX-кандидаты и демонстрационные хранилища не импортировались.

## Архитектура: принятые решения

1. **Сохранить модульный монолит и переносимость.** `libraries/iquipage` — независимый UI-пакет; `products/sprintique` — автономный продукт с локальной packed-зависимостью. Detached build/test остаётся обязательным gate. Разделение сервисов допустимо позже по фактическим границам нагрузки, не по числу директорий.
2. **Один набор доменных правил.** Старые HTTP-формы и Planning должны вызывать одинаковые инварианты. Не добавлять «специальный режим для агента», обходящий подготовку/допуск/подтверждение. Actor/initiator берутся из credential, а не из тела запроса.
3. **Общий граф блокировок.** Проверка доступа → project lock → повторная проверка credential/доступа → asset lock → запись ресурса/audit/outbox в одной транзакции. Не лечить40P01 безусловным повторением внешних эффектов.
4. **Снимок и realtime — единый протокол.** Сначала durable watermark, затем загрузка состояния, затем replay. Пропуски закрываются resync; событие — сигнал инвалидации, не замена авторизованного документа. Роль подтверждается текущим серверным состоянием.
5. **UI-время и server-time разделены.** Отмена чтения не отменяет уже committed-команду. Поздний ответ не может менять другой экран. Receipt сохраняет смысл даже при недоступной проекции.
6. **DS не обходится ради исправления.** Controlled roadmap пересоздаётся через публичный контракт; компактный редактор/crop/upload/chips сохраняют одобренный язык. Публичный API DS в R4 не изменён, новый tarball не подменялся.

## Следующие инвестиции и release-ограничения

Это не скрытые «готовые» функции. Они требуют отдельного проверяемого изменения поведения или эксплуатационной политики, а не механического исправления подтверждённого бага.

| Направление | Зачем | Следующий проверяемый шаг |
| --- | --- | --- |
| Remote parent/link picker и windowing доски | Холодное открытие/DOM всё ещё масштабируются с каталогом. | Пагинированный typed endpoint, выбранный off-page parent, исключение потомков, stale/denied/cancel; публичная DS-версия при новом API. |
| Параллельное чтение Planning | Сейчас консервативный project FOR UPDATE сериализует и читателей. | Отдельный MVCC/read-snapshot протокол; нагрузочные и lock-upgrade тесты. Не менять все locks на FOR SHARE вслепую. |
| Staged media finalization | Decode/S3 держат SQL-транзакцию и project lock. | ADR состояний staging/ready/link/GC, короткий fenced finalize, сбой между каждой парой внешних эффектов. |
| Retention/audit/replay | История, login state, plans, receipts и outbox растут со временем. | Согласованный срок хранения и replay tombstones, bounded worker, recovery/backup tests; без произвольного удаления данных. |
| Непрерывная типизация фронта | JS host не защищён целиком strict TS. | JSDoc/checkJs или TS по модулям, public consumer fixtures; без any/ts-ignore как способа «позеленить» сборку. |

| Наблюдаемость и много экземпляров | Локальные тесты не определяют реальную ёмкость. | p95/p99/read/write/job metrics, распределённые rate limits, multi-replica revoke/stream/drain tests, восстановление с шифрованной внешней копии. |

| MCP/AI execution | Сейчас проверяемые grants/proposals/approvals/receipts, не произвольный runner. | Явные narrow tools, scopes, budgets, provenance и sandbox/provider policy до включения внешнего исполнения. |

## Достоверность проверки

После перекрёстного review и FE-R4-09:209 DS +135 product +135 detached, без skips, отдельно на native и Docker PostgreSQL. Сборка, границы и source-stability PASS. Точные checkpoint, container/browser evidence и оставшиеся проверки — в [ACCEPTANCE.md](ACCEPTANCE.md).

Первый прогон честно отказал в source-stability: чистая библиотечная сборка создала отсутствовавшие генерируемые HTML. Инвентарь исправлен по реальному `build.mjs`, а не ослаблением сравнения всех HTML; отдельный тест различает generated HTML и входной template. Последующие успешные результаты не стирают эту диагностическую запись.

Docker smoke проверяет immutable image ID, non-root/read-only/no-new-privileges/cap-drop, настоящие DB/S3 readiness, session и event-head, отсутствие анонимного доступа и packaged OpenAPI. Полный OIDC-login внутри контейнера, registry-push и deployment не выполнялись. Локальные сервисы и браузерные проекты — только изолированные QA-ресурсы.

## Источники и воспроизводимость

- Все утверждения о баге привязаны к базовому SHA, конкретному use case и воспроизведению в исследовательских отчётах; новые regression tests воспроизводят исправленные критерии, а не ожидают старый баг.
- Нулевой exit code нельзя выводить из `null`, возвращаемого для signal-termination: [официальная документация Node.js, Child process exit](https://nodejs.org/api/child_process.html#event-exit). Локальная Node24-регрессия является решающей проверкой нашей реализации.
- `immutable` применён только к именованным по содержимому публичным ресурсам; частные ответы остаются `no-store`: [MDN, Cache-Control](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Cache-Control).
- [Planning upstream983de13](https://github.com/it-novikov/iquipage-design-system/commit/983de1319266cd2c8ff3ff4a87260e3efc8e90e0) — источник ограниченного recovery-исправления, не свидетельство проверки нашей backend-интеграции.

Никаких credentials, session storage, исходных пользовательских баз, backup-файлов или приватной infra-конфигурации в отчёт/PR не включено. Исследование и локальная реализация не равны production-приёмке.
