## Решение, которое предлагается проверить

**Существующий wide-list должен по умолчанию сохранять полный текст и сам переносить значение под подпись, когда двум полезным колонкам не хватает места.** Размер экрана не является условием: решают ширина конкретной пары и размер её текста. Агент-потребитель использует прежний публичный pattern и реальные подписи; ему не надо вспоминать отдельный «доступный режим».

Первый кандидат — intrinsic layout без обязательного `container-type`, измеряющего JavaScript и смены DOM; подпись сохраняет разумный предпочтительный бюджет, значение получает оставшееся пространство. Конкурент — явно включаемый потребителем container mode, который позволяет менять геометрию всей пары. Ни способ CSS-реализации, ни приведённые ниже текстовые бюджеты пока не имеют native acceptance. **Не растягивать подпись ради формальной симметрии:** ширина её невидимого box не является пользовательской целью. Важны полный текст и ясная связь со значением.

## 1. Что должен получить человек

При открытии задачи человек читает **название свойства → его полное текущее значение**, затем при необходимости меняет его. Для этого не требуется открыть select, догадаться о tooltip или переключить размер интерфейса. Назначенное и неназначенное значение одинаково доступны чтению. Для readonly строки не появляется ложное обещание редактирования.

На достаточной ширине колонка подписей помогает быстро найти «Срок», «Исполнитель», «Оценка»; колонка значений помогает просмотреть состояние задачи. На тесной ширине приоритет — целостная пара: подпись над значением, следующий факт ниже с отчётливым интервалом. Более длинная вертикальная страница допустима. Требование уместить все свойства в первый экран при text200 противоречило бы этой цели.

Наблюдения, на которые опирается предложение: в native Task при root32px подписи сокращены и на viewport320, и на viewport768; в узком кадре также сокращены значения, а статичные План/Автор переносятся тесно. Причины фиксированной колонки120px, fixed heights32/26px, line-height20px и nowrap/ellipsis найдены в actual DS54. Полный набор исходных кадров, метаданных, границ и SHA находится в discovery. Это наблюдаемый барьер чтению, а не результат исследования поведения людей. [S1–S4]

## 2. Два конкурирующих подхода

| | **A. Автоматический intrinsic reflow — первый кандидат** | **B. Явный container mode у потребителя** |
| --- | --- | --- |
| Default | Существующий `data-label=wide` автоматически выбирает inline/stacked по полезным текстовым бюджетам. Нового обязательного attr нет. | Полнота текста и естественная высота исправляются в existing wide-list; он сохраняет две переносящие текст колонки. Host явно включает адаптивную композицию в подходящем размерном контексте. Название нового opt-in ещё не является API. |
| Кто задаёт ширину | Обычный layout родителя; пары используют фактически доступное им место. Сам список не выключает свой вклад в intrinsic sizing. | Host подтверждает, что ширина query-container определяется родителем. Он явно выбирает нужный размерный контейнер; не полагается на случайного ближайшего предка. |
| Как ведёт себя список | Общий label budget даёт одну колонку; весь остаток получает value. Это хуже для чтения, даже без формального clipping. |
| Цена для агентов | Один основной recipe, без проверки viewport и без набора режимов по каждому экрану. Сложность остаётся внутри DS. | Ещё одно решение и размерное обязательство в каждом consumer; вложенный drawer/поповер легко подключить неправильно. Нужно документировать отказ от intrinsic sizing и совместимость override ширины label. |
| Условие отказа | Если согласованный inline/stacked layout требует хрупкого CSS-трюка, огромных flex-grow коэффициентов, content-measurement JS, remount или даёт разные колонки из-за контента строки. | Если для исправления одного popover приходится добавлять произвольную фиксированную ширину; если требуемый порог нельзя корректно связать с текущими font/label overrides; если неполучивший opt-in consumer остаётся практически нечитаемым. |

**Предварительно выбрать A для небольшого rendered опыта.** B разумен, если ограниченный label box мешает чтению длинных подписей либо простой CSS не выполнит полезный ритм и геометрию. Это не разрешение сохранить старые усечения в B. Постоянно вертикальные пары — безопасный резерв для конкретного тесного host, если ему нечего выиграть от горизонтального сравнения; отдельную систему пользовательских настроек ради этого не вводить.

## 3. Проверяемая геометрия A: текстовые бюджеты

Это **псевдоспецификация поведения**, не готовый синтаксис CSS и не доказательство поддержки браузером. Она нужна, чтобы опыт проверял определённую гипотезу, а исполнитель не подбирал breakpoint под один PNG.

Обозначения:

- `W` — доступная inline-width **одной пары** после внешних padding/границ. Если пары находятся в нескольких внешних колонках, использовать ширину ячейки, не всей секции и не viewport.
- `U` — вычисленный размер основного текста значения в этом property-list. Сейчас interface role равен14px при root16 и28px при root32. Не вычислять его из меньшего font-size подписи или status pill. [S1]
- `H` — существующий предпочтительный label size: default120px, известный fullscreen override136px. [S2, S4]
- `L = max(H, 7U)` — базовый бюджет подписи; `V = 14U` — базовый бюджет области значения; `G` — существующий column gap `--iq-space-3` (сейчас12px).

Пара остаётся в двух колонках, когда **`W ≥ L + G + V`**. Иначе label и value располагаются последовательно; value получает всю ширину `W`. Для label допустим предпочтительный budget `L`, ограниченный доступной шириной: он должен показывать полный текст, но не обязан занять невидимым box всю строку. В любой ветви тексты могут переноситься; переключение не обещает, что любой произвольный label останется однострочным.

Почему именно такая исходная пропорция: около границы короткая категоризирующая подпись получает примерно треть базового пространства, а содержимое — две трети. Дополнительная ширина принадлежит значению. Значения включают имя, дату, единицу и обычные affordances, поэтому нельзя отдавать им только оставшиеся несколько букв после жёсткого label track. `14U` — бюджет всей области значения с её штатными деталями, не обещание четырнадцати символов. `7U/14U` — гипотеза для сравнения на реальных шрифтах/русских подписях; это не новая обязательная константа всех компонентов.

Первый простой прототип — wrapping layout с предпочтительными базами `L` и `V`: label не получает flex-grow, value получает свободное пространство; оба могут сжаться до ширины своей отдельной строки. При inline label равен `L`, value — `W − L − G`. Content minimum не должен отменять перенос и выталкивать пару наружу. Popup/hidden input не становятся третьими элементами строки. Это ещё нужно подтвердить на настоящих wrappers select/date/tag/static, особенно с нынешними отрицательными ghost margins.

Обсуждалась другая intrinsic возможность: распределить свободное пространство label:value как1:3, чтобы после переноса label тоже растягивался целиком. При615px/normal она расширяет label с120 до≈191.75px и уменьшает value до≈411.25px. **Такой сдвиг не выбран стартовым решением:** он расходует полезную ширину обычного Task ради свойства невидимого box. Вернуться к нему можно только при конкретном вреде от более раннего переноса длинной подписи, с сопоставлением цены. Не усложнять CSS ради его математической симметрии.

| Размер текста и родителя | Исходная граница A | Что происходит / что опыт должен оценить |
| --- | --- | --- |
| `U=14`, `H=120` | `W < 328px` → stacked; `W ≥ 328px` → две колонки | Следует из120+12+196. Это вычисленная граница данного шрифта, не viewport media query. |
| `U=14`, `H=136` | Граница344px | Override подписи учитывается, а не игнорируется новым режимом. |
| `U=28`, `H=120` или136 | `W < 600px` → stacked; `W ≥ 600px` → две колонки | Label budget становится196, value392. Все значения `W` здесь — ширина пары, не ширина окна. |
| Около280px содержимого узкого Task | Stacked при normal и text200 | Value получает всю строку; больше нет узкой второй колонки рядом с120px label. Длинные слова всё ещё требуют безопасного переноса. |
| `W≈615`, normal | Две колонки: label120, value483 | Сохраняется исходный разумный label budget; нет предлагаемого сдвига до≈192px. Отдельно проверить фактические ghost insets и нормальный ритм. |
| `W≈615`, text200 | Две колонки: label196, value407 | Известный широкий Task остаётся горизонтальным; есть только15px сверх базовой потребности. Проверить фактический padding, gap, borders и область фокуса около перехода. |
| `W≈350`, normal → text200 | Две колонки → stacked | Один и тот же родитель может поменять композицию только из-за увеличения текста. |

Для всего списка одинаковой ширины решение и колонка одинаковы; оно не должно зависеть от длины выбранного владельца или статуса. Не выбирать режим отдельно для каждой строки по текущему `scrollWidth`: иначе при изменении данных список начинает колебаться и разрушает навык поиска. `--iq-properties-label` в A становится предпочтительным базовым размером, который может быть увеличен текстовым minimum или ограничен тесным родителем. **Это изменение публичной семантики нужно прямо описать и проверить**, а не выдать за полностью совместимую замену единиц.

Если измеренный normal Task теряет полезную ширину без выигрыша чтению, выяснить конкретное ограничение, а не повышать порог до совпадения с одним кадром. У B необходимо доказать связь запроса с фактическим `H/U`: псевдоформулу нельзя просто скопировать в `@container` с неподтверждённым синтаксисом переменных.

## 4. Общий контракт текста, ритма и управления

Он обязателен для обоих вариантов. Решение «stacked» само по себе его не выполняет.

| Часть | Конкретное поведение |
| --- | --- |
| Подпись | Полностью видима, без nowrap/ellipsis/line-clamp. Текущая label typography и muted role сохраняются; unitless line-height из label role **1.45**, а не20px. В inline режиме привязана к первой строке значения, не к вертикальному центру длинного блока. |
| Основной текст | Interface role с line-height **1.5**; естественный перенос по словам. Для действительно неразрывных имён/ключей/строк — аварийный перенос без горизонтального выхода; исходные данные и копируемый текст не меняются. Значимые дата/сигнал/единица остаются полностью доступны. |
| Высота |36px row,32px ghost и26px pill перестают быть фиксированными потолками. Это нижние границы; блок растёт по строкам и внутренним отступам. Начальная гипотеза block-padding controls — существующий `space-1`; не уменьшать шрифт ради старой высоты. Это не утверждение о полной touch/WCAG-приёмке. |
| Inline ритм | Статичное и editable значение имеют одинаковый текстовый край и согласованную первую baseline. Статичное значение получает нужный внутренний текстовый отступ, без hover/Tab-stop. Нельзя просто снять height с кнопок и оставить static line-height20px: чередование строк станет неровным. |
| Stacked ритм | Один текстовый левый край. Начальная пара spacing roles: `space-1` между label/value, `space-3` между соседними парами; внутренние control insets учитываются в видимом расстоянии. Связь label/value сильнее, чем расстояние до следующего label. Новые карточки/рамки вокруг каждого свойства не нужны. |
| Avatar/dot/chevron | Сохраняют размер affordance; длинная подпись не сжимает их до точки и они не занимают всю текстовую колонку. Выравнивание по первой строке, не посередине трёх строк. Тексту выделен собственный сжимаемый/wrapping блок. |
| Status pill | Caption полностью переносится, fill растёт вместе с ним. Скругление ограничено размером **однострочной** pill: многострочное значение не становится огромным овалом, в углах которого текст выходит за спокойную заливку. Цвет/смысл статуса не меняются. Окончательные insets и форма требуют кадра. |
| Составные значения | Имя с avatar — единая основная группа, secondary date допускает собственную строку. Автор не должен распадаться на отдельный avatar-only ряд, затем тесные имя/дату. У parent key остаётся связанным с полным title, но не блокирует его перенос; у tags переносится и список, и длинный текст отдельного chip. |
| Readonly | Полный текст, прежние tones/units/empty state. Не заменять его disabled select ради получения CSS. Отсутствие hover и команды остаётся правдивым. |
| Input | Настоящий input у `iq-combobox` остаётся однострочным редактором; не обещать ему multiline textfield. Если нужен длинный выбранный display caption без редактирования строки, использовать существующий select/searchable по задаче. Label и размеры оболочки подчиняются применимой части контракта. |
| Фокус и intent | Тот же DOM/control при изменении ширины и текста; label/name linkage, DOM/Tab order сохраняются. Resize не переоткрывает editor и не отправляет команду. Весь видимый trigger доступен для hit/focus; focus outline и нижняя строка не отсекаются родителем. Открытый popup и Escape возвращают к тому же объекту управления через существующий механизм. |

Hover-fill может сохранять привычный небольшой выход влево, **если остаётся место для него и focus ring**. Его отрицательный margin не должен незаметно менять условие переноса, уводить caption за границу или создавать горизонтальный scroll. При stacked режиме текстовые края сравниваются по видимому тексту, а не только по прямоугольникам разных wrappers.

## 5. Почему нельзя автоматически поставить `container-type` на любой list

`container-type:inline-size` включает inline-size containment: вклад содержимого в intrinsic inline sizing меняется. У auto-width/shrink-to-fit родителя это может изменить или схлопнуть рассчитываемую ширину; block height продолжает зависеть от содержимого. Поэтому обещание «поставим container-query и остальные размеры останутся прежними» неверно. Конкретный popover ещё надо проверить. [W1]

В B нужен явный, имеющий определённую ширину контекст. Font-relative единицы в size query относятся к font query-container; этот font должен соответствовать `U`, а не случайному меньшему label. Имя контейнера исключает выбор постороннего предка. Сам факт поддержки container queries не доказывает нужный sizing contract. [W2]

A избегает добавления containment, но **не освобождается от проверки intrinsic ширины**: смена grid на wrapping layout также меняет min/max-content вклад. Нужен маленький shrink-to-fit пример, а не утверждение «без container-type рисков нет». Не лечить его произвольной шириной/`contain-intrinsic-size`, придуманной под320px Task.

## 6. Известные consumers и граница ответственности

По текущему source search production `data-label=wide` найден в двух ветвях общего Task. Документы/тесты — другие упоминания, не независимые runtime consumers. [S2–S4]

| Consumer | Что покрывает общий contract / что остаётся у продукта |
| --- | --- |
| Task editable list | Статус, исполнитель, срок, приоритет, тип, parent используют существующие controls. Их label/trigger/wrap — DS. Callback, meaning, права — продукт. |
| Release/tags slots | `catalog-picker.js` создаёт настоящий `iq-select` / `iq-tag-picker`, slot использует `display:contents`. Новый row layout должен работать через этот wrapper, не требовать вручную копировать CSS в каждый слот. [S4] |
| Estimate и Plan host trigger | Публичная `.iq-property` + label + `.iq-date-trigger`: участвуют в той же ширине, baseline и переносе, хотя их команды/поповеры продуктовые. Readonly Plan — обычный текст `.iq-property-value`, ему нужен тот же полный перенос. |
| Task readonly list | Статичные owner/date/estimate/release/parent/tags/author используют public value/text/meta parts. Семантика сохраняется; wrapper имени/метаданных можно уточнить при adoption, чтобы не имитировать структуру набором случайных flex children. |
| `.tdr-pill` в readonly status | **Одного DS patch недостаточно:** продукт сам задаёт `height:26px` и имеет собственную композицию dot/text. При adoption необходимо снять потолок, согласовать typography/insets/radius, выделить полный caption в существующий text part. Иначе editable status исправится, а readonly останется дефектным. Не заменять на `ui.badge` только по похожему названию: текущие API не гарантируют одинаковые dot/tone/height semantics. |
| Другие public properties variants | `data-columns=auto/2` управляет внешними колонками, strip скрывает labels. Не переносить этот policy на них незаметно через широкий selector. При затронутом shared правиле — узкая проверка реального сочетания; обычные формы/меню не перепроектировать. |

Ближайшая поставка может оставить `.tdr-pill` продуктовым composed value с явным соответствием общему DS-контракту. Если её форма требует повторить весь новый layout/style policy, это аргумент вынести **маленький публичный static-value recipe** в DS, не создавать второй status engine. Новое имя класса или helper в этой записке не объявляется существующим API. Главное — не закрывать DS acceptance по editable и забывать readonly.

Тот же drawer открывают Board и Planning creation. Это основания проверить общий consumer, а не повод переписывать все маршруты. Состав/порядок свойств, workflow сохранения, права и уже исправленный Estimate popup вне данного изменения.

## 7. Минимальный опыт, который различит гипотезы

Browser-author сейчас готовит **baseline** на54; следующая таблица не требует менять его задания или запускать параллельный стенд. После baseline выбрать только проверки, которые отвечают оставшемуся вопросу.

| Неопределённость | Различающий опыт и основание решения |
| --- | --- |
| Причина DS / вклад продукта | Сопоставить уже подготовленный public recipe54 и actual Task при тех же данных/font. Измерить track/line-height/overflow, показать полный caption. Если отдельный static failure есть только в продукте, не маскировать его общим DS selector. |
| Правильный переход | На одном viewport изменить **ширину пары** через вычисленную границу; отдельно изменить font при том же `W`. Особенно около `W≈615/U28`: кадр и geometry покажут, полезны ли две колонки или нужна более широкая область значения. Измерять content width, не вычитать padding на глаз. |
| Цена A против B | Сопоставленные normal Task и text200 с одинаковыми данными: найти поле, прочитать полный текущий факт, просмотреть соседние значения. A выигрывает только если устранение clipping не оплачено бесполезной пустой label-колонкой и слишком ранним переносом обычных values. Это экспертное сравнение; человеческая скорость/успешность остаются непроверенными. |
| Составная строка | В выбранной тесной композиции показать long owner/release, date+signal, оценку с единицей, unbroken caption, readonly Plan/author и pill. Проверять реальное clipping предков и glyph/text rects вместе с кадром; `scrollWidth == clientWidth` не доказывает отсутствие ellipsis. |
| Intrinsic sizing | Тот же public recipe внутри простого auto-width родителя/popover рядом с definite-width вариантом. Проверить calculated width/overflow до и после; это различает безопасное intrinsic wrapping и побочный эффект containment. |
| Сохранилось управление | Пока trigger сфокусирован/открыт, перейти через границу ширины, завершить или отменить существующее действие. Проверить identity, visible focus, одну UI-команду, возврат, доступность нижних строк прокруткой. Synthetic dispatch не доказывает сохранение backend. |

Закрывается ровно принятый layout/interaction scope на точной поставке. Root-font200 не переименовывается в browser zoom200. Native evidence и независимый opponent review предложения ещё ожидаются; новых human PASS, общих числовых квот и повторного большого аудита нет. Safari/Firefox/iOS/VoiceOver остаются в принятой проверке перед релизом, без объявления Chromium опыта полной платформенной приёмкой.
