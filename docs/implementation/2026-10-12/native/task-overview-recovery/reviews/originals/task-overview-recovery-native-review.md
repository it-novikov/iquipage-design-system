## 1. Человеческая задача и предел принятого решения

Человек открывает задачу, чтобы понять, что сейчас требует его внимания, что уже получилось и куда перейти дальше. Его не должна отвлекать техническая разница между завершившимся запуском, незавершённым шагом и ещё не принятым результатом. При этом интерфейс обязан сохранять сами различия: завершение запуска не принимает результат, чтение не отправляет решение, ограничение права отвечать не скрывает доступный для чтения вопрос.

Текущий PR исправляет потерю ранее принятого представления после PR87 и ограничивает дополнительную status-строку случаями question/review. Отдельный Compact-дизайн, изменение бюджета результата и гарантия размещения всех сведений без прокрутки не входят в этот PR.

Этот P2 открыт для композиционного продолжения и не является регрессией, внесённой условием status-строки.

**R2-F2 [P2, подтверждённое представление + гипотеза интерпретации, OPEN] — смысл завершения всё ещё неоднозначен в полном Work.**

В after-CTA rejected/blocked/review/question кадрах под «Кодекс» остаётся «Работа завершена», а ниже показаны доработка, нужный ответ или непринятый результат. В rejected/blocked overview при этом совсем нет короткой подписи типа «Нужна доработка»: смысл приходится выводить из title. Именно наличие этих строк/отсутствие подписи подтверждено; возможное понимание «вся задача готова» — экспертная гипотеза.

Причина: общий словарь session state применяется в заголовке Work, а overview branch для selected step теперь не показывает дополнительный session status. Это устраняет ложную строку в текущем месте, но не завершает проектирование всех уровней статуса. Следующая работа должна рассмотреть язык «запуск завершён / результат ждёт проверки / шаг требует доработки» как единую модель, сохраняя реальные states и приоритет одного действия. Сначала сверить все callers этих подписей; простая глобальная замена строки без проверки контекста не предлагается.

Приёмка будущего изменения: возвращённый шаг, blocked, pending review и genuine complete различимы без знания внутренней модели; не появляются два конкурирующих сигнала «готово»/«не готово». Backend state и Task status не меняются ради текста. Это существующий более широкий Work UX и не обязательный дополнительный redesign PR88.

**R2-F3 [P2, подтверждённая нехватка объяснения + гипотеза затруднения, OPEN] — полный вопрос без права ответить выглядит как недоступная форма без объяснения причины.**

В question-no-answer after-CTA PNG видны варианты и textarea, но нет видимого объяснения, кто может ответить или почему текущему читателю действие недоступно. Текущий recovery правильно убирает требование ответа из overview; внутри вопроса сохранено прежнее disabled presentation.

Возможное улучшение: короткое contextual read-only объяснение на основании реально известных прав. Не придумывать имя отвечающего, если projection его не сообщает, и не выдавать получение дополнительного права за уже доступное действие. Проверка должна показать, что человек понимает отсутствие собственной команды и продолжает читать вопрос; enabled answer path при наличии права должен сохраниться. Нынешняя fixture не доказывает backend permission enforcement.

**R2-D1 [диагностический follow-up, без утверждения keyboard-дефекта] — общий переход «Открыть работу» оставляет recorded focus на BODY.**

Это прямое наблюдение в трёх per-case records, тогда как targeted review/question получают конкретный focus target. Здесь тест использует pointer и не выполняет следующую Tab/Shift+Tab. Поэтому потеря keyboard пути или screen-reader объявлений не считается доказанной. Для следующего исправления навигации достаточно ограниченного keyboard воспроизведения и осмысленной цели фокуса, а не немедленного общего screen-reader аудита. Существующий release порядок проверки реальных assistive technologies сохраняется.

Ни одно из этих наблюдений не отмечено как исправленное или waived. Автору продолжения следует связать открытые P2 с соответствующими карточками композиции/Work, сохранив этот оригинал. Ограниченный APPROVE_IN_SCOPE не принимает их за готовую продуктовую приёмку.

Утверждение «вся работа завершена» убрано из проблемного overview без изменения состояния запуска. Нейтральный вопрос не выдаёт чтение за команду ответа. Review action не принимает результат и не скрывает сам результат. Эти три изменения имеют достаточно текущих доказательств для ограниченного принятия. Оставшаяся композиция требует следующего небольшого опыта, основанного на новых кадрах.

## 7. Что это ревью не проверяло и не утверждает

Не проверялись backend запись, grants enforcement, выполнение агента, принятие/отклонение результата, сохранение после reload, влияние polling/conflict/permission changes, полноценный keyboard путь или screen-reader announcements. Нулевые adapter attempts показывают только отсутствие попыток записи в выполненных frontend путях.

Тёмная тема, font scaling, иные размеры и платформы не входят в эту замороженную семантическую матрицу. Настоящие Safari, Firefox, iOS touch, VoiceOver и другие screen readers остаются отдельной проверкой перед релизом по правилу владельца. Новый onboarding не проектировался и не внедрялся.

Этот reviewer не собирал и не принимал full vNext или Maps артефакты. Общий native job содержит отдельные Tabs/Estimate шаги, однако настоящий вердикт опирается на Task artifact и его определённые проверки. Исторический или соседний PASS не подменяет независимую оценку другого scope. Обещаний отсутствия любых лагов, багов или всех UI-дефектов нет; performance trace, backend reliability и человеческая понятность здесь не измерялись.
