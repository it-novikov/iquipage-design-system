## 3. Собственная позиция до предложения и результат её сверки

Основание — перенос содержания вверх без новой ширины drawer и без переменного длинного пути к оценке/релизу. При этом ядро из четырёх строк было гипотезой, а планировочные поля не назывались редкими. Это совпало с направлением VT1 автора, но не подтвердило его результат. [I1, I2]

## 4. Явный спор с оригинальным предложением

Ниже указано, что именно оспорено в input SHA `4a8a1862…`, чем возражение подкреплено и какую поправку автор принял в переписке с reviewer и root. **Принятая поправка к плану ещё не является исправленным и проверенным UI.**

### R-F1. Второй полный `workStep` снова оттесняет описание

**Исходное предложение:** компактный summary наверху, затем четыре свойства и disclosure, затем отдельный `workStep(expanded:true)` с полным `result/evidence`; дальше описание. [I2 §5]

**Возражение reviewer:** название и состояние шага уже есть в summary. Ещё одна полная история результата создаёт повтор и неограниченную по длине область до описания. На длинном результате пользователь снова проходит чужую длинную секцию, чтобы добраться до текста задачи; при добавлении обязательного short preview получаются две проекции одного предмета на одной вкладке. У public `workStep` допустимый API, но это само по себе не делает композицию спокойной. [S2, S3]

**Ответ автора и принятая поправка:** убрать отдельный full `workStep/evidence` с Task-вкладки. Использовать один existing overview: идентичность/название выбранного шага, нейтральное review-состояние, буквальное начало его `result` либо честный fallback, прежний `review:<id>` для полной проверки. Полные result/evidence/criteria и approve/reject остаются в существующем work-разделе. Не расширять первую пробу дополнительными телами `what/next/complete`.

Для сокращённого текста явно написано «Начало результата» и показано многоточие; для полного короткого текста — «Результат шага». Автор предложил 160 Unicode code points с границей слова как **пробный внутренний бюджет**, не публичный DS-контракт, не критерий приёмки и не доказанный размер. Reviewer допускает такой prototype: фрагмент буквальный, escaped, без генерации; title сохраняет предмет; фактическая высота проверяется. Если этого бюджета недостаточно для ясности или он вытесняет прямые поля в narrow, меняется правило/композиция. Пустой нормализованный текст — «Описание результата не добавлено», а не «Результата нет»: evidence может существовать отдельно.

### R-F2. Вывод ранее скрытого `status` может создать ложное личное требование

**Source evidence:** question-ветвь всегда возвращает «Нужно ваше решение», даже при `canAnswer=false`; тогда только label корректно меняется на «Открыть вопрос». Fallback-ветвь берёт status из session: возвращённый шаг при завершённом session может получить рядом с названием «Работа завершена», а blocked-шаг — «В работе». Full work view уже различает «Нужна доработка» и step states. [S2, S3]

**Возражение reviewer:** механически показывать все status отдельно от text шире нужного исправления H02. Право посмотреть вопрос не означает обязанность лично ответить; завершение запуска не отменяет доработку шага.

**Принятая стратегия:** отдельно показывать корректное состояние только для `question/review`. При `question && !canAnswer` — нейтральное «Вопрос ждёт ответа» с прежней «Открыть вопрос»; при `canAnswer` сохраняется существующий доступный путь ответа. Review — «Результат на проверке». Для остальных branch сохраняется текущее отображение до адресной проверки, без нового общего вывода session status. Selector, actions и grants не меняются. Root и автор согласились с этой ограниченной стратегией; новый WP05 не открывается.

### R-F3. «Другие свойства» устойчиво расположено, но слабо сообщает о планировочных полях

**Согласие:** вход перед длинным содержимым, один native disclosure, один экземпляр каждого контрола и сохранённое open-состояние в текущем эпизоде — хорошая основа пробы. Автор уже не называет поля редкими. [I2 §5]

**Возражение reviewer:** generic label скрывает, что здесь находятся именно оценка, тип, релиз и план. Частый планировщик не обязан выводить это из термина «другое». Пустая фикстура не показывает цену заполненных значений и повторных открытий.

**Принятая поправка:** проверить «Другие свойства» с видимой вторичной подсказкой «Оценка, тип, релиз, план…» внутри того же native summary. Подсказка переносится естественно, её слова входят в доступное имя; это не второй контрол и не набор дублированных значений. Открытая группа сохраняется до явного закрытия/закрытия Task, включая tabs и fullscreen. Если hint сам создаёт шум или плохие переносы, его форма уточняется по actual render.

Цена раскрытия между задачами остаётся открытым H11-вопросом. При неудобстве не следует прятать результат за усреднённым PASS других ролей или автоматически сохранять глобальную персонализацию. Можно изменить устойчивый состав ядра либо предпочесть другой контекст работы. **Прежняя оценка экономии 205–207 px отозвана для refined варианта:** hint и новый preview меняют высоту, измерения нового render нет.

### R-F4. Удаление «Описание» преждевременно объявляет его дубликатом

**Исходное предложение:** убрать внешний heading «Описание», поскольку Markdown может иметь собственный заголовок. [I2 §5]

**Возражение reviewer:** Markdown может начинаться обычным абзацем, а доступное имя секции не заменяет видимую границу для sighted/low-vision читателя. В задаче с обзором результата такая граница особенно помогает различить содержание поручения и предъявленный результат. Возможность собственного Markdown-heading не гарантирует дубликат. [S1]

**Принятая поправка:** в первом сравнении сохранить «Описание» одинаково с baseline. Удаление остаётся отдельной визуальной гипотезой discoverability; это не обязательная стадия следующей работы.

### R-F5. Read-only кадр не проверяет H11, а обязательный набор вариантов становится процедурной квотой

**Исходное предложение:** «read-only сравнительные реализации», обязательный VT2 в §6 и последующий render всех обозначенных вариантов. [I2 §§6, 8, 9]

**Возражение reviewer:** кадр проверяет композицию, но не раскрытие → editor → сохранение/ошибка → возврат. Вдобавок отдельная wide-гипотеза нужна по конкретному конфликту, а не чтобы выполнить фиксированный набор макетов.

**Принятая поправка:** первый короткий опыт — baseline и уточнённый VT1; H11 проверяется интерактивно на прежних контролах. Изолированные адаптеры допустимы для направления, но подтверждение mock callback не считается настоящим сохранением. VT2 подключается к конкретному wide-конфликту; C — контроль цены раскрытия/порядка на той же ширине. Это конкуренты, не универсальная квота. Новый Task либо проверяется как действительно затронутая ветвь, либо первоначальная production-композиция ограничивается существующими Task.

## 5. Предметные state-примеры для уточнённого overview

Текущие `workFocus/workOverview` вызваны read-only на управляемых state-примерах. Это проверка ветвей модели, **не browser run, backend test или human validation**. Она подтвердила: question с разрешением и без него имеет одинаковый status; review с текстом и без него имеет одинаковый текущий overview/title. [S3]

| Состояние | Что должно быть различимо после refinement | Что сохраняется |
|---|---|---|
| Обычная Task без `workPlan` | Описание в новом месте; без искусственной цели/nextAction или пустой result-card. | `summaryRoot.hidden`; канонический Markdown и текущий редактор. |
| Открытый вопрос, `canAnswer=true` | Реальный вопрос и его состояние, прежний доступный ответ. | Приоритет вопроса, action/id, единственная форма ответа. |
| Тот же вопрос, `canAnswer=false` | «Вопрос ждёт ответа»; «Открыть вопрос» не выглядит личным обязательством решить. | Никакой новой возможности записи. |
| Выбранный review-шаг с `result` | Состояние + идентичность/название + буквальный preview результата с явным признаком сокращения. | Полная проверка и решение во вкладке работы, прежние permissions. |
| Выбранный review-шаг без текста результата | «Описание результата не добавлено», а не выдуманный результат и не утверждение об отсутствии evidence. | Переход к существующим evidence/criteria; исходные права решения. |
| Открытый вопрос одновременно с готовыми шагами | Вопрос сохраняет существующий приоритет. | Не обещается показ «последнего» результата или одновременная новая выборка. |
| Rejected/blocked step при другом session state | Не появляется новое ложное утверждение о завершении выбранной работы. | Прочие branch labels остаются прежними в этом срезе. |

## 6. Что означает сохранённая быстрая правка

Для планировщика «План» здесь — диапазон `plannedStart/plannedEnd` с явным «Применить» и `schedule {start,end}`, не выбор sprint membership. `due` остаётся отдельным сроком. Изменение типа влияет на предложение/применение шаблона; у новой задачи может ещё задать default priority, пока человек его не трогал. Приоритет high/critical — существующий видимый сигнал, поэтому его нельзя объявить автоматически второстепенным. [S1, S5]

Проверять нужно фактический изменённый путь: открыть группу, выполнить нужную правку оценки/релиза/типа/плана, понять сохранение или отказ, продолжить прежнюю работу со списком. Open-состояние не должно сбрасываться из-за poll, переключения вкладки или fullscreen. Generic save error нельзя приписывать произвольному скрытому полю; если ошибка действительно связана с конкретным полем, оно должно быть доступно до переноса фокуса. Это условия сохранности изменённого пути, не требование прогнать весь продукт.

Один экземпляр формы необходим не только для чистоты кода: существующие `FormData`, `querySelector`, estimate callback, catalogs и plan mount читают конкретные элементы. Desktop/narrow копии или lazy mount дают риск прочитать другое значение и потерять draft. Нативный disclosure и resize должны сохранять эти же элементы. Read-only/accepted Task сохраняет видимое объяснение ограничения рядом с основным контекстом, а не внутри закрытых свойств. [S1, S5]

## 7. Доступность, DS и визуальная граница

Для опыта достаточно существующих публичных `.iq-properties[data-label=wide]`, native `.iq-work-details`, work-story, Markdown editor и dialog. У `iq-work-layout` нет выдуманных `aside/properties` slots. Продукт владеет составом групп; библиотека — общими контролами и геометрией. Предложение автора здесь подтверждается проверенным пакетом.

При text200 уже видна проблема подписей. Нельзя объявить её устранённой удалением семи строк или уменьшить текст ради первого экрана. Публичный `--iq-properties-label` можно проверить в конкретной композиции; если его недостаточно, вопрос общего reflow остаётся отдельной адресной задачей DS. Новый prototype не получает полный readability PASS от прежних PNG. [E5, публичный DS54]

Важный consumer уже найден: Workbench переопределяет `grid-template-areas` при personal supplement, в том числе fullscreen от 900 px. Это конкретный риск порядка зон, не повод открывать весь Workbench-аудит. Обложка перед title и personal request отсутствуют на исходных пяти кадрах; вывод обычной Task на них автоматически не переносится. [S1, S4, S6]

С точки зрения арт-дирекции после refinement остаётся один ясный поток: title → реальный контекст → устойчивые ключевые поля и понятный вход в остальные → обозначенное описание → материалы/обсуждение.
