# PF04 / WP04 — первый экран Task

Дата: 12 октября 2026. Статус: **предложение для сравнительного прототипа, не принятый дизайн и не human PASS**.

## 1. Решение, которое предлагается проверить

Первым прототипировать **VT1: короткий постоянный список ключевых свойств, затем содержание работы, остальные свойства — через заметное раскрытие**. Сохранить на прежних контролах Статус, Исполнителя, Срок и Приоритет; Оценку, Тип, Релиз, План, Родителя, Теги и Автора оставить в устойчивом порядке под «Другие свойства». Эти семь строк названы дополнительными по месту в композиции, **не редкими по частоте**. Частота их использования неизвестна. Приоритет остаётся сразу видимым также потому, что его high/critical тон — существующий смысловой сигнал, который пропал бы при механическом скрытии всех строк после срока. [S1, S2]

В том же сравнении проверить **VT2: содержание слева, полный открытый список свойств справа в существующем полноэкранном режиме**. Drawer шириной 664 px для двух таких колонок недостаточен. VT2 получает преимущество по месту для чтения ценой ширины, контекста доски и более сложного узкого режима. Его нельзя объявить универсальным desktop-решением лишь потому, что окно браузера широкое. [S2, S10]

Для обеих альтернатив краткий блок работы агента продолжает использовать существующие `workFocus` / `workOverview`, но отдельно показывает `overview.status`. Когда выбран шаг на проверку, содержательная зона показывает **его же** `result` и `evidence`, а не только название шага. «Проверить результат» ведёт в существующий review; кнопка принятия наверх не переносится. Это изменение проекции известных данных, не новая сущность «результат Task» и не новый алгоритм внимания. [S3, S4, S5]

Предпочтение VT1 пока экспертное: оно сохраняет привычную ширину, один поток чтения и прямое редактирование четырёх полей. Его необходимо изменить, если выигрыш H01/H02 не проявится либо работа с Оценкой, Типом, Релизом или Планом потребует мешающих повторных раскрытий. VT2 может оказаться предпочтительнее в контексте длительной работы на полном экране. **Ни один вариант здесь не отрендерен и не проверен участниками.**

Это продолжение принятой PF04, §5.5 и WP04; весь аудит и две завершённые итерации review не повторялись. Планирование как отдельная поверхность здесь не перепроектируется. H12 служит границей: выбор Task не должен заставлять руководителя открывать каждую задачу ради сравнения периодов. [V3]

## 3. Проблема и полная причинная цепочка

**Человеческий эпизод.** Исполнитель открывает задачу из доски или плана, чтобы понять ожидаемую работу и продолжить её. Reviewer должен увидеть, какой именно результат предложен, прежде чем принимать решение. Человек, ведущий проект, часто входит в тот же Task ради изменения атрибутов. Один список служит всем этим эпизодам, но на коротком первом экране описание проигрывает списку по месту. Известна геометрия; неизвестны частота эпизодов, время выполнения и величина ущерба людям. [E1–E5, V3]

Цепочка обычной Task прослеживается до данных: `openTaskDialog` получает Task, проектный контекст, каталоги, настройки шаблонов и участников → `editableFacts` / `staticFacts` создают один упорядоченный массив 11 строк → шаблон помещает `.task-editor-properties` перед `.task-editor-description` → `.iq-properties[data-label=wide]` задаёт строки минимум 36 px → 11 обычных строк занимают примерно 396 px ещё до интервалов секций → описание оказывается ниже первого полезного просмотра. Скрытые пустые данные сами по себе не обязательны: пустые значения сейчас сознательно оставлены на месте ради устойчивого редактирования. [S1, S2, S7]

У review есть отдельная причинная ветвь. `/work` возвращает plan, steps, permissions и sessions → `workFocus` выбирает открытый вопрос, затем непринятый done-шаг, затем активный/заблокированный/возвращённый шаг, затем завершение / checkpoint → `workOverview` уже возвращает и `status`, и `text` → Task summary печатает **`overview.text || overview.status`**. При заполненном `text` состояние не получает отдельного текста. Для review `text` — название шага; `step.result` и `evidence` показаны только внутри «Работы агента». Краткий верхний блок **уже существует перед свойствами**, если есть `workPlan`; утверждать, что любой агентный результат скрыт одиннадцатью строками, неверно. [S3, S4, S5]

## 4. Какие сведения и действия реальны

| Понятие человека | Реальный источник и ограничение |
|---|---|
| Цель обычной Task, критерий и то, что сделать | `taskMarkdown(task)` из канонического `description` / совместимости старых checklists. «Цель», «Что сделать», «Критерии готовности» — текст starter template, не гарантированные структурированные поля каждой задачи. [S8, S9] |
| Цель поручения агенту | `workPlan.goal`; это цель плана работы, её нельзя молча объявить заменой описания Task. [S3, S5] |
| Текущий предмет проверки | `workFocus(state).item` только при `kind === 'review'`: идентичность шага, `result`, `evidence`, `criteria`, `approval`. Не «последний комментарий» и не произвольный последний session. [S3, S4] |
| Следующее действие | Существующие `workOverview.action/label`; для обычной Task — написанный человеком следующий шаг / checklist в Markdown. Универсального `task.nextAction` нет. [S3, S9] |
| Завершение и принятие | Work step `state: done` отличается от его `approval`; `task.result === 'accepted'` — ещё одно состояние Task, которое делает её поля неизменяемыми. Их нельзя объединять в общий зелёный «Готово». [S1, S3, S4] |
| Срок и плановый интервал | `due` редактируется как поле Task; `plannedStart/plannedEnd` сохраняются отдельной Planning-командой через preview/commit. Один новый контрол «Дата» исказил бы смысл и сохранение. [S1, S11] |
| Тип задачи | Изменение Type может предложить / применить шаблон; у новой задачи ещё и default priority, пока человек сам не менял приоритет. Перенос Type — не просто перенос независимой строки. [S1, S8] |
| Дополнительный контекст | Материалы, wiki links, связи, файлы, обсуждение — уже отдельные sections; `supplement` Workbench добавляет собственные запросы. Не сортировать их «по важности» новым общим алгоритмом. [S1, S12] |

Сохраняются текущие границы: принятую Task редактировать нельзя; `canPlan` требует `canEdit` и Planning-hook; work permissions приходят из `/work`, включая отдельные `canDecide` / `canAnswer`. На сервере решение по результату требует human interactive actor и `APPROVALS_DECIDE`; ответ дополнительно зависит от `THREADS_WRITE`. Layout не расширяет эти права. Текущее различие callers — Board/Planning используют permissions, Workbench передаёт свою role-проверку — здесь не исправляется незаметно. [S1, S5, S12, S13]

## 5. Композиции для сравнения

### Общий язык двух вариантов

Ключ, заголовок, две вкладки, закрытие, fullscreen и их public DS-поведение сохраняются. Заголовок остаётся `.iq-inline-title` с естественным переносом, пределом 240 символов и существующим edit/focus; никакого ellipsis для названия. Вкладки не ужимаются ради компенсации DS54. Ghost-поля сохраняют свои подписи, readonly — статичные значения и объяснение с замком, просрочка — существующее слово и тон. [S1, S2, S7]

Иерархия: название работы — главный заголовок; состояние и следующий доступный путь — компактный контекст; описание / результат — читаемая основная зона; свойства — понятная поддержка работы. Никаких дополнительных карточек вокруг каждой группы или новой палитры. Сохраняются DS-роли: свойства 13 px label / 14 px interface при root 16 px; основной title сейчас использует `--iq-work-compact-title:24px`; Markdown использует собственные `--iq-md-text-size` / `--iq-md-text-leading` и одинаковую типографику при чтении и редактировании. Эти значения описывают текущий пакет, а не разрешают уменьшить их в продукте. [S7, S14]

Общий небольшой приём для сравнения: убрать дублирующий визуальный заголовок «Описание» перед Markdown, оставив доступное имя секции «Описание задачи» и `label="Описание"` у редактора. Документ уже может начинаться с «Цель», «Проблема», «Контекст» или другого собственного заголовка. Пустое состояние остаётся существующим «Нажмите, чтобы добавить описание» / «Описания нет» и «Начать с шаблона». Этот приём требует actual-render проверки и может быть отменён независимо, если редактор становится менее обнаружимым. В обоих вариантах он одинаков, чтобы не приписывать его эффект только колонкам. [S1, S8, S9]

**Общий содержательный блок работы:** существующий компактный summary остаётся в начале Task; его `overview.status` читается независимо от заголовка вопроса/шага. Ниже кратких свойств в VT1 либо непосредственно в основной колонке VT2 — чтение выбранного `workFocus`:

- `review`: публичный `workStep`, `expanded:true`, тот же step id с отдельным DOM-prefix, настоящий `result` и безопасно отрендеренные `evidence`; `[data-step-actions]` пуст. Верхняя «Проверить результат» сохраняет существующий переход `review:<id>` во вкладку, где находятся criteria и разрешённое решение. Длинный результат растёт естественно; его не пересказывают и не обрезают незаметно.
- `question`: нынешние название вопроса / состояние / действие; формы ответа остаются в своём единственном месте. При одновременно открытом вопросе и review сохраняется нынешний приоритет вопроса.
- `step`, `next`, `complete`: допускается показать уже имеющееся `what` либо `focus.text` из `workFocus`, с его настоящим смыслом. Отсутствующий следующий шаг не генерируется.
- Нет `workPlan`: никакой пустой рамки «Результат» и никакой выдуманной рекомендации агенту; описание сразу следует своему месту. Нет тела результата у review-шагa: прямо видна нехватка текста/ссылок, она не считается исправленной композицией.

Это чтение из того же подтверждённого snapshot, не вторая модель работы. При обновлении не терять идентичность выбранного шага, фокус и позицию чтения; не объявлять предыдущие данные актуальными после ошибки обновления. В исходных пяти кадрах этот блок отсутствует, поэтому его вид и высота пока **NOT_RUN**. [S3–S6]

### VT1 — короткий список и один поток чтения

| Порядок | Постоянно видно / раскрывается | Конкретная композиция |
|---|---|---|
| 1 | Идентичность, title, tabs | Существующая `.iq-dialog` / drawer; текущие шапка и маршруты. |
| 2 | Существующий summary работы и отдельный personal supplement, когда у них есть данные | Summary получает явный status. Личные запросы не смешиваются с общей приёмкой. |
| 3 | Статус → Исполнитель → Срок → Приоритет | Та же `.iq-properties[data-label=wide]`, тот же порядок четырёх контролов; значения редактируются сразу. |
| 4 | «Другие свойства», по умолчанию закрыто при новом открытии Task | Native `<details class="iq-work-details">`; внутри одна `.iq-properties[data-label=wide]`: Оценка → Тип → Релиз → План → Родитель → Теги → Автор. Раскрытие остаётся открытым до явного закрытия / закрытия Task, включая tabs и fullscreen. |
| 5 | Текст выбранного результата / продолжения работы, если он реально есть; затем описание | Public work-story/workStep и существующий compact Markdown editor. Содержательный документ растёт в одном scroll owner. |
| 6 | Материалы, wiki, связи, файлы, обсуждение | Их существующие именованные секции и команды. |

«Другие свойства» стоит **перед длинным содержимым**, поэтому вход в Оценку / План / Релиз не уезжает за десять тысяч символов. Открытие занимает место и сдвигает описание вниз — это сознательная цена редактирования, а не overlay над текстом. Внутри disclosure контролы уже смонтированы; раскрытие ничего не создаёт и не перезагружает. Обе группы остаются частью той же формы. Нет второго быстрого редактора одного значения. [S1, S7, S15]

**Геометрический бюджет, не измерение будущего render.** Четыре штатные строки — примерно 144 px вместо 396 px. Native summary по public recipe имеет 12 px вертикального padding с каждой стороны плюс строку текста, то есть около 45–47 px при обычном шрифте. Семь строк заменяются одной строкой раскрытия: экономия примерно **205–207 px**. Удаление внешнего «Описание» потенциально убирает ещё его штатные 32 px и 12 px отступа. Реальный выигрыш зависит от переносов, lock/warning, result и personal-блоков. Нельзя вычитать их из кадра и назвать это проверенной высотой. [S2, S7, S15]

Ритм: 8 px между связанными строками повествования, 12 px внутри disclosure / группы действий, 16 px между компактным контекстом и следующим блоком, 24 px между самостоятельными содержательными секциями — существующие `--iq-space-2/3/4/6`. Не складывать одновременно grid-gap и два section-padding для одной границы. У списка остаётся собственная плотность 36 px; сжатие строк до 28 px не входит в вариант. [S7, S15]

При 390 / 320 px сохраняется тот же линейный порядок. Длинное название переносится; дополнительные свойства раскрываются на всю ширину, а не в узкую боковую панель. Длинный result не прячет быстрые поля, потому что его тело находится после них; кнопка перехода к review остаётся в верхнем summary. Недостаток: содержание всё ещё начинается после четырёх строк, а у сложного agent/personal состояния ниже; reviewer вправе предпочесть VT2. При 200% текста пропускная способность первого экрана закономерно ниже; нельзя обещать все блоки до fold, срез требует сохранения чтения и редактирования, а не фиксированной высоты.

### VT2 — содержание рядом с открытыми свойствами

| Зона | Состав и геометрия |
|---|---|
| Общая шапка | Тот же title / tabs / identity, на ширину рабочей поверхности. Существующее fullscreen-переключение, не новый тип окна. |
| Основная колонка | Summary и личный запрос, соответствующий выбранный result, описание, материалы / wiki / связи / файлы / обсуждение. Наименование работы и текст имеют одну левую ось. |
| Колонка свойств | Все 11 строк в нынешнем порядке, всегда раскрыты; собственная подпись «Свойства задачи». Те же контролы, каталожные и плановые mount slots. |
| Условие двух колонок | Рабочая ширина после padding должна вместить около `39rem` чтения + `21rem` свойств + `--iq-space-6` между ними: около 984 px при root 16 px. Это начальный бюджет для render, не уже принятый breakpoint. |
| Реальная ширина | У нынешнего drawer внутреннее место около 615 px; разделение оставило бы непригодно узкое чтение. Существующий fullscreen body имеет max-width 1160 px; при штатном padding место для такой композиции есть. [S2, S10] |
| Недостаток ширины / большой текст | Один DOM-порядок: основной текст, затем весь открытый список свойств. Две колонки не сохраняются уменьшением шрифта. Поля не дублируются и не перемонтируются на resize; при узком режиме H11 получает реальную цену прокрутки. |

VT2 использует продуктовый grid вокруг public DS sections/controls. **У `iq-work-layout` нет slot `aside` / `properties`**: его реальные slots — header, navigation, summary, toolbar, content, footer; compact разделяет navigation/summary, не редактор Task и sidebar. Использовать имя компонента вместо подходящей геометрии было бы ошибкой. Новый DS layout-компонент для этого сравнения не доказан необходимым. [S10]

В первом прототипе у обеих колонок один scroll owner — `.iq-dialog-body`. «Всегда открыты» не означает неподвижную высокую панель со вторым scrollbar. Sticky для 11 строк с длинными тегами и text200 не объявляется готовым свойством этого варианта; при необходимости его исследуют только после первого сравнения. DOM и визуальный порядок не должны расходиться из-за одного CSS `order`.

VT2 сравнивается и с нынешним **fullscreen** baseline, иначе улучшение можно ошибочно приписать двум колонкам, хотя его дала просто ширина. При сопоставлении с VT1 отдельно учитывать переход в fullscreen / изменение default: это часть пользовательской цены, а не бесплатная предпосылка. На узком устройстве VT2 фактически превращается в следующий вариант C и может проиграть частому редактированию.

### C — умеренная перестановка без disclosure

Достоверный запасной вариант: title / tabs / существующие callouts → описание и действительный результат → **весь нынешний открытый список свойств** → дополнения. DOM переставляется вместе с чтением; поля, их плотность и подписи не меняются. Это самый прямой контроль гипотезы «мешает порядок» без нового раскрытия.

Цена — свойства находятся ниже всего описания. При коротком содержании это может быть приемлемее, чем раскрытие; при длинном документе Оценка и Исполнитель одинаково удалены от начала. C имеет смысл сохранять, если люди систематически не находят раскрытие, а содержимое их задач коротко. Он не становится победителем потому, что дешевле закодировать. Если H11 требует прокручивать длинное описание, C отвергается для этого контекста.

## 6. Спор пяти перспектив

Ниже **экспертная симуляция** конфликтов требований одним автором. Интервью, рабочая сессия пяти людей и независимое пользовательское исследование не проводились.

| Перспектива | Содержательное возражение | Как разрешено и что может изменить решение |
|---|---|---|
| Исполнитель | «Мне нужен текст задачи; зачем четыре поля перед ним?» | VT1 убирает семь строк и повторный heading, но сохраняет четыре понятные опоры. H01 должен показать, что этого достаточно; если человек всё равно начинает с прокрутки и не понимает задачу, одной экономии высоты мало. |
| Reviewer | «Название готового шага не является результатом. Принимать по короткой карточке опасно для смысла работы». | Показать тело именно выбранного шага и его ссылки; status отдельно. Принятие остаётся в review с criteria/permissions. Приоритет открытого вопроса не меняется ради красивого review-кадра. Если нужно больше одновременного чтения, VT2 имеет содержательное преимущество. |
| Руководитель проекта | «Оценка, релиз и план — моя частая работа. Ваше “другое” не значит редкое». | Согласиться с возражением: частота неизвестна, H11 включает эти поля. Раскрытие сохраняется во время работы с Task, но повтор между задачами учитывается. При систематической цене выбирать VT2 для широкого рабочего контекста либо пересмотреть состав VT1; роли не персонализируются автоматически. |
| Пользователь клавиатуры | «Две копии поля или перестановка CSS заставят терять место; скрытая ошибка останется в закрытой группе». | Один экземпляр каждого поля, обычный DOM-порядок и native details. Поповер возвращает фокус своему триггеру; resize не создаёт новые редакторы. Ошибка дополнительного поля раскрывает его группу до переноса фокуса. Если это нельзя сохранить на текущих callbacks, вариант не принимается. |
| Сопровождающий DS | «Не создавайте TaskSummary-компонент из продуктового приоритета и не выдавайте page layout за drawer API». | Все бизнес-группировки и `workFocus` остаются в Sprintique. Проверены реальные public property / work-story / editor / dialog recipes. В DS передаётся только подтверждённая проблема чтения property list при text200, без общего алгоритма “что важно”. |

Предварительное разрешение спора: VT1 — первый обратимый product prototype; VT2 — обязательная альтернатива для читателя/reviewer и частого планировщика; C — простой запасной способ проверить порядок без раскрытия. Принятие остаётся по ролям и задачам, не по числу согласных аналитических перспектив.

## 7. Единственный подтверждённый общий DS-вопрос

**Property list при увеличенном тексте.** На E5 две обычные подписи уже сокращены, хотя места в текущем drawer относительно много. В DS54 это связано с фиксированной колонкой 120 px, `white-space:nowrap; overflow:hidden; text-overflow:ellipsis`, `line-height:20px` и фиксированной геометрией ghost triggers при rem-типографике. Это воспроизводимое сочетание публичного recipe и text scaling; перенос семи строк не устранит его у четырёх оставшихся. [E5, S7]

Сначала проверить разрешённую настройку `--iq-properties-label` в реальном узком контейнере: она может исправить конкретную ширину, но сама по себе не даёт полноценный stacked/wrap contract. Если потребитель всё ещё не может показать полные подписи и доступное значение, запросить минимальный **общий контракт reflow property list** в DS с проверкой label/value, readonly и editable при text200 / narrow. Не обещать здесь уже выбранные имя нового API и package version. Продукт не патчит внутренние `.iq-select-*`, не уменьшает текст и не делает свой заменитель поля.

Не доказаны отдельные DS-пробелы «Task goal card», «умный приоритет атрибутов», новый sidebar slot или новый tab API. Текущий work overview теряет `status` в **продуктовом** выражении `text || status`; это не недостаток DS. `.54` уже исправляет геометрию вкладок, повторно открывать WP02B ради компенсации высоты не нужно. [S3, S7, S10]

Две композиции можно проверить на существующем DS54. Финальную UI-приёмку text200 нельзя объявлять, пока видимая проблема свойств не разрешена или не найден работающий публичный способ композиции. Это ограничение конкретного режима, не повод остановить весь продуктовый срез.

### Предел первого среза

На исходных кадрах нет обложки, personal request и настоящего workPlan. Обложка в текущем коде находится **перед title** и имеет собственную высоту; длинный personal request тоже занимает место. Не скрывать их в сравнительном fixture ради красивого первого экрана и не распространять результат no-cover случая на эти состояния. Перед общим применением проверить их отдельно: если они снова оттесняют смысл, потребуется обоснованное решение об их месте, а не уменьшение заголовка. [S1, S2, S12]

Новый Task использует тот же renderer, но имеет явную кнопку создания, другую template/default-priority семантику и ещё не сохранённые attachments/links. Группировка не должна автоматически считаться принятой для создания на основании проверки существующей Task.
