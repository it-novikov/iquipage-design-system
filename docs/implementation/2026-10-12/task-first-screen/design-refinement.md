## 2. Обоснование и границы результата

Основная причина остаётся прежней: перед реальным описанием renderer размещает 11 равномерных строк свойств. На лично просмотренном desktop light 1280×720 текст описания не помещается в первый экран; более высокий desktop dark показывает его начало. Эти изображения обосновывают проблему приоритета и доступного места, но не частоту использования полей или превосходство нового варианта. Пустота значений synthetic fixture ничего не говорит о редкости оценки, типа, релиза или плана. [P] [E0]

Отдельная причина H02 доказана исходником. В workOverview для review возвращается название шага; renderer выводит text || status. Даже видимое «Результат на проверке» рядом с названием ещё не показывает результат. Новая проекция берёт текст именно из result шага, который уже выбрал workFocus; она не получает новое определение «актуального» или «последнего» результата. Открытый вопрос по-прежнему имеет приоритет перед первым готовым непринятым шагом. [M] [W]

У обычной Task нет отдельного структурированного поля goal или nextAction: смысл хранится в настоящем Markdown, сформированном пользователем и существующими шаблонами. Перенос описания выше делает этот смысл доступнее, когда он там написан. Он не создаёт отсутствующие цель, критерий или следующий шаг и не исправляет слабое содержание шаблона автоматически. [T] [TM]

Предпочтение VT1 остаётся предварительным: он сохраняет привычный drawer и прямое редактирование статуса, исполнителя, срока и приоритета, а вход к остальным контролам находится до длинного документа. Цена — раскрытие дополнительных полей, в том числе потенциально частых, при переходе между задачами. Именно эта цена может изменить выбор.

Для первого сравнительного render верхний summary использует нынешние публичные work-story/head/copy/question recipes. Он не получает дополнительную вложенную рамку. Упрощение его существующей внешней рамки до plain work-story допустимо как отдельная эстетическая проба, если actual render покажет лишнюю тяжесть; это не часть обязательной первой дельты. Смысловая иерархия важнее нового декоративного оформления: главный заголовок — Task, название шага — предмет краткой сводки, статус — ясный контекст, result — обычный читаемый текст, действие — переход к полной проверке. [T] [W]

Native раскрытие открывается одной командой и остаётся открытым до явного закрытия или закрытия Task, включая переходы Task/Work и fullscreen. Повторное открытие другой Task начинает с устойчивого исходного состояния. Частый переход между задачами поэтому действительно может требовать повторных раскрытий; это не скрывается из H11. Popover должен вернуться к своему единственному trigger. Ошибка дополнительного поля раскрывает его группу перед переносом туда фокуса. Ни poll, ни resize не перемонтируют контролы.

Длинный title, hint и result переносятся; нет fixed-height summary и незаметного line-clamp. Тёмная тема использует те же DS-токены и смысловые сигналы. При text200 сохраняется известная входная проблема property reflow: новая группировка не считается её решением. Полный label/value, читаемость и достижимое действие важнее обещания уложить весь экран в заданную высоту. Readonly/accepted reason, overdue words и тон остаются прежними. [P] [T] [B]

## 4. Короткий result: конкретный presentation-контракт для пробы

Review summary читает уже вычисленный focus из того же state, который использует полный Work view. Предмет — focus.item.title; переход — существующее действие review с исходным focus.item.id. Title не подменяет результат. Пользователь не получает выдуманный номер шага или утверждение «последний по времени». [M] [W]

Предварительное правило preview:

1. Взять весь сохранённый focus.item.result, пропустить через существующий workText, убрать крайние пробелы. Не ограничиваться первым абзацем: он сам может оказаться только заголовком.
2. При пустом нормализованном тексте показать «Описание результата не добавлено». Это не означает отсутствия evidence, фактической работы или возможности проверки.
3. При коротком тексте показать его целиком с подписью «Результат шага». При длинном — буквальное начало с подписью «Начало результата» и видимым многоточием. Начальный внутренний предел для пробы — до 160 Unicode code points, с предпочтением ближайшей предыдущей границы слова; для длинного непрерывного токена допустимо сокращение по этому пределу.
4. Это предел для первого render, не новый DS API, не фиксированная высота и не окончательный acceptance-контракт. Его пересматривают, если long title/result, narrow или H11 обнаружат потерю предмета или чрезмерное оттеснение свойств. Нормализация и сокращение не создают резюме и не изменяют сохранённый result.
5. Текст передаётся через существующий escaping; он не становится HTML и не получает новый renderer evidence/ссылок. Полное содержание доступно в прежнем Work review.

Кнопка перехода находится в верхней группе рядом с состоянием/названием и **до preview в DOM**; при нехватке ширины переносится естественно. Она не уезжает за полный длинный результат и не принимает решение. Approve/reject, criteria, evidence, revisions и существующие permission gates остаются в полном review. Название выбранного шага сохраняется даже при длинном result, чтобы фрагмент не оказался без предмета.

В первом срезе не добавляются тела what/next/complete, checkpoint или session summary в обычный overview. Это ограничивает вмешательство конкретным недостатком H02 и не создаёт одновременно несколько новых повествовательных блоков. Никакой новый сетевой запрос не требуется. [M] [W]

## 5. Самый небольшой полезный actual render на существующем frontend

Здесь ничего не запускается и production-код не меняется. Ниже — следующий конкретный обратимый опыт в среде, где существующий frontend и браузер доступны.

**Начать с source baseline и VT1 на DS54, с одинаковыми данными, drawer и viewport.** Первый основной размер — 1280×720 light при root text 100%: именно на нём исходный кадр показывает недостаток места. Для обычной заполненной Task без workPlan сравнение изолирует порядок свойств. Для review сравнение дополнительно проверяет новую содержательную проекцию; её эффект не приписывается только экономии высоты.

Использовать уже существующий frontend вход [product.html][FH] / [product.js][FJ]. Он импортирует настоящий openTaskDialog, mountTaskBoard и реальные стили DS/Product/Workbench. Для него существуют параметры surface=board, theme=light/dark, density=comfortable, text=100/200. Bootstrap и ответы adapter остаются явно synthetic. Не создавать вторую демонстрационную Task, новый набор компонентов, отдельную платформу, workflow или зависимости.

После разрешённой изолированной реализации кандидат меняет существующие composition/summary entry points, а контролируемые чтения для обеих сторон задаются в существующем [repository.js][FR]. Нужны содержательно одинаковые состояния:

- Обычная Task с написанной целью, критерием и конкретным следующим действием в реальном Markdown, а также заполненными значениями свойств. Одна общая фраза текущего tabs fixture недостаточна для H01.
- Review выбранного шага с реальным result; точный исходный пример уже есть в [work-preview-seed.ts][FS]: результат о сохранении истории после обновления страницы. Для review открытый вопрос этого seed должен быть разрешён штатно в данных сценария, иначе selector обоснованно покажет вопрос. Отдельно проверяется вопрос без права ответа и отсутствие result. Это контролируемые примеры, не поведение участников.

Оба render используют одинаковые package/tar hash, описание, result, права, имена и viewport. Сохраняются кадры первого экрана с начальным scroll, а для спора о раскрытии — тот же экран с открытой группой. Достаточно записать source/data fingerprint и условия вместе с изображениями; новая система отчётности не требуется. По фактической паре можно измерить начало читаемого описания и видимость результата/перехода, но не скорость человека.

Затем проверить конкретные оставшиеся риски: узкий размер с наиболее длинным title/result, тот же размер в dark для чтения и иерархии, text200 для label/value и переноса. Если смысл снова оттеснён, это отрицательный результат данного режима, а не основание тайно уменьшить шрифт или скрыть часть названия. Размеры 390×844 и 320×720 уже известны из входных кадров; выбор следующего кадра отвечает обнаруженному риску. Cover и длинный personal supplement проверяются перед распространением вывода на эти случаи.

Существующий [tabs-geometry-browser.mjs][FB] уже умеет Vite build/capture, но его runner выполняет полный набор Minimal/Board/Wiki и принимает только --build-only как CLI-флаг. У него нет режима --task-only или переключателя VT1. Поэтому не придумывать команды и не расширять этот harness ради эксперимента: можно открыть существующий product.html через уже доступный Vite/browser путь и получить выбранные кадры имеющимися средствами. PASS геометрии tabs не является PF04 PASS.

### Где начинается настоящая проверка H11

Текущий synthetic repository бросает Unsupported synthetic operation при Task write, а /work возвращает пустой plan. После подстановки read fixtures можно проверить композицию, реальное раскрытие, Tab order, открытие доступных контролов и переход к выбранному review. Это не подтверждает сохранение, планировочную запись, автосохранение или конфликт. [FR]

Для H11 использовать существующий продуктовый preview/backend с одноразовыми тестовыми Task и прежними адаптерами. Выполнить действительное изменение исполнителя/срока и последовательность оценка → тип → релиз → план; закрыть Task, вернуться к месту списка, открыть снова и подтвердить сохранение. Type должен сохранить существующий offer/template/default-priority сценарий; Plan — собственный preview/commit. Нельзя заменить это read-only PNG или фиктивным успешным save.

Если backend недоступен, честный результат этапа — «композиция и доступ к контролам проверены; H11 сохранение NOT_RUN». Реальные участники нужны, чтобы утверждать снижение ошибок, понятность без подсказки или выигрыш рабочего темпа. Экспертный walkthrough может выявить дефект, но не подменяет такое наблюдение.

### Когда добавлять альтернативу

VT2 включается, если в широком рабочем контексте reviewer или планировщику требуется одновременно видеть длинное содержание и постоянно открытые атрибуты. Тогда сравнивается **нынешний fullscreen baseline**, а не только узкий drawer; цена самого перехода в fullscreen учитывается отдельно. Ширина двух колонок и перенос в одну остаются гипотезой из оригинала.

C включается, если цена или обнаружимость disclosure стала решающим вопросом: те же summary/данные/ширина, но весь список свойств открыт после содержания. Его цена зависит от длины документа. Это уместный контроль порядка без раскрытия; победа на короткой Task не переносится на длинные. Число вариантов следует вопросу.

| work-model.js: presentation copy | Нейтральный question status при отсутствии canAnswer. workFocus и серверный контракт не меняются. Пробная нормализация/префикс не изменяют сохранённые данные. |
| board.css и применимые Workbench grid areas | Только необходимая композиция контейнеров; проверить personal/fullscreen overrides. Не превращать срез в общий CSS cleanup и не переопределять внутренности DS select/date/editor/tabs. |
| Существующие read/form/flush/type/plan/grants/callers | Поведение сохраняется и проверяется для затронутого пути. Раскрытие не записывает данные; mounted controls ровно по одному; нет role-specific reorder. |

Приёмка первого среза состоит из проверяемых исходов:

- На основном сопоставимом кадре ordinary Task видно содержательное начало настоящего описания, а не только заголовок «Описание». Сформулировать цель, критерий и следующий шаг всё ещё должен позволять сам текст.
- Review показывает нейтральное состояние, предмет выбранного шага, реальный короткий result либо точную нехватку его текста и достижимый переход. Title, generated summary и время session не считаются result. Приоритет вопроса остаётся прежним.
- Четыре прямых свойства сохраняют прямое действие; дополнительные можно найти и последовательно изменить без повторного раскрытия в том же эпизоде. Цена раскрытий между задачами фиксируется отдельно.
- Нет потери draft, двойного name, focus jump при resize/poll, недостижимой ошибки закрытой группы или подмены Plan write. Readonly, accepted и permission-различия проверяются прежними путями.
- Длинный текст, narrow, dark и text200 читаемы в заявленном режиме. Если input DS property reflow остаётся дефектным, этот режим не получает визуальный PASS.

VT1 пересматривается, если hint не помогает найти планировочные поля, повторные раскрытия заметно мешают частой работе, начало описания всё ещё не доступно на целевом размере или короткий result не даёт понять предмет. Возможные ответы — C для короткого документа, VT2 для подтверждённого широкого пути или пересмотр устойчивой группировки. Ни число четырёх строк, ни 160 code points, ни экономия высоты не становятся самоцелью.

Единственный доказанный общий DS-вопрос остаётся прежним: публичный property list при text200 не даёт достаточного reflow label/value в текущем контейнере. Сначала проверить разрешённую настройку ширины label; при её недостаточности нужен минимальный общий reflow contract. Новый TaskSummary, sidebar API или общий алгоритм приоритетов из этой работы не следуют. [P]

Лично просмотрены все пять исходных PNG Task; прочитаны frozen Task renderer, модель работы, реальные шаблоны/права/контейнеры и public DS54. Новый вариант не реализован и не отрендерен. Browser rerun, человеческие задания, backend save и пользовательское сравнение не проводились. Следующий результат — минимальная сравнимая реализация на существующем frontend; согласованная гипотеза ещё не означает принятую production UI.
