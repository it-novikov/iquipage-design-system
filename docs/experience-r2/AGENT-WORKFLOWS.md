# UX R2 — процессы совместной работы людей и агентов

Статус: исследованное предложение. Не готовый runtime и не обязательство реализовать весь агентный стек до исправления интерфейса. Модель согласуется с параллельным backend-агентом. Источники — [RESEARCH](RESEARCH.md).

## 1. Продуктовая граница
Sprintique организует работу над задачей и проверяемым результатом: кто отвечает, кто исполняет, какой контекст разрешён, что считается результатом, кто принимает и что происходит при сбое. Не строим универсальный редактор интеграций, где пользователь соединяет сотни провайдерских операций и преобразует JSON между портами.

Рабочая формула: **задача → исполнитель/команда → результат → проверка → принятие**. Она применима к человеку, внешнему агенту или смешанной команде. Простая задача решается одним исполнителем; процесс и дополнительные роли добавляются только при потребности. Пользователь не обязан рисовать граф перед делегированием.

Сохраняем детерминированные правила без LLM: напомнить, назначить проверку, обновить допустимый статус, создать обсуждение по событию PR/MR. Такие правила и агентные шаги могут участвовать в одном процессе, но вызов модели не становится движком каждого перехода.

Не входят по умолчанию: произвольные HTTP/SQL/code-узлы; marketplace коннекторов; неограниченные циклы агентов; свой IDE, CI или облачный runner; самопроизвольное создание подагентов; автоматическое слияние/деплой; LLM на hover, поиск и сортировку. Внешний исполнитель и провайдер отвечают за execution environment; Sprintique показывает возможности и управляет разрешённой оркестрацией.

## 2. Три уровня, а не три обязательных продукта
Первый уровень — «Поручить агенту» в существующей задаче: выбрать подключённого исполнителя, понятную цель, разрешённый контекст и ожидаемый результат. Хорошие настройки проекта подставляются, редкие поля не обязательны. Отсутствие подключённого исполнителя объясняется; запуск не симулируется как реальный.

Второй — «Процессы команды» в настройках проекта. Пример шаблона: «Подготовить изменение и проверить его». Основной редактор — упорядоченные шаги с ролями, результатами и точками проверки. Шаги можно добавлять/переставлять без рисования стрелок; параллельный блок явно показывает, какие результаты нужны для продолжения. Представление схемой — дополнительное, а не условие настройки.

Третий — карточка процесса на карте. Она ссылается на ту же опубликованную конфигурацию и показывает краткое состояние конкретного запуска. Открывает тот же редактор/журнал. Не копирует процесс внутрь MapDocument. Геометрия и декоративные связи карты не являются программой исполнения.

## 3. Минимальный набор блоков процесса
| Блок для человека | Смысл | Чего не делает |
|---|---|---|
| Выполнить работу | Поручение человеку либо разрешённому агенту; цель, контекст, выход | Не даёт глобальный доступ ко всем данным |
| Проверить результат | Тесты/CI, проверка критериев или ограниченное экспертное ревью | Не превращает мнение модели в факт успешного теста |
| Получить решение | Ответ/принятие уполномоченного человека | Не считает молчание согласием |
| Дождаться события | Конкретное событие задачи/PR/MR/проверки с версией | Не запускает LLM для polling без необходимости |
| Обновить работу | Ограниченная продуктовая команда или уведомление | Не обходит права, подготовленность и подтверждение состава |

Начальное условие, завершение, ветка отказа и лимит повторов относятся к процессу. Это не отдельные технические карточки на холсте. «Если проверка не прошла» — простой явно ограниченный повтор исправления или передача человеку. Полный произвольный язык выражений не нужен; расширение словаря требует реального сценария.

## 4. Пример первого полезного процесса
Человек выбирает подготовленную задачу и поручает изменение подключённому агенту-разработчику. Агент работает в своей изолированной ветке/среде, возвращает diff или PR, краткую сводку и доказательства проверок. CI подтверждает тесты конкретного commit SHA. Необязательный агент-ревьюер проверяет ограниченный риск. Ответственный человек принимает результат или даёт уточнение. Только после соответствующего события меняется рабочий статус задачи.

Безопасный default: один агент выполняет работу, автоматические тесты проверяют, человек принимает. Дополнительного «менеджера агентов» не запускаем на каждую задачу. Для независимых фронт/бэк/QA-частей допустимы параллельные исполнители, но нужны согласованный контракт, раздельные области изменений и ответственное сведение результата. Два агента не редактируют одну ветку одновременно без контроля конфликтов.

Экспертный агент не является автоматически независимым контролем: одинаковая модель и контекст могут повторять одинаковую ошибку. Его вывод — дополнительное evidence, не замена CI, продуктовой проверки или обязательного человеческого approval. Для некодовой работы результатом может быть документ или исследование с источниками; от пользователей не требуется PR в каждом процессе.

## 5. Предлагаемая модель и разделение владения
Это смысловые контракты для согласования, не новые имена таблиц/маршрутов поверх backend другого агента.
| Объект | Назначение |
|---|---|
| Task | Каноническая задача, содержание, подготовленность, рабочий статус, revision |
| Responsibility | Человек/команда, отвечающие за результат; не исчезает после делегирования |
| Delegation | Конкретный исполнитель human/agent и цель поручения; не новый тип задачи |
| TeamProcessVersion | Неизменяемая опубликованная версия шагов, ролей, ограничений и критериев |
| ProcessBinding | Где процесс разрешён: проект/задача/категория и события запуска |
| Run / StepAttempt | Один запуск и конкретные попытки шагов; состояние исполнения отдельно от задачи |
| Proposal / Evidence / Decision | Предложенное изменение, артефакты и конкретное решение по ним |
| Mandate / BudgetReservation | Проверяемые полномочия, срок, ресурсы и резерв лимита до вызова |
| MapReference | Ссылка карты на Task/Process/Run; геометрия не владеет их бизнес-состоянием |

Используем существующие backend-понятия mandate, proposal, approval, run, audit/outbox. Не заводим для «процессов команды» второй механизм полномочий и исполнения. Человек может выполнить шаг, который первоначально предназначался агенту, с явным новым attempt и авторством; прежняя история сохраняется.

Состояния разделены: процесс ещё исполняется/ожидает/остановлен; результат предложен/принят/отклонён/устарел; изменение сохраняется/подтверждено/в конфликте. «Агент закончил» не означает «Задача готова», «Релиз завершён» или «Код опубликован». Не показываем внутренние схемы состояний одной длинной гирляндой на карточке; пользователю нужна одна актуальная причина ожидания и следующий шаг.

В UI задачи сохраняется ответственный человек; агент виден отдельным исполнителем поручения. Отсутствие назначенного человека не создаёт скрытого owner по умолчанию: перед требующим approval действием нужен явный approver либо уполномоченная команда из политики проекта. Агента визуально отличаем от человека, не используем человеческую аватарку для сокрытия actor.

## 6. Контекст и полномочия
Контекст собирается из разрешённых task/map-object/discussion/repository ссылок с зафиксированными версиями и ограничением объёма. По умолчанию не отправляется вся карта, весь проект, все обсуждения или приватные файлы. В UI до передачи видны источники и внешний получатель данных. Инструкции из текста задачи/комментария/результата инструмента не могут расширить mandate, выбрать новые secrets или изменить policy.

Роль «Разработчик», её инструкция и набор предпочтительных инструментов не равны правам. Права действуют на пересечении grant инициатора, grant агента и ограничений конкретного поручения. Отзыв проверяется перед следующим действием; поздний callback остановленного/отозванного запуска не принимает изменение автоматически. DS рисует capability-состояния, но backend остаётся источником решения.

## 7. Принятие, проверка и история
Approval относится к hash конкретного proposal, task revision, process version, commit SHA, сроку действия и approver. Новый commit или изменившийся task scope делает старое подтверждение непригодным. Нажатие «Принять результат» не является универсальным разрешением на будущий merge/deploy. Для merge и других внешних эффектов применяются отдельные правила проекта/репозитория. Агент не подтверждает собственное повышение прав.
В задаче показывается компактный блок «Работа команды»: кто делает, что уже готово, что требуется от человека, артефакты и стоимость при её наличии. Подробности исполнения открываются по запросу. Не показываем/не требуем приватный chain-of-thought; нужны краткое обоснование, источники, diff, тесты и ошибки. Вопрос агента создаёт структурированный тред; ответ человека возобновляет нужную попытку, а не запускает второй процесс.

## 8. События GitHub/GitLab и защита от повторов
Входящие PR/MR/CI-события нормализуются провайдерским адаптером: идентичность репозитория, объект, действие, commit/base SHA, actor, provider event ID и время. Подпись webhook и права проверяются до обработки. Идентичные доставки не создают повторный effect; события не всегда приходят по порядку, поэтому переход проверяет актуальное каноническое состояние.
Не принимаем «PR закрыт» за «PR слит». Проверка старого SHA не подтверждает новый commit. Несколько PR одной задачи не означают завершение после первого merge. Squash/rebase, повторное открытие и отзыв ревью учитываются через версионированную связь артефактов. Слияние кода, тестирование, принятие результата и выпуск — отдельные факты.
Изменение состава активного релиза от автоматизации использует ту же команду и preview/approval, что перенос человеком, либо специально заранее выданный ограниченный mandate. Закрытие релиза при незавершённой работе не обходится сценарием. Изменение task status агентом не должно бесконечно запускать его же через event loop: нужны correlation/causation IDs, семантическая дедупликация, лимит повторов и pause.
Настройка события — не платный запуск. Перед включением доступны просмотр «когда сработает», тест на синтетическом/историческом обезличенном событии без внешних действий и показ будущих эффектов. Включение требует версионированной публикации; правки черновика не меняют работающий процесс. Активный run закрепляет версию; переход на новую явно создаёт новый run/continuation с повторной проверкой.

## 9. Сбои, параллельность и остановка
Потеря ответа после внешнего вызова даёт «Результат уточняется», а не кнопку слепого повтора. Повтор использует receipt/idempotency провайдера или reconciliation. Если провайдер не даёт безопасной проверки, требуется решение человека. «Остановить» прекращает будущие шаги; уже созданный PR или отправленное сообщение не исчезает. Компенсация отдельно подтверждается и существует только для обратимых действий.
Пауза, отмена и повтор не смешиваются. При паузе исполнитель прекращает выдачу новых действий в пределах поддержанного контракта; если внешняя система не поддерживает паузу, UI говорит об этом. Отдельный attempt сохраняет предыдущие артефакты и ошибки. Нельзя объявить внешнюю отмену подтверждённой только потому, что frontend убрал spinner.
Редактирование человеком во время работы агента не затирается поздним proposal. Права и версии перепроверяются при принятии. Изоляция worktree помогает файлам, но не заменяет сравнение версии задачи. После потери инициатором членства grant не продолжает действовать бессрочно. Human takeover переносит ответственность за продолжение явно, сохраняя audit.

## 10. Экономика LLM: полезность измеряется принятым результатом
В первом пилоте достаточно одного сценария «задача → изменение/PR → проверки → человек» и ручного запуска сводки длинного обсуждения с источниками. Сводка пересчитывается по изменившемуся контексту, а не при каждом открытии. Ключевые даты, переносы, фильтры, поиск по словам и обработка статусов выполняются без LLM.
Показываем до запуска режим расхода и лимит; различаем лимит платформы, резерв, фактические единицы и оценку стоимости. Неизвестная цена внешнего агента обозначается как неизвестная, а не нулевая. Резервирование атомарно: несколько параллельных шагов не должны одновременно потратить один остаток бюджета. Учитываются неудачные платные попытки и задержанная отчётность провайдера.
Если провайдер не поддерживает твёрдый потолок затрат или отмену активного запроса, платформа не обещает абсолютный hard cap. Она ограничивает новые вызовы и объясняет возможный остаточный расход. Дополнительные роли, reviewer, параллельные ветки и итерации включаются осознанно. Сначала измеряем полезные принятые результаты, стоимость на принятый результат, доработки человеком и время ожидания; количество вызовов/агентов не является продуктовым успехом.

## 11. Возможности интеграции, а не обещание совместимости со всеми агентами
Agent adapter сообщает поддержанные действия: начать, запросить состояние, ответить на вопрос, отменить, перечислить артефакты и расход, работать с ограниченным контекстом. Отсутствующее действие видно в UI. Прямой API и будущий MCP используют те же use cases/policy; не добавляем новый независимый сервер полномочий. Реальное подключение и оплату провайдера согласуем отдельно.

## 12. Порядок внедрения
Сначала компактная оболочка/Планирование и упрощение обычной карты. Затем редактор процесса как прототип и контракт; затем один настоящий внешний исполнитель с callback/recovery, CI-доказательством и human approval. После проверки полезности — ограниченные GitHub/GitLab-события, второй агент-ревьюер, параллельные независимые шаги и выборочные правила запуска. Не задерживаем исправление неудобного списка ради гипотетического многоагентного «центра управления».

## 13. Тонкая настройка без технической перегрузки
Редактор выбранного шага открывает четыре группы: «Результат», «Исполнитель», «Контекст», «Проверка». Пример шага: «Подготовить изменение»; исполнитель — выбранный подключённый агент; контекст — эта задача и выбранный репозиторий; результат — PR с описанием; проверка — согласованные CI-проверки и решение ответственного. Сложность раскрывается по потребности, а не требует заполнить все поля для старта.
В «Дополнительно» доступны только параметры, которые поддерживает adapter: провайдер/модель, версия инструкции и навыков, разрешённые инструменты/области репозитория, выходной формат, лимит времени/попыток/расхода, стратегия ошибки, условие следующего шага. Неподдерживаемое значение не исчезает при открытии: объясняется несовместимость. Ограничения безопасности нельзя повысить сменой UI-пресета.
Роль/набор инструкций и процесс версионируются независимо. Проект задаёт рекомендуемый набор; процесс закрепляет его версию; шаг может явно переопределить только разрешённые поля. До публикации показывается итоговая конфигурация и отличие от наследованной. Изменение шаблона проекта не переписывает активные запуски. Список больших многострочных промптов по всему холсту не является основным редактором.
Условие перехода собирается из понятных проверок «результат принят», «нужны изменения», «проверки прошли», «получено указанное событие», с видимой веткой иначе. Несовместимые/неполные ветви обнаруживаются до публикации. В первом варианте не нужен скриптовый язык. Для параллельного блока явно выбирается ожидание всех обязательных результатов; раннее продолжение по одному результату — отдельное осознанное правило.
У процесса доступны черновик, проверка структуры, тест без внешних эффектов, публикация и пауза новых запусков. Пауза новых запусков не отменяет существующие. Перед повтором предлагается повторить конкретный неуспешный шаг либо начать новый запуск; зависимые результаты после изменённого входа получают статус «Нужно перепроверить». Нельзя использовать старое успешное ревью после изменения diff.

## 14. Совместная команда и место человека
Человек может выполнять любую обычную работу процесса, не только нажимать «Принять». Например: дизайнер прикладывает решение, агент-разработчик реализует, человек-тестировщик проверяет на устройстве, агент готовит сводку изменений, владелец подтверждает выпуск. Результаты каждого шага проверяемы и привязаны к версии; агенты могут задавать вопросы друг другу в пределах разрешённого контекста, но не расширяют состав команды и бюджет без мандата.
В задаче человек видит не постоянный чат всех агентов, а текущую работу, один следующий запрос внимания и готовые результаты. Вкладка/раскрытие «Все действия» даёт историю попыток. Уведомления группируются по задаче и причине; поток технических событий не засыпает основной inbox. Тихое успешное действие не требует отдельного модального окна.
Если задача меняется в Планировании, активный процесс не продолжает работать по старой цели незаметно: можно завершить текущий результат по зафиксированному контексту или пересогласовать поручение. Операция переноса релиза не всегда требует остановить разработку; это решение политики конкретного процесса, явно показанное в preview. Изменение геометрии карты само по себе не инвалидирует кодовую проверку.
