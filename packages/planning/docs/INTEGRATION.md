# Planning PN2 — подключение к vNext

## Владение
`src/` — frontend consumer, не доменный сервер. `types/index.d.ts` фиксирует read-проекцию и интерфейс операций для адаптера. Backend-агент владеет каноническими контрактами, авторизацией, SQL/транзакциями, outbox и SDK. Названия методов адаптера не навязывают HTTP URL, схемы таблиц или генератор SDK. `demo/` никогда не импортируется production-приложением.

## Точка входа
```js
import {mountPlanning} from '@sprintique/planning-ui';
import '@sprintique/planning-ui/styles.css';
const planning = await mountPlanning(root, {
  adapter, project, viewState,
  onOpenTask, onCreateTask, onCreateRelease, onOpenBoard
});
```
Хост предоставляет одну совместимую IQUIPAGE через публичные `@iquipage/web/core` и `@iquipage/web/advanced` и её CSS. Каталог/расширения не регистрируются повторно. В PN2 import map стенда указывает на собранную копию board.7. Это временная упаковочная граница; независимую библиотеку и новый SDK не создаём параллельно с их владельцами.

## Read-модель
`listGroups` получает проект, строку поиска, подготовленность, порядок и cursor. Возвращает версию проекции, разрешённые группы/счётчики, следующий cursor и возможности. `listRows` дополнительно получает groupId, ту же revision и свёрнутые Task ID. Возвращаемый порядок, контекстные предки, счётчики и принадлежность вычисляются адаптером нового backend, не браузером.
Строка содержит только отображаемые поля, собственный rowId и canonical taskId. Контекстный предок не выбирается и не считается ещё одной задачей. Тела Markdown, вложения, треды и все задачи проекта не нужны для первой страницы. Числа 50/200 в стенде — окна запросов, не лимиты задач в релизе.

## Запись
`preview(intent)` → конкретный snapshot token / expiry / изменения / запреты → `commit(token, idempotencyKey)` → receipt. Мутация с неизвестным результатом получает `uncertain`: интерфейс не повторяет эффект и запрашивает `receipt(key)`. Нужны серверные revisions, проверки scope/прав, дедупликация и атомарность. `{definitive:true}` в ошибке адаптер ставит только при доказанном отсутствии сохранения; произвольный HTTP 4xx после неясного предыдущего результата не является таким доказательством.
Сохранённый SDK receipt journal с восстановлением после полного закрытия вкладки относится к PN3. В PN2 recovery тестируется внутри открытой операции. Подтверждение в UI не заменяет серверную проверку полномочий.

## Документ и навигация
Callbacks открывают существующий единый документ. Хост вызывает `onChanged` после подтверждённого сохранения и `onClose` после реального закрытия; возвращает modal с `close()`. Перед сменой раздела проверяется `planning.readyToLeave()`, затем вызывается `destroy()`. Нельзя уничтожать область с незавершённым сохранением. При переходе с карты ожидайте её асинхронный `destroy()`, иначе позднее очищение карты удалит следующий экран.

## Что передавать backend-агенту
Текущий пакет, `BACKEND-BRIEF-R2.md`, публичные типы и проверки. Adapter PN3 должен пройти тот же набор projection/operation тестов и дополнительные реальные API/ACL/concurrency tests. Не переносить `fixture-repository.js` или `fixture-adapter.js` в API/worker. Старый репозиторий Sprintique не изменяется и не используется во время работы нового экрана.
