# Sprintique vNext — передача Planning R2 backend-агенту

Дата: 12 сентября 2026. Статус: проектирование, не реализованный экран/API.
Полный комплект из пяти новых MD, матрицы приёмки и исходного архитектурного документа приложен в чате как Sprintique-vNext-Planning-R2.zip. Этот файл — самостоятельная краткая передача, не копия всего архива.

## Новая граница
Старый it-novikov/Sprintique не поддерживаем: его backend, React frontend, URL, схемы, авторизацию, финансы и другие разделы не переносим ради паритета. Старый Planning P0/R1 superseded по этому scope. В его PR больше не вести реализацию. Сохраняем одобренный фронт v3.4 и IQUIPAGE, подключаем их к новой платформе через общий SDK. Переписывание на React не требуется.

Основание: приложенный владельцем «Sprintique vNext — архитектура и план новой платформы», Proposed r1, и последнее уточнение о новой версии с нуля. Его стек/репозиторий не считаются автоматически утверждёнными; конкретный commit нового backend пока не предоставлен. В текущем проходе UI repo проверен git fetch: main f3dd146, UI v3.4 37b2399. Код приложения/DS, старый репозиторий и БД не изменялись.

Наш трек отвечает за Planning UI/UX, продуктовый контракт, DS-GAP и consumer tests. Backend-агент владеет use cases, схемами/PostgreSQL, API/SDK, policy, audit/outbox, worker и серверными тестами. Extraction DS выполняет один согласованный владелец. Не создавать второй сервис планирования или альтернативные модели ради локального UI.

## Продуктовая модель
Основная навигация: Планирование → Доска задач → Карты. Настройки возле профиля; автоматизация и подключения внутри настроек. Авторизованный логотип ведёт на доску доступного проекта, гость — на стартовый экран. Материалы/Обзор не добавляются.

В Planning: Список / По времени / Даты. В списке группы активных релизов, будущих релизов и бэклог. Подзадачи раскрыты по умолчанию. Один Task ID в списке, доске, документе и ссылке карты. Флажок родителя не выбирает всех детей; «Выбрать с подзадачами» явно. Контекстный родитель в другой группе не становится второй выбираемой задачей. Выбор скрытых фильтром строк обозначается. Массовые действия — только в Planning.

Релиз гибкий, с произвольным составом и необязательными датами/дедлайном. Спринт — timeboxed-формат этого же Release, не второй Sprint aggregate. Настройка проекта влияет на новые пакеты, не на прошлую историю. Несколько активных релизов и работа без релиза допустимы. Нет WIP или лимита количества задач; лимит размера API-команды не является лимитом группы.

Scope Release нужно подтвердить: предложение R2 — один Project внутри Workspace. Приложенная архитектура этот выбор не фиксирует. Мультипроектность старой платформы не наследуется автоматически.

Подготовленность общей задачи «Черновик / Готова» отделена от рабочего статуса и результата. Несохранённая форма приватна до явной записи; обязательный старый PrivateDraft-сервис не требуется. Черновик можно предварительно включить в planned Release, но запуск не превращает его в ready автоматически. Старт фиксирует baseline и допуск, не сбрасывает шесть статусов доски и не меняет исполнителей.

Рекомендуемые режимы принадлежности: inherit / assigned(releaseId) / none. У эпика нет второго специального release-поля. None у ребёнка явно отключает наследование. Reparent тоже может изменить состав и проходит тот же контроль. Planning order не переписывает board rank.

## Критические команды
Перенос из активного релиза, в активный релиз, изменение состава через родителя и закрытие используют preview → подтверждение → commit. Preview содержит выбранные и реально затронутые задачи, последствия для детей и доски, source/destination, версии/policy, expiry и непрозрачный token. Сервер пересчитывает scope; affectedIds/confirm=true от клиента не являются полномочием.

Commit повторно проверяет tenant/права/мандат, версии и exact intent. Данные, audit, receipt и outbox фиксируются одной транзакцией. Повтор с тем же ключом не создаёт дубль; другое тело отвергается. Lost ACK отображается как неизвестный результат с проверкой receipt, не как локальный rollback. Undo — новая проверяемая команда. Обычный Task editor/worker/agent не обходят эти правила прямым PATCH releaseId.

Закрытие не равно деплою, merge PR, завершению всех задач или автоматическому архивированию. Ready-for-release — кандидат к явному принятию по policy, а не production-факт. Остаток распределяется в существующий/новый релиз или бэклог; можно продолжить текущий пакет. New destination + transfer + close атомарны. Timeboxed closure не публикует событие выпуска продукта.

Если открытый родитель/эпик переносится дальше, принятые результаты детей остаются в прошлом релизе: pin/history и current resolver должны согласоваться. Одного красивого snapshot при неверной текущей принадлежности недостаточно. Незавершённый ребёнок не остаётся под автоматически архивированным родителем. Смена родителя/повышение ребёнка только явно. Task ID, текст, файлы/обложки, треды и связи сохраняются.

Прямой перенос active→future/backlog сохраняет статус, но явно показывает прекращение активного исполнения; «Продолжить без релиза» — отдельный исход. Для больших составов нужен server-side prepared plan и безопасная финализация; частичная пачка не выдаётся за атомарный результат.

## Контракты для frontend
Нужны capabilities и разрешённые actions; cursor pages групп/задач/детей; compact Task row; Release summary с scope revision; effective membership и основания наследования; preview и command receipt; immutable close result; schedule/milestone/dependency projections. Полные Markdown/файлы/треды не загружаются для каждой строки. Counts permission-filtered и не зависят от DOM/page.

Use cases по смыслу: read Planning, create/update Release, prepare Task, assign/move scope, start Release, take/defer without Release, close/cancel, reparent, bulk edit, change dates/constraints, read receipt. Точные routes, enum и operation IDs публикует backend в едином contracts; frontend не заводит второй OpenAPI.

Плановая дата, deadline, граница timebox и фактические UTC timestamps не смешиваются. Данные без дат видимы. Сдвиг полосы релиза не сдвигает все задачи. «Связана с» не превращается во временную зависимость; calendar constraint включается явно. Map/list/roadmap используют общие IDs/commands, не независимые нарисованные стрелки.

SSE — разрешённые committed revisions с replay/resync, не CRDT. Отзыв доступа очищает доступный клиенту контекст. Outbox at-least-once с дедупликацией. Для опасного agent intent переиспользуется общий mandate/approval, привязанный к hash и revision. В нашем этапе нет live LLM, MCP-транспорта, deploy или платных вызовов.

## DS и работа по этапам
Сохранить v3.4; source-owned DS вместо string-patching, immutable 0.5.7 provenance, public exports и одна регистрация. Generic grouped hierarchy/selection/windowing — DS, Task/Release/permissions/network — продукт. Не подменять недостающий компонент локальной копией. Видимый keyboard focus и reduced motion проверяются отдельно.

PN-0 R2: проектирование. PN-1: согласовать contracts/DS ownership (M0–M1). PN-2: UI на явно обозначенных contract fixtures параллельно backend M2–M3. PN-3: реальный create draft→prepare→assign→start→board на API/PostgreSQL (M3–M4). PN-4: transfers/close/recovery (M4–M5). PN-5: timebox/roadmap (M4–M5). PN-6: два клиента/агент, v3.4 parity, a11y, нагрузка и финальный CI (M6–M7). Fixture PASS не равен готовности интеграции.

## Необязательная миграция
Основной запуск — пустая новая схема. MIG отдельно после стабилизации ядра: read-only консистентный экспорт → inventory/mapping → dry-run → подтверждение → staging → restartable import → reconciliation → активация. Ни in-place update, ни dual-write, ни совместимость старого API не нужны.

Core: выбранные пространства, проекты и данные задач с типом/описанием/статусами/приоритетами/датами/иерархией/номерами. TaskContext opt-in: чек-листы, теги, task relations, текстовые обсуждения и реальные байты файлов/обложек при наличии экспорта. Предварительный отчёт обязан явно показать, что не переносится; metadata без bytes не считается перенесённым вложением.

Старые токены/сессии/пароли/grants/invites и настройки automation не переносятся. Identity mapping не делается автоматически по email. Project visibility и новые роли подтверждаются отдельно. Неизвестные типы/статусы, orphan/cycle, конфликт номеров и отсутствующие файлы не исправляются молча. Старые releases не создаются/не запускаются в vNext автоматически.

Дедупликация по source workspace + kind + source ID + mapping version; читаемые номера резервируются серверным allocator. Replay не перезаписывает уже отредактированный человеком target. Import audit не подделывает текущего пользователя под исторического автора, старые events не вызывают webhook/email/workflow. Partial отчёт не объявляется полным success. Rollback затрагивает только ещё не изменённые данные конкретного import-run. При отсутствии export новая платформа работает независимо.

Backend может иметь отдельный параллельный трек; coordinator интегрирует по SHA/schema revision, не одновременной записью в один lockfile/contracts. Старый PR Planning не закрывался и не обновлялся в этом проходе. Новый repo не выбран молча; push/merge/deploy не выполнены.

Полный пакет в чате содержит 75 будущих сценариев приёмки, все NOT_RUN. Новые runtime/production/FPS проверки и независимое multi-agent review не заявлены. Важна проверка настоящего backend с PostgreSQL, двух клиентов, отказов/повторов, отзыва прав и чистого consumer DS, а не только число файлов или сборка.
