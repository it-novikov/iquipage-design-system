# Контракт событий и восстановления R4

## Подтверждённая запись

FileRepository сохраняет документ и envelope события в одном атомарном переименовании файла. При отказе записи канонический документ и очередь не изменяются. Это однопроцессная reference-реализация, не распределённая транзакционная БД.

Envelope schema=2 содержит ID события, projectId, recordId/revision, снимки правил, входные данные каждого получателя и inputMapRevision. Версия входных данных отделена от опубликованной версии workflow. Другой получатель в том же проекте также получает снимок на момент commit, а не произвольные более поздние данные.

Внешний `POST /api/events` не может назначить событию статус trusted. `dispatchCommitted` читает только каноническую сохраняемую очередь. Правило завершения архива допускается только при совпадении своей сессии, её финальной revision и перехода active/paused → archived. Расписание, webhook и ручной запуск этой льготы не получают.

## Доставка

Состояния: pending → delivered либо retry → dead. Успешная доставка означает передачу исполнителю, не успешное завершение workflow. Отдельные получатели изолированы: ошибка одного не подавляет остальных. Повтор сохраняет ID и input; уже созданный запуск возвращается без повторных задач.

Пределы reference store: 5 автоматических попыток, экспоненциальная задержка до 5 минут, до 3 явно подтверждённых ручных циклов повторов, до 10 000 ожидающих событий. Ошибка в формате/снимке сразу останавливает доставку. История хранит последние 500 результатов без содержимого заметок.

Правило, приостановленное или перепубликованное до доставки, пропускается. Старые envelope без снимка не пересчитываются по текущей карте: они помещаются в dead с SNAPSHOT_MISSING, доступны для просмотра и явного закрытия, но не для повтора.

## HTTP и UI

`GET /api/event-deliveries?projectId=…&mapId=…` возвращает очередь и историю для проекта/карты. Возвращаются состояние, revision самой записи доставки, число попыток, код ошибки и ссылки на запуски; не возвращаются входные заметки и снимки правил.

`POST /api/event-deliveries/{id}/retry` и `/dismiss`: JSON `{projectId, baseRevision}`. Только dead-событие, свежая версия и тот же проект. Retry не меняет вход и ID. Dismiss не удаляет документы, запуски и уже созданные задачи. Конфликт версии — HTTP 409, чужой/несуществующий ID — 404.

UI требует manageAutomation, повторно проверяет право перед отправкой и показывает диалог подтверждения. Production-адаптер обязан повторять авторизацию на сервере; reference-user не является полноценной системой ролей.

## Проверки и эксплуатация

`tests/outbox.test.mjs` покрывает сбои диска, рестарт, конкуренцию, повтор ack, снимки, архив, legacy-очередь и отравленного получателя. HTTP-тесты проверяют настоящие endpoints; browser-events-final и browser-delivery-recovery — настройку и журнал с видимыми действиями.

Для production нужны БД/outbox в одной транзакции, эксклюзивные leases работников, ACL, квоты, защищённые подключения и политика хранения. Ни файлы reference store, ни ключи окружения не входят в распространяемый архив.
